# Headscale CLI redesign

**Status:** draft, for discussion. This PR exists so we can shape the design together. It is not meant to be merged as-is.

The current CLI addresses targets inconsistently. Nodes take `--identifier` (ID only), users take `--identifier` or `--name`, and API keys take `--id` or `--prefix`. Short flags mean different things on different commands, tables have a fixed set of columns, and extra arguments are silently ignored.

This proposal restructures the command tree and its conventions. Breaking changes are allowed.

It is designed together with the API redesign ([002](002-api.md)). 002 adds a Headscale API at `/api/headscale/v0`, and the CLI described here is its first client: it calls only that API, and `--output json` prints what that API answers. Where the two documents meet, 002 defines the objects and the error codes, and this document defines how the CLI presents them.

The proposal also answers every CLI request in the tracker. The [decision log](#decision-log) maps each issue and closed pull request to what was decided.

## Words used here

The CLI and the API ([002](002-api.md)) use one vocabulary.

| Word             | Meaning                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| server command   | a command that talks to a running headscale, over the socket or a remote address                                            |
| local command    | a command that works on local files and needs no running headscale (one exception: `generate config --running`)             |
| v0               | the Headscale API at `/api/headscale/v0`, defined in 002                                                                    |
| entity           | a stored thing with an ID: a node, a user, an auth key, an API key, an OAuth client. 002 says "resource" for the same thing |
| target           | the entity a command acts on, given as a positional argument                                                                |
| resolver         | the code that turns a target into exactly one entity                                                                        |
| sheet            | the output of `get`: one entity, one `Field: value` line per column                                                         |
| name             | of a node: the name it has in headscale, used by MagicDNS; `nodes set --name` changes it                                    |
| hostname         | the name a node reports about itself; headscale cannot change it                                                            |
| username         | the name of a user; what you write in the policy                                                                            |
| display name     | the free-text name of a user, shown in Tailscale clients                                                                    |
| owner            | who a node or key belongs to: one user, or a set of tags, never both; an API key may have none                              |
| auth key         | a key a node uses to join (today: "pre-auth key")                                                                           |
| API key          | a key a program uses to call the API                                                                                        |
| OAuth client     | an ID and secret that mint short-lived, scoped access tokens                                                                |
| auth request     | a short-lived request from a node, named by its auth ID: a registration or an SSH check                                     |
| problem          | an error answer of v0; it carries a stable `code`                                                                           |
| Tailscale client | the `tailscale` software on a node                                                                                          |

The examples use the same people and nodes everywhere, and 002 uses them too:

| Who or what        | Details                                                                        |
| ------------------ | ------------------------------------------------------------------------------ |
| User 3, `alice`    | local user, no email; owns Node 12 `mynode`, Node 15 `laptop`, Node 16 `phone` |
| User 4, `bob`      | local user, no nodes; owns 2 auth keys and 1 API key                           |
| User 5, `carol`    | OIDC user, email `carol@example.com`; owns 12 nodes                            |
| Node 12, `mynode`  | hostname `ubuntu-vm`, owned by User 3 (alice)                                  |
| Node 13, `builder` | tagged `tag:ci`, `tag:build`                                                   |
| Node 14, `gateway` | tagged `tag:infra`, an exit node                                               |

The examples shorten IDs, key prefixes and IPv6 addresses. A real key prefix has 12 characters. "Now" in the examples is 2026-11-10 09:14 UTC.

## Principles

1. **One way to name a thing.** The target of a command is a positional argument. A resolver turns it into exactly one entity, or fails.

1. **Required is positional, optional is a flag.**

1. **Nothing is silently ignored.** A wrong argument count, an unknown column, an unknown filter key and a flag that does not apply are errors. Three harmless things are accepted on purpose: `--force` on a command that can prompt but does not this time, `--columns +x` for a column that is already shown, and `--columns -x` for a column that is not shown.

1. **A command asks first when something is gone afterwards.** `--force` skips the question, and exists only on commands that can ask.

1. **Two outputs.** A table for people, and `--output json` for scripts. The JSON is the API object.

1. **The CLI covers the API.** Every entity has `list` and `get`, and create, change and delete where that makes sense.

1. **Help is the documentation.** Every command carries a short text, a long text and examples. The reference in the docs is generated from them.

1. **Server commands talk to the headscale server and to nothing else**, and only through v0. The one exception is the [database bypass](#the-database-bypass) of `policy`.

## Command tree

Every leaf is a runnable command. `<x>` is required, `[x]` is optional. The comment lists the flags of the command.

```
headscale

  # ── Local commands: work on local files, need no running server ───

  serve                              # run the control server
  version                            # print version, check for updates

  check                              # offline: no server, no DB, no prompt
    config        [file]             # was `configtest`
    policy        <file>             # was `policy check`; runs the policy's tests
    derp-map      <file>
    extra-records <file>
    all           [config-file]      # every file the config points at

  generate
    private-key
    config                           # --running
    nixos-options
    cli-reference

  completion <shell>

  # ── Server commands: talk to a running headscale ──────────────────

  nodes
    list
    get           <node>
    set           <node>             # --name, --expiry
    expire        <node>
    delete        <node>             # --force
    update-client <node>
    routes
      list  [node]
      set   <node> <routes>          # alias: approve
      clear <node>
    tags
      list  [node]
      set   <node> <tags>            # --force

  users
    list
    get    <user>
    create <name>                    # --display-name, --email, --picture-url
    set    <user>                    # --name, --display-name, --email, --picture-url
    delete <user>                    # --with-nodes, --force

  # node authentication to headscale: registration and the SSH check
  auth
    register <auth-id> <user>
    approve  <auth-id>
    reject   <auth-id>               # --force
    keys                             # was `preauthkeys`
      list                           # --all
      get    <key>
      create <owner>                 # --reusable, --ephemeral, --expiry, --description
      delete <key>                   # --force

  # authentication towards the headscale API
  api
    whoami
    keys                             # was `apikeys`
      list                           # --all
      get    <key>
      create                         # --user, --expiry
      delete <key>                   # --force
    oauth-clients
      list                           # --all
      get    <client>
      create <scopes>                # --tags, --description
      delete <client>                # --force

  policy
    get                              # --bypass-server-and-access-database-directly, --force
    set <file>                       # --dry-run, --bypass-server-and-access-database-directly, --force
    reload

  # ── Debug: a health check and test tools ──────────────────────────

  debug
    health                           # was top-level `health`
    mockoidc                         # was top-level `mockoidc`
    create-node
```

Every server command, `debug health` and `version` also take `--output`. Every `list` also takes `--columns`, `--list-columns`, `--filter` and `--sort`.

### How the tree is built

- **A group that holds many things is a plural noun:** `nodes`, `users`, `keys`, `oauth-clients`, `routes`, `tags`.

- **`policy` is singular.** There is exactly one policy.

- **`auth` and `api` are namespaces.** They say what a credential is for: `auth keys` let nodes in, `api keys` and `api oauth-clients` let programs call the API.

- **`routes` and `tags` sit under `nodes`.** `headscale nodes --help` shows everything you can do to a node. They are views of nodes, not entities.

- **`check`, `generate` and `debug` are tool groups.** They are named after what they do, because they have no entity.

### Aliases

The CLI has many aliases today. Three survive:

| Alias                  | Means              | Where                  |
| ---------------------- | ------------------ | ---------------------- |
| `ls`                   | `list`             | every `list` command   |
| `rm`                   | `delete`           | every `delete` command |
| `nodes routes approve` | `nodes routes set` | routes only            |

There are no group aliases. `node`, `user`, `preauthkey`, `apikey` and the rest are gone.

`nodes routes approve` is a pure alias of `set`. It replaces the whole list and does not add to it, and the help text of the command says so. It is kept because people know the word; it is not the same verb as `auth approve`.

### Commands that go away

- **`nodes backfillips`**. 0.30 removes the command, in its own commit, and the changelog tells operators to run it once before they upgrade. The `/api/v1` endpoint and its server logic (`State.BackfillNodeIPs`, `HSDatabase.BackfillNodeIPs`) stay until 0.31, because the legacy API works in 0.30 as it did in 0.29. A `TODO` marks each of them in the code, so that nothing is left behind when the legacy API goes.

- **`nodes register`**. Already deprecated. Use `auth register`.

- **`nodes rename`, `nodes expire --expiry`, `nodes expire --disable`**. Folded into `nodes set`.

- **`users rename`**. Folded into `users set --name`.

- **`configtest`, `policy check`**. Replaced by `check config` and `check policy`.

- **`dumpConfig`** (hidden). Replaced by `generate config --running`.

## Verbs

A verb means the same thing in every group. The alias `nodes routes approve` is the one exception; it is kept for habit and is not in this table.

| Verb            | Meaning                                             | Exists on                                         |
| --------------- | --------------------------------------------------- | ------------------------------------------------- |
| `list`          | show many, as a table                               | every entity; `routes` and `tags`                 |
| `get`           | show one, as a sheet                                | every entity; `policy get` prints the policy text |
| `create`        | make a new one                                      | users, auth keys, API keys, OAuth clients         |
| `set`           | change an existing one                              | nodes, users, routes, tags, policy                |
| `delete`        | end it: a node or user is removed, a key is revoked | every entity                                      |
| `expire`        | log a node out now                                  | nodes                                             |
| `clear`         | remove every entry of a list                        | routes                                            |
| `update-client` | ask a node to update its Tailscale client           | nodes                                             |
| `register`      | answer a registration: give the new node to a user  | auth                                              |
| `approve`       | answer an SSH check with yes                        | auth                                              |
| `reject`        | answer a registration or an SSH check with no       | auth                                              |
| `reload`        | read the policy again from where it is stored       | policy                                            |
| `whoami`        | show what the CLI is connected as                   | api                                               |

**`set` has one rule.** A positional value replaces the whole thing. A flag changes only that field.

```console
$ headscale nodes routes set mynode 10.0.0.0/8      # the route list is now exactly this
$ headscale nodes tags set builder tag:a,tag:b      # the tag list is now exactly this
$ headscale policy set policy.hujson                # the policy is now exactly this

$ headscale nodes set mynode --name web-1           # only the name changes
$ headscale users set alice --email a@b.c           # only the email changes
```

Where a verb is missing, there is a reason:

- **Nodes have no `create`.** A node is created when it registers.

- **Keys and OAuth clients have no `set`.** They cannot be changed. Make a new one.

- **Keys and OAuth clients have no `revoke`.** `delete` is the revoke: the credential stops working at once, and its record is removed later. See [How a credential ends](#how-a-credential-ends).

- **Tags have no `clear`.** A tagged node needs at least one tag.

- **Policy has no `list` and no `delete`.** There is one policy. Set a new one.

- **`routes` and `tags` have no `get`.** They are views of nodes. `list [node]` narrows the view to one node.

- **Auth requests have no `list` and no `get`.** They cannot be listed in the API either, see [`auth`](#auth). The CLI reads a request only to say in a prompt what is being answered.

## Targets and resolvers

The target comes right after the operation.

```console
$ headscale nodes set <node> --name new-name

$ headscale nodes set 12 --name new-name            # by ID
$ headscale nodes set mynode --name new-name        # by name
$ headscale nodes set 100.64.0.1 --name new-name    # by tailnet IP
```

A resolver returns exactly one entity, or an error. It never guesses.

| Type         | An exact match on this wins | Otherwise searched together               |
| ------------ | --------------------------- | ----------------------------------------- |
| Node         | ID, then tailnet IP         | name, hostname                            |
| User         | ID                          | email, username, OIDC provider identifier |
| Auth key     | ID                          | key prefix                                |
| API key      | ID                          | key prefix                                |
| OAuth client | ID                          |                                           |
| Auth request | full auth ID                |                                           |

How it works:

1. **An exact ID ends the search.** For a node, an exact tailnet IP does too. Both are unique.

1. **All other fields are searched together.** The resolver collects every entity that matches in any of them. An entity that matches in two fields counts once.

1. **One entity:** that is the target.

1. **More than one:** an error that lists the candidates, with the fields that were searched.

1. **None:** a "not found" error.

More rules:

- **A match is exact.** The whole value must be equal. There is no partial match.

- **The resolver works on the client.** It walks the list through v0, 1000 rows a page, and matches there. Up to 1000 rows that is one call. The API takes only IDs in a path, so the matching rules stay out of the API contract ([002, "Finding a target"](002-api.md#finding-a-target)).

- **A key can be typed three ways:** the ID, the prefix, or the masked form that older output shows (`hskey-auth-ab12cd-***`). The API gives the prefix as a plain field; the masked form is accepted as input only.

- **Resolve once, then act by ID.** The entity shown in a prompt is the entity the command changes. The command never looks the name up a second time.

- **Second arguments and flags use resolvers too.** `<user>` in `auth register <auth-id> <user>`, `--user`, the `<owner>` of `auth keys create`, and the value of `--filter owner=`.

- **One target per command.** Bulk work is a shell loop, see [recipes](#recipes).

- **A revoked key can still be named.** It stays in the list until its record is removed.

- **A node named like an ID.** A node whose name is `12` cannot be selected by name when a node with ID 12 exists. Use its ID.

A name is searched in the name and in the hostname, so two nodes can match:

```console
$ headscale nodes delete web
Error: "web" matches 2 nodes. Use the ID to select one:

  ID  NAME   HOSTNAME  OWNER
  21  web    ubuntu    tag:infra
  27  web-1  web       carol@example.com
```

A username is unique only among local users. A user from OIDC can have the name of another user ([#3429] shows two users with the same name):

```console
$ headscale users get debtquity
Error: "debtquity" matches 2 users. Use the ID to select one:

  ID  NAME       EMAIL          PROVIDER
  8   debtquity  -              local
  9   debtquity  d@example.com  oidc
```

Nothing matches:

```console
$ headscale nodes get nope
Error: no node matches "nope".
```

## Flags

### Global flags

| Flag       | Short | On                                                 |
| ---------- | ----- | -------------------------------------------------- |
| `--output` | `-o`  | every server command, `debug health` and `version` |
| `--config` | `-c`  | every command that reads the config                |
| `--help`   | `-h`  | every command                                      |

`serve`, `completion`, `check`, `generate` and the two debug test tools have no `--output`. They print one fixed format.

`--config` names the config file that the CLI itself runs with. It is not the file that `check config [file]` checks; with no argument, `check config` checks the file that `--config` resolves to.

### `--force`

`--force` is **not** global any more. It exists on every command that can prompt, and only there.

- On a command that can prompt, `--force` is always accepted, also when this run would not ask. `nodes tags set` asks only for a user-owned node; a script can pass `--force` every time.

- On a command that never prompts, `--force` is an unknown flag. `headscale nodes list --force` is an error.

The help text of a command therefore tells you whether it can prompt.

### Short flags

A short flag has one meaning in the whole CLI. Today `-i` means five different IDs and `-e` means expiry or email.

| Short | Long            | On                                                 |
| ----- | --------------- | -------------------------------------------------- |
| `-o`  | `--output`      | global                                             |
| `-c`  | `--config`      | global                                             |
| `-h`  | `--help`        | global                                             |
| `-e`  | `--expiry`      | `nodes set`, `auth keys create`, `api keys create` |
| `-d`  | `--description` | `auth keys create`, `api oauth-clients create`     |
| `-u`  | `--user`        | `api keys create`                                  |

Every other flag is long only. A test fails when a letter gets a second meaning. The `debug` test tools are exempt.

### Positional or flag

Required input is positional. Optional input is a flag. Two cases need a word:

- **A read command may take one optional positional** that says what to read: one node in place of all nodes, or one file in place of the default file. These are `nodes routes list [node]`, `nodes tags list [node]`, `check config [file]` and `check all [config-file]`.

- **`set` on nodes and users needs at least one flag.** Each flag is optional, but a `set` with no flag has nothing to do and is an error.

The owner of a key shows the rule at work. `auth keys create <owner>` needs an owner, so it is positional. `api keys create --user` works without one, so it is a flag.

### Lists as input

Every list value is comma separated: routes, tags, scopes, columns.

An empty list value is always an error. It never means "clear".

```console
$ headscale nodes routes set 12 ""
Error: the route list is empty.
To remove all routes: headscale nodes routes clear 12
```

The same error, with its own word, applies to tags, scopes, `--tags` and `--columns`.

### Time values

One parser reads every time value, for `--expiry` and for `--filter`:

| Form      | Example                | Meaning                                  |
| --------- | ---------------------- | ---------------------------------------- |
| Timestamp | `2027-08-27T10:00:00Z` | that moment                              |
| Date      | `2027-08-27`           | midnight UTC                             |
| Duration  | `30m`, `24h`, `90d`    | that long from now                       |
| `now`     |                        | this moment (for `--expiry`: nodes only) |
| `never`   |                        | no expiry (for `--expiry`: nodes only)   |

For `--expiry`, a time in the past is an error. It is almost always a typo. The CLI turns a duration into a time before it calls the server; the API takes times, and the word `now` for the expiry of a node.

A key must expire. The server enforces this, and the CLI supplies the defaults: 1 hour for an auth key, 90 days for an API key.

```console
$ headscale api keys create --expiry never
Error: a key must have an expiry.
```

The spelling is `expiry` everywhere. Today nodes use `--expiry` and keys use `--expiration`.

How a filter compares a time is described under `--filter` in [The table engine](#the-table-engine).

### Argument count

Every command checks its argument count before it sends anything to the server.

```console
$ headscale nodes routes set 12
Error: `nodes routes set` needs 2 arguments, got 1.

  headscale nodes routes set <node> <routes>

To remove all routes: headscale nodes routes clear 12


$ headscale nodes delete 12 13
Error: `nodes delete` needs 1 argument, got 2.


$ headscale nodes routes list 12 13
Error: `nodes routes list` takes at most 1 argument, got 2.
```

## Confirmation prompts

A command asks first when something is gone afterwards and no other command brings it back.

| Command                               | What is gone                                       |
| ------------------------------------- | -------------------------------------------------- |
| every `delete`                        | the record, or the key that stops working for good |
| `auth reject`                         | the auth request; it cannot be answered again      |
| `nodes tags set` on a user-owned node | the user's ownership; it cannot be given back      |

One more command asks, for a different reason:

| Command                                       | Why                              |
| --------------------------------------------- | -------------------------------- |
| `policy get` / `set` with the database bypass | the server must be stopped first |

These do **not** ask, on purpose:

- **`nodes expire`.** The node keeps its record and can log in again.

- **`nodes routes set` and `clear`.** The routes can be set again.

- **`policy set`.** You hold the file. The server refuses an invalid policy and keeps the old one.

- **`nodes set` and `users set`.** Every field can be set back.

`check` commands never prompt. Read commands never prompt, except `policy get` with the database bypass.

A prompt carries what the user needs to decide. The CLI asks the server for it where it does not have it: `users delete` makes a dry run of the delete, and `auth reject` reads the auth request.

```console
$ headscale nodes delete 12
Delete Node 12 (mynode), owned by User 3 (alice)? [y/N]


$ headscale nodes delete builder
Delete Node 13 (builder), tagged tag:ci, tag:build? [y/N]


$ headscale nodes tags set mynode tag:server
Node 12 (mynode) is owned by User 3 (alice).
Tagging removes that ownership and cannot be undone.
Continue? [y/N]


$ headscale auth reject hskey-authreq-AbC...xyz
Reject the registration of "newlaptop"? The node must start again. [y/N]
```

`--force` skips the question:

```console
$ headscale nodes delete 12 --force
Node 12 (mynode) deleted.
```

"Not done" is never exit 0:

```console
$ headscale nodes delete 12
Delete Node 12 (mynode), owned by User 3 (alice)? [y/N] n
Aborted.
$ echo $?
1


$ echo | headscale nodes delete 12
Error: confirmation needed, but there is no terminal.
Run again with --force to delete Node 12 (mynode).
$ echo $?
1
```

## Output

There are two formats: a table for people (the default) and `--output json` for scripts. `yaml` and `json-line` are dropped. An unknown `--output` value is an error.

### The table

- **On a terminal:** colour, and cells cut to the terminal width.

- **In a pipe:** no colour, no truncation, one line per row. Stacked lists are joined with commas. `grep` and `awk` work.

- **`NO_COLOR`** turns colour off on a terminal.

A column that holds a list says how the list is shown:

| Way     | Looks like                                  | Used by                              |
| ------- | ------------------------------------------- | ------------------------------------ |
| inline  | joined with commas on one line; the default | `IP`, `OWNER` tags, `SCOPES`, `TAGS` |
| stacked | one entry per line on a terminal            | the three route columns              |
| cut     | as many as fit, then `… (+K)`               | `NODES`                              |

Times are relative in tables: `now`, `3d ago`, `in 89d`, `never`. A sheet shows both forms. The table shows the word `exit` for the two exit prefixes.

A list with no rows prints `No nodes.` on a terminal, and only the header in a pipe. With `-o json` it prints `[]`.

The table is made for people and may change between releases. Do not parse it.

### JSON is the API object

`--output json` prints what v0 answers. 002 defines every object, and its OpenAPI document is the field reference. The same keys appear in `headscale nodes list -o json` and in `curl`.

```console
$ headscale nodes get mynode -o json
{
  "id": "12",
  "name": "mynode",
  "hostname": "ubuntu-vm",
  "fqdn": "mynode.example.com",
  "owner": {"user": {"id": "3", "name": "alice", "loginName": "alice", "displayName": "Alice", "email": ""}, "tags": []},
  "ipAddresses": ["100.64.0.1", "fd7a::1"],
  "online": true,
  "lastSeen": "2026-11-10T09:14:00Z",
  "expiry": "2027-02-07T10:00:00Z",
  "expired": false,
  "created": "2026-07-13T08:02:00Z",
  "clientVersion": "1.82.0",
  "os": "linux",
  "approvedRoutes": ["10.0.0.0/8"],
  "availableRoutes": ["10.0.0.0/8", "192.168.0.0/24"],
  "servingRoutes": ["10.0.0.0/8"],
  "ephemeral": false,
  "registerMethod": "cli",
  "authKeyId": null,
  "createdBy": {"id": "3", "loginName": "alice"},
  "machineKey": "mkey:ab12…",
  "nodeKey": "nodekey:cd34…",
  "discoKey": "discokey:ef56…",
  "attributes": {"ip:publicAddress": "203.0.113.7"}

```

The CLI does three things to an answer, and no more:

1. **It prints the array of a list without the object around it.** The API answers `{"nodes": [...]}`; the CLI prints `[...]`, so `jq '.[].name'` works. v0 pages every list ([002, "Paging"](002-api.md#paging)); the CLI walks every page and prints one array.

1. **It applies `--filter` and `--sort`.** A filter drops rows and a sort orders them. Neither changes a row. Both work on all rows: the CLI walks every page before it filters, sorts or prints, and it prints nothing when a walk fails. Some lists also drop rows by default, in the table and in JSON alike: the key and OAuth client lists hide what is not `valid` unless `--all` is given, and `nodes routes list` shows only nodes that have routes.

1. **It prints nothing where the API has no body.**

The CLI never renames a key, changes its case or reshapes a value. If the CLI needs another name or another shape, the API changes.

**The CLI prints each object as it came.** For JSON it does not decode the answer into its own types and encode it again, because a field that this build does not know would be lost that way.

**A command prints what the API answers:**

| Command                                                   | `-o json` prints                                    |
| --------------------------------------------------------- | --------------------------------------------------- |
| `list`                                                    | an array of the entity                              |
| `nodes routes list`                                       | an array of nodes: the nodes that have routes       |
| `nodes tags list`                                         | an array of tag rows, from `GET /tags`              |
| `get`                                                     | the entity; the same object as in the list          |
| `create`                                                  | the new entity; for a key, with the secret in `key` |
| `set`, `expire`, `routes set`, `routes clear`, `tags set` | the entity after the change                         |
| `nodes update-client`                                     | the node                                            |
| `auth register`                                           | the new node                                        |
| `users delete`                                            | what was removed: the nodes and the key counts      |
| `policy get`, `policy set`, `policy reload`               | the policy object                                   |
| `api whoami`                                              | the credential in use                               |
| `debug health`                                            | `{"healthy": true, "databaseConnectivity": true}`   |
| every other `delete`, `auth approve`, `auth reject`       | nothing; the exit code says it worked               |

Two outputs have no API object: `version -o json` and `--list-columns -o json`. The CLI defines them, and their keys are Go field names (`BuildTime`). So the case of the keys tells the two kinds apart: camelCase comes from the API, Go field names come from the CLI. `check` has no JSON.

**What a script can rely on.** The JSON matches the binary that printed it. v0 may change in any minor release, and every such change is in the changelog ([002, "What v0 promises"](002-api.md#what-v0-promises)). The CLI makes no promise beyond that.

```console
$ headscale nodes list -o json | jq -r '.[].name'

$ headscale nodes set 12 --name web-1 -o json | jq -r .name
web-1

$ headscale nodes delete 12 --force -o json
$ echo $?
0
```

### Streams and exit codes

| Where  | Carries                                                                         |
| ------ | ------------------------------------------------------------------------------- |
| stdout | the result: a table, a sheet, JSON, a success sentence, the secret of a new key |
| stderr | errors, prompts, notes for the human, the update hint of `version`              |
| exit 0 | done                                                                            |
| exit 1 | not done: an error, a declined prompt, a failed check                           |

A script checks the exit code. It never has to parse text to know if a command worked.

Server commands print no log lines.

With `-o json`, the success sentence and the notes are not printed. The object takes their place.

`--output json` changes the output format and nothing else. Today it also silences logs and skips the update check.

### Errors

Errors are plain text on stderr, with exit code 1, in both output modes. This is what kubectl, gh, aws and docker do.

stdout is therefore either valid result JSON or empty. `jq` never reads an error.

```console
if ! out=$(headscale nodes get nope -o json 2>err); then
  echo "failed: $(cat err)"       # Error: no node matches "nope".
  exit 1
fi

echo "$out" | jq -r .name
```

How the CLI turns a problem from the server into its message is described under [Messages and errors](#messages-and-errors).

### Secrets

A `create` command for an auth key, an API key or an OAuth client prints a secret that is shown only once. The API returns it in the field `key` of the answer to create, and nowhere else.

stdout carries only the secret. The notes for the human go to stderr.

```console
$ headscale auth keys create alice --reusable -e 24h
hskey-auth-ab12cd-XXXXXXXXXXXXXXXX                                  <- stdout
Auth key 7 (ab12cd) for User 3 (alice), reusable, expires in 24h.   <- stderr
This is the only time the key is shown.                             <- stderr


$ headscale api keys create --user alice
hskey-api-vw56xy-XXXXXXXXXXXXXXXX                                   <- stdout
API key 3 (vw56xy) for User 3 (alice), expires in 90d.              <- stderr
This is the only time the key is shown.                             <- stderr


$ headscale api oauth-clients create devices:core --tags tag:ci
hskey-client-c9f2-XXXXXXXXXXXXXXXX                                  <- stdout
OAuth client c9f2: scopes devices:core, tags tag:ci.                <- stderr
This is the only time the secret is shown.                          <- stderr
```

A script captures the secret directly. With `-o json` the object has the field `key`, and the notes are not printed:

```console
$ KEY=$(headscale auth keys create alice)

$ headscale api oauth-clients create devices:core --tags tag:ci -o json | jq -r '.id, .key'
```

### Extraction with `jq`

We do not build jsonpath into the CLI. `--output json` piped to `jq` covers extraction without a dependency or a second expression syntax.

The `jq` examples live in the help text of the commands they belong to, so they also appear in the generated reference.

## The table engine

The CLI has one piece of code that turns a list of API objects into a table. Every `list` command uses it, and so does every sheet. No command has table code of its own.

### One declaration per resource

The rows are the types of the generated v0 client. A resource declares its columns once: a name, the API field behind it, and a few words about how to show it.

```go
var nodeColumns = table.Columns[v0.Node]{
    {Name: "id",        Field: "id",            Default: true, Help: "Node ID"},
    {Name: "name",      Field: "name",          Default: true, Help: "Name in headscale (MagicDNS uses it)"},
    {Name: "owner",     Field: "owner",         Default: true, Help: "Owning user, or the tags"},
    {Name: "ip",        Field: "ipAddresses",   Default: true, Help: "Tailnet IP addresses"},
    {Name: "version",   Field: "clientVersion", Default: true, Kind: table.Version, Help: "Tailscale client version"},
    {Name: "online",    Field: "online",        Default: true, Help: "Whether the node is connected"},
    {Name: "last-seen", Field: "lastSeen",      Default: true, Help: "Time of last contact"},
    {Name: "expiry",    Field: "expiry",        Default: true, Help: "When the node key expires"},
    {Name: "hostname",  Field: "hostname",                     Help: "Hostname the node reports"},
    {Name: "approved-routes", Field: "approvedRoutes", Header: "APPROVED", List: table.Stacked},
    // ...
}

// every list command
return table.Render(cmd, nodes, nodeColumns)
```

- **`Field` is the JSON key of the API object.** The engine finds the field in the generated struct by its JSON tag and reads it. Nobody writes a getter per column.

- **The kind comes from the Go type of the field.** A time is a `time` column, a `[]string` a `list`, a `bool` a `bool`, the owner object an `owner`. `Kind` is given only where the Go type cannot say it: a version is a string in the API.

- **`Header`, `Default`, `List` and `Help` are optional.** The header is the name in upper case unless said otherwise.

- **A new field in the API becomes a column with one line.**

- **A field with no column is in the JSON only.** Examples are `fqdn` and `expired` on a node, and `createdBy` on an auth key.

- **A test fails when a column names a field that the generated type does not have.**

### What the engine does

From that one declaration the engine provides, for every `list` command:

| Feature                 | How                                                                   |
| ----------------------- | --------------------------------------------------------------------- |
| the table               | default columns, relative times, list layouts, colour, terminal width |
| the sheet of `get`      | every column, one line each                                           |
| `--columns`             | pick, add or remove columns                                           |
| `--list-columns`        | print the declaration                                                 |
| `--filter`              | one grammar, matched by kind                                          |
| `--sort`                | ordered by kind                                                       |
| JSON with `-o json`     | the same filter and sort, applied to the objects as they came         |
| shell completion        | the column names                                                      |
| the generated reference | the column table of each command                                      |

An unknown name is always an error:

```console
$ headscale nodes list --columns id,nmae
Error: unknown column "nmae". Did you mean "name"?
Run `headscale nodes list --list-columns`.
```

### Kinds

| Kind      | In the table                         | In the API                                            |
| --------- | ------------------------------------ | ----------------------------------------------------- |
| `id`      | as it is                             | a string                                              |
| `text`    | as it is; `-` when empty             | a string; `""` when unknown                           |
| `number`  | as it is                             | a number                                              |
| `bool`    | `yes` or `no`                        | `true` or `false`                                     |
| `time`    | relative; `never` when there is none | RFC 3339, or `null`                                   |
| `version` | as it is                             | a string                                              |
| `list`    | inline, stacked or cut               | an array; `[]` when empty                             |
| `owner`   | the user, or the tags                | `{"user": {...}, "tags": []}`, or `null` for no owner |

For a user, an `owner` cell shows the `loginName` of the user: the email when the user has one, the username when not. For tags it shows the tags.

A `list` of references, such as `nodes` on a user, shows the names.

### `--columns`

```console
$ headscale nodes list --columns id,name,online    # only these
$ headscale nodes list --columns +os,+hostname     # the defaults, plus two
$ headscale nodes list --columns -ip               # the defaults, minus one
```

A value is either a plain list, or a list of `+` and `-` entries. Mixing the two forms is an error.

```console
$ headscale nodes list --columns id,+os
Error: --columns takes a plain list, or only + and - entries. Not both.
```

Adding a column that is already shown, or removing one that is not, changes nothing and is not an error.

`--columns` works on tables only. Together with `-o json` it is an error, because JSON always has the whole object.

```console
$ headscale nodes list --columns id,name -o json
Error: --columns works on tables only. JSON has the whole object.
To pick fields: ... -o json | jq '.[] | {id, name}'
```

### `--filter`

A filter keeps the rows that match. It applies to the table **and** to JSON.

A filter is a column name, one operator, and a value. The first `=`, `:`, `<` or `>` after the name is the operator. So `owner:tag:ci` is the column `owner`, the operator `:` and the value `tag:ci`.

| Operator | Meaning                                                    | Example                    |
| -------- | ---------------------------------------------------------- | -------------------------- |
| `=`      | exact match                                                | `hostname=ubuntu-vm`       |
| `:`      | contains                                                   | `name:web`                 |
| `<` `>`  | compare; time, number and version columns, and numeric IDs | `last-seen>30d`, `count>0` |

Several filters are joined with commas, and all must match. The flag may also be repeated. A value cannot contain a comma.

How each kind matches:

| Kind      | `=`                               | `:`                               | `<` `>`                                        |
| --------- | --------------------------------- | --------------------------------- | ---------------------------------------------- |
| `id`      | the ID is equal                   | error                             | smaller, larger; only when the IDs are numbers |
| `text`    | the text is equal                 | the text contains the value       | error                                          |
| `number`  | the number is equal               | error                             | smaller, larger                                |
| `bool`    | `true`, `false`, `yes` or `no`    | error                             | error                                          |
| `time`    | only `never`                      | error                             | see below                                      |
| `version` | the version is equal              | error                             | older, newer                                   |
| `list`    | one entry is equal                | one entry contains the value      | error                                          |
| `owner`   | resolved like a target, see below | the shown text contains the value | error                                          |

An "error" cell looks like this:

```console
$ headscale nodes list --filter 'online>true'
Error: column "online" is a bool. It works with = only.

$ headscale nodes list --filter colour=red
Error: unknown column "colour".
Run `headscale nodes list --list-columns`.
```

**Lists.** An entry of `IP`, `SCOPES` or a route column is a text. An entry of `NODES` is a node; it matches by the node's name. `exit` matches the two exit routes.

**Time.** A filter takes a duration or a timestamp.

With a **duration**, the filter compares how far the time is from now. The direction belongs to the column: `last-seen`, `last-used` and `created` look back (an age), `expiry` looks ahead (the time left). `<` means nearer to now, `>` means further away.

| Filter          | Meaning                              |
| --------------- | ------------------------------------ |
| `last-seen>30d` | not seen for more than 30 days       |
| `last-seen<1h`  | seen within the last hour            |
| `created<30d`   | created within the last 30 days      |
| `expiry<7d`     | expires within 7 days, or is expired |
| `expiry>90d`    | more than 90 days left               |

A time on the other side of now counts as a distance of zero. So `expiry<7d` also finds what is already expired.

With a **timestamp**, the filter compares points in time. `<` is earlier, `>` is later: `created<2026-01-01`.

A row with no time never matches `<` or `>`. `expiry=never` finds those rows.

**Owner.** `owner=` names a user the same way a target does: by ID, email, username or provider identifier. A value that starts with `tag:` matches every row that has that tag.

```console
$ headscale nodes list --filter owner=alice
$ headscale nodes list --filter owner=3                   # the same rows

$ headscale nodes list --filter owner=carol@example.com
$ headscale nodes list --filter owner=5                   # the same rows

$ headscale nodes list --filter owner=tag:ci              # has this tag
$ headscale auth keys list --filter owner=tag:ci
```

A name that matches no user is an error, as for a target. A user who exists but owns nothing gives an empty list.

```console
$ headscale nodes list --filter owner=alcie
Error: no user matches "alcie".

$ headscale nodes list --filter owner=bob
No nodes.
```

More examples:

```console
$ headscale nodes list --filter name:web,online=true
$ headscale nodes list --filter 'last-seen>30d'
$ headscale nodes list --filter 'expiry<7d'
$ headscale nodes list --filter expiry=never
$ headscale nodes list --filter 'version<1.80'
$ headscale nodes list --filter ip=100.64.0.1
$ headscale nodes list --filter public-ip=203.0.113.7

$ headscale users list --filter email=carol@example.com -o json
$ headscale users list --filter 'count>0'
```

`--filter` replaces the old filter flags: `nodes list --user`, and `users list --name`, `--email` and `--identifier`. To look up one user, `users get <user>` is shorter. There is no `--filter-mode` and no fuzzy matching.

**Filtering happens on the client.** The grammar works on what the table shows: relative times, the word `exit`, an owner that is a user or tags. The API has a few exact filters of its own (`GET /nodes?user=3`); they are for other clients, and the CLI does not need them.

### `--sort`

```console
$ headscale nodes list --sort last-seen
$ headscale nodes list --sort -last-seen      # reverse
$ headscale nodes list --sort version
$ headscale users list --sort -count
$ headscale auth keys list --sort expiry
```

`--sort` takes one column. It applies to the table and to JSON.

- A `version` column sorts as a version, not as text.

- An `id` column sorts as a number when the IDs are numbers.

- A `bool` column sorts `no` before `yes`.

- A `list` or `owner` column sorts by the text that the table shows.

Without `--sort`, the rows come in the order of the API: nodes, users and keys by ID, OAuth clients by creation time, tags by name.

## Messages and errors

Success and error messages are written for humans.

A message names an entity the same way every time: the kind, the ID, and in brackets the name that tables show for it.

| Entity       | Written as                                     |
| ------------ | ---------------------------------------------- |
| node         | `Node 12 (mynode)`                             |
| user         | `User 3 (alice)`, `User 5 (carol@example.com)` |
| auth key     | `Auth key 7 (ab12cd)`                          |
| API key      | `API key 2 (tr81ys)`                           |
| OAuth client | `OAuth client c9f2`                            |

An owner is written the same way: `owned by User 3 (alice)`, or `tagged tag:ci, tag:build`.

### Success

Every command that changes something prints one sentence:

| Command                    | Message                                                                                       |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| `nodes set --name`         | `Node 12 (web-1) was mynode.`                                                                 |
| `nodes set --name ""`      | `Node 12 (mynode) was web-1. The name is made from its hostname again.`                       |
| `nodes set --expiry`       | `Node 12 (mynode) expires in 290d (2027-08-27 10:00 UTC).`                                    |
| `nodes set --expiry never` | `Node 12 (mynode) does not expire.`                                                           |
| `nodes expire`             | `Node 12 (mynode) is now expired. It must log in again.`                                      |
| `nodes delete`             | `Node 12 (mynode) deleted.`                                                                   |
| `nodes update-client`      | `Client update started on Node 12 (mynode).`                                                  |
| `nodes routes set`         | `Node 12 (mynode) approved routes: 10.0.0.0/8, exit.`                                         |
| `nodes routes clear`       | `Node 12 (mynode) has no approved routes now.`                                                |
| `nodes tags set`           | `Node 13 (builder) tags: tag:ci, tag:build.`                                                  |
| `users create`             | `User 6 (dave) created.`                                                                      |
| `users set`                | `User 3 (alice) updated: email, display name.`                                                |
| `users delete`             | `User 4 (bob) deleted with 2 auth keys and 1 API key.`                                        |
| `auth register`            | `Node 17 (newlaptop) registered to User 3 (alice).`                                           |
| `auth approve`             | `SSH check from Node 12 (mynode) to Node 13 (builder) approved.`                              |
| `auth reject`              | `Registration of "newlaptop" rejected.`                                                       |
| `auth keys delete`         | `Auth key 7 (ab12cd) is revoked. Its record is removed in 7 days.`                            |
| `api keys delete`          | `API key 2 (tr81ys) is revoked. Its record is removed in 7 days.`                             |
| `api oauth-clients delete` | `OAuth client c9f2 is revoked. Its record is removed in 7 days.`                              |
| `policy set`               | `Policy updated.`                                                                             |
| `policy reload`            | `Policy reloaded from /etc/headscale/policy.hujson.`, or `Policy reloaded from the database.` |

The time in a `delete` message comes from `removal` on the revoked record, which the CLI reads after the delete. When the server keeps the record, the second sentence is `Its record is kept.` The read is best effort: the delete has worked when the server answered it, so a read that fails is no error. The CLI then prints the first sentence alone and exits 0. This is what happens when the CLI deletes the API key that it uses itself, because that key stops working at once.

The `create` commands for keys print their notes on stderr, see [Secrets](#secrets).

A count of zero is left out of a prompt and of a message.

### Errors from the server

The server answers an error with a problem ([002, "Errors"](002-api.md#errors)). A problem has a stable `code`, the entity it is about in `object`, and data for that code in `details`.

**An error line starts in lower case after `Error:`**, as the errors of Go and of cobra do. The name of an entity, such as `User 3 (alice)`, keeps its capital.

**The CLI writes its own sentence from `code`, `object` and `details`.** It does not print the `detail` text of the server, and it never matches on text. The same error then reads the same in the CLI whatever the server version words it like.

| Code                   | The CLI says                                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `user_has_nodes`       | `User 3 (alice) still owns 3 nodes: mynode, laptop, phone`, and how to delete them together                                         |
| `name_taken`           | `the name "web-1" belongs to Node 27 (web-1).`, or `... belongs to User 4 (bob).`                                                   |
| `nodes_changed`        | `User 3 (alice) got a new node while you decided: tablet.` and to run the command again                                             |
| `user_managed_by_oidc` | `User 5 (carol@example.com) is managed by OIDC and cannot be edited here.`                                                          |
| `expiry_in_past`       | `2024-01-01 00:00 UTC is in the past.`                                                                                              |
| `expiry_required`      | `a key must have an expiry.`                                                                                                        |
| `tags_required`        | `the tag list is empty. A tagged node needs at least one tag.`                                                                      |
| `tags_not_permitted`   | `these tags are not in the policy: tag:serverr` (tags on a node, and the owner of a new auth key)                                   |
| `owner_conflict`       | `a key is owned by one user or by tags, not both.`                                                                                  |
| `scope_requires_tags`  | `scope auth_keys needs at least one tag (--tags).`                                                                                  |
| `invalid_scope`        | `unknown scope: devices:cor`                                                                                                        |
| `auth_request_kind`    | `this is a registration request. It needs a user:` and the right command                                                            |
| `update_refused`       | one sentence per `reason`, see [`nodes`](#nodes)                                                                                    |
| `policy_invalid`       | `the policy is not valid.`, then every error and every failed test                                                                  |
| `policy_read_only`     | `the policy is read from /etc/headscale/policy.hujson. Edit that file.`                                                             |
| `not_found`            | `Node 12 (mynode) no longer exists.`; for an auth request: `no auth request has this ID.`                                           |
| `unauthorized`         | `The server did not accept the API key.`                                                                                            |
| `forbidden`            | `This credential may not do that.`, and the scope it lacks when the problem names one                                               |
| `too_large`            | `The file is too large for the server.`                                                                                             |
| `unhealthy`            | `The server is not healthy:` and the reasons                                                                                        |
| `invalid_field`        | the field and the reason, for each entry of `errors`                                                                                |
| `invalid_page_token`   | nothing at first: the CLI starts the walk again, once. Then: `the server restarted while the list was read. Run the command again.` |
| `internal`             | `The server had an internal error. Its log has the request hs1/Zx81kq-000042.`                                                      |

For a code that this build does not know, the CLI prints the `title` of the problem and its code.

**The CLI still checks what it can check without a call:** the argument count, an empty list, a time that does not parse, an unknown column. The server is the authority for everything else, so a script that calls the API gets the same refusals as the CLI.

An error says what is wrong and what to do next:

```console
$ headscale nodes set 12 --expiry 2024-01-01
Error: 2024-01-01 00:00 UTC is in the past.
To expire the node now: headscale nodes expire 12


$ headscale users delete alice
Error: User 3 (alice) still owns 3 nodes: mynode, laptop, phone
Delete or tag them first, or delete them together:
  headscale users delete alice --with-nodes
```

When the server cannot be reached, the error names what the CLI tried:

```console
$ headscale users list
Error: cannot connect to /var/run/headscale/headscale.sock
Is headscale running? To use another server:
  --config <file>, HEADSCALE_UNIX_SOCKET, or HEADSCALE_CLI_ADDRESS
```

## Commands by group

### `nodes`

```console
$ headscale nodes list
$ headscale nodes list --columns +os,+hostname --sort -last-seen
$ headscale nodes list --filter owner=alice -o json

$ headscale nodes get mynode
$ headscale nodes get 12 -o json
$ headscale nodes get 100.64.0.1
```

`get` prints a sheet with every column, and the attributes of the node:

```console
$ headscale nodes get mynode
ID:                12
Name:              mynode
Owner:             User 3 (alice)
IP:                100.64.0.1, fd7a::1
Version:           1.82.0
Online:            yes
Last seen:         now (2026-11-10 09:14 UTC)
Expiry:            in 89d (2027-02-07 10:00 UTC)
Hostname:          ubuntu-vm
OS:                linux
Approved routes:   10.0.0.0/8
Available routes:  10.0.0.0/8, 192.168.0.0/24
Serving routes:    10.0.0.0/8
Public IP:         203.0.113.7
Ephemeral:         no
Register method:   cli
Auth key:          -
Machine key:       mkey:ab12...
Node key:          nodekey:cd34...
Disco key:         discokey:ef56...
Created:           120d ago (2026-07-13 08:02 UTC)

Attributes:
  ip:publicAddress   203.0.113.7
```

The sheet has the columns in their order. For a tagged node the owner line reads `Owner: tag:ci, tag:build`.

`Attributes` are the node attributes that the server has, under their Tailscale names. Tailscale's admin console shows them the same way, in the "Attributes" section of a machine. Today headscale sets one, `ip:publicAddress`, and the column `public-ip` reads it. If the server fills more later, they appear here without a change to the CLI.

`set` changes the plain fields of a node:

```console
$ headscale nodes set mynode --name web-1

$ headscale nodes set mynode --expiry 2027-08-27T10:00:00Z
$ headscale nodes set mynode --expiry 2027-08-27     # midnight UTC
$ headscale nodes set mynode --expiry 90d            # 90 days from now
$ headscale nodes set mynode --expiry now            # same as `nodes expire`
$ headscale nodes set mynode --expiry never          # no expiry

$ headscale nodes set mynode --name web-1 --expiry never
```

- A flag you do not pass leaves the field alone.

- `set` with no flag is an error.

- `--name ""` resets the name: the node gets the name that is made from its hostname again. Tailscale does the same.

- **Every `set` is one call.** Both fields change, or neither does. `--expiry now` is sent as the word `now`, so that the server's clock decides.

```console
$ headscale nodes set mynode
Error: nothing to change. Give at least one of
  --name, --expiry

$ headscale nodes set mynode --name web-1
Error: the name "web-1" belongs to Node 27 (web-1).

$ headscale nodes set web-1 --name ""
Node 12 (mynode) was web-1. The name is made from its hostname again.
```

Nodes keep `expire` as its own command. It is the quick daily action: a reversible logout. It does the same as `nodes set --expiry now`.

```console
$ headscale nodes expire mynode
$ headscale nodes delete mynode             # prompts
$ headscale nodes delete 12 --force
```

`expire` lives under `nodes`, not as a top-level verb. A node expiry is a reversible logout; ending a key is not reversible.

What `expire` does to a tagged node is not settled, see [Open points](#open-points).

`update-client` asks a connected node to update its Tailscale client:

```console
$ headscale nodes update-client mynode
Client update started on Node 12 (mynode).
```

A node can refuse, and the server says why. The CLI has one sentence per reason:

| `reason`            | The CLI says                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `notConnected`      | `Node 12 (mynode) is not connected.`                                                       |
| `updatesNotAllowed` | `Node 12 (mynode) does not allow remote updates. Run "tailscale set --auto-update" on it.` |
| `clientRefused`     | `Node 12 (mynode) refused the update:` and the text the Tailscale client sent              |
| `timeout`           | `Node 12 (mynode) did not answer in time.`                                                 |

#### `nodes routes`

`routes` is a view of nodes. It has no `get`.

Approved routes are a **set**. `set` takes the full list and replaces what was there. It does not add.

```console
$ headscale nodes routes list                 # every node that has routes
$ headscale nodes routes list mynode          # one node

$ headscale nodes routes set 12 10.0.0.0/8,192.168.0.0/24
$ headscale nodes routes approve 12 10.0.0.0/8,192.168.0.0/24    # alias of set

$ headscale nodes routes clear 12
```

`list` shows three route columns. `APPROVED` is what the admin allowed. `AVAILABLE` is what the node announces. `SERVING` is what is in use. Seeing "available but not approved" is the main reason to open this view.

`list` shows only nodes that have routes: at least one approved, available or serving route. A node argument narrows the table and the JSON to that node. An unknown node is an error; today it silently shows every node.

`clear` is the only way to remove all routes. An empty list on `set` is an error.

```console
$ headscale nodes routes clear 12
Node 12 (mynode) has no approved routes now.
```

An exit node is the pair `0.0.0.0/0` and `::/0`. The keyword `exit` means both, and it mixes with subnet routes. The server also approves both when it is given one of them. Tailscale does not: there, one of the two alone gives no exit node.

```console
$ headscale nodes routes set 14 exit
$ headscale nodes routes set 14 10.0.0.0/8,exit
$ headscale nodes routes set 14 0.0.0.0/0     # same as exit
```

There is no `exit-node` spelling and no separate exit subcommand. In JSON a route is always its real prefix.

#### `nodes tags`

`tags` is a view of nodes as well. It has no `get`.

Tags are a set. `set` replaces the full list.

```console
$ headscale nodes tags list                   # one row per tag, with its nodes
$ headscale nodes tags list builder           # only the tags that builder has

$ headscale nodes tags set 13 tag:ci,tag:build,tag:test
```

A tagged node needs at least one tag. Headscale has no way to hand a tagged node back to a user:

```console
$ headscale nodes tags set 13 ""
Error: the tag list is empty. A tagged node needs at least one tag.
```

Tagging a user-owned node prompts, because it cannot be undone. Changing the tags of a tagged node does not prompt. A tag that is not in the policy is refused by the server.

`tags list` shows every tag that the policy names and every tag that a node has. It therefore shows tags that no node uses (`COUNT 0`) and tags that sit on a node but are gone from the policy (`IN POLICY no`). The server builds the list.

With a node argument, `tags list` shows only the rows of the tags that the node has. The rows themselves do not change: `COUNT` and `NODES` still cover all nodes.

```console
$ headscale nodes tags list builder -o json
[
  {"tag": "tag:build", "inPolicy": true, "nodeCount": 1, "nodes": [{"id": "13", "name": "builder"}]},
  {"tag": "tag:ci",    "inPolicy": true, "nodeCount": 1, "nodes": [{"id": "13", "name": "builder"}]}
]
```

### `users`

```console
$ headscale users list
$ headscale users list --filter provider=oidc --sort -count

$ headscale users get alice
$ headscale users get carol@example.com -o json

$ headscale users create dave
$ headscale users create dave --display-name "Dave D" --email dave@example.com
```

`set` changes any field of a user, including the username:

```console
$ headscale users set alice --display-name "Alice A" --email a@b.c
$ headscale users set alice --name alice2
$ headscale users set 3 --name alice2 --email a@b.c
$ headscale users set alice --picture-url ""            # clear the field
```

- A flag you do not pass leaves the field alone.

- An empty value clears the field. `--name ""` is an error; a local user needs a name.

- No flag at all is an error.

- The server checks the values: `--picture-url` must be an absolute `http` or `https` URL, and `--email` must be an address. `users create` gets the same checks.

- OIDC users are refused. The identity provider owns those fields, and the next login would overwrite them.

- All given fields change in one call. It is all or nothing.

```console
$ headscale users set alice
Error: nothing to change. Give at least one of
  --name, --display-name, --email, --picture-url


$ headscale users set carol --display-name Carol
Error: User 5 (carol@example.com) is managed by OIDC and cannot be edited here.
```

`delete` removes a user together with what only that user can own: their auth keys and their API keys.

A user who still owns nodes is refused. `--with-nodes` also removes the nodes. It is one operation on the server, so it is all or nothing.

The CLI first asks the server what the delete would remove (a dry run), shows that in the prompt, and then deletes.

```console
$ headscale users delete bob
Delete User 4 (bob), 2 auth keys and 1 API key? [y/N]


$ headscale users delete alice
Error: User 3 (alice) still owns 3 nodes: mynode, laptop, phone
Delete or tag them first, or delete them together:
  headscale users delete alice --with-nodes


$ headscale users delete alice --with-nodes
Delete User 3 (alice), 3 nodes and 2 auth keys?
  mynode, laptop, phone
[y/N] y
User 3 (alice) deleted with 3 nodes and 2 auth keys.


$ headscale users delete alice --with-nodes --force
```

The delete carries the node IDs that the prompt showed. If the user owns other nodes by then, the server refuses, and nothing is deleted:

```console
$ headscale users delete alice --with-nodes
Delete User 3 (alice), 3 nodes and 2 auth keys?
  mynode, laptop, phone
[y/N] y
Error: User 3 (alice) got a new node while you decided: tablet.
Run the command again.
```

### `auth`

`auth` is how nodes authenticate to headscale.

A node that wants something shows an auth ID, in the browser or in the terminal. That is an auth request. There are two kinds, and each has its own answer:

| Kind         | The node wants                      | Answer yes                       | Answer no     |
| ------------ | ----------------------------------- | -------------------------------- | ------------- |
| registration | to join the tailnet                 | `auth register <auth-id> <user>` | `auth reject` |
| SSH check    | a fresh login for an SSH connection | `auth approve <auth-id>`         | `auth reject` |

The CLI reads the auth request before it acts, so its prompt and its message say what is being answered:

```console
$ headscale auth register hskey-authreq-AbC...xyz alice
Node 17 (newlaptop) registered to User 3 (alice).

$ headscale auth approve hskey-authreq-QrS...tuv
SSH check from Node 12 (mynode) to Node 13 (builder) approved.

$ headscale auth reject hskey-authreq-AbC...xyz
Reject the registration of "newlaptop"? The node must start again. [y/N] y
Registration of "newlaptop" rejected.

$ headscale auth reject hskey-authreq-QrS...tuv
Reject the SSH check from Node 12 (mynode) to Node 13 (builder)? [y/N]
```

The wrong verb for the kind is an error. The server refuses it too:

```console
$ headscale auth approve hskey-authreq-AbC...xyz
Error: this is a registration request. It needs a user:
  headscale auth register hskey-authreq-AbC...xyz <user>


$ headscale auth register hskey-authreq-QrS...tuv alice
Error: this is an SSH check request. Use:
  headscale auth approve hskey-authreq-QrS...tuv
```

The target is the full auth ID. There is no prefix match, no `auth list` and no `auth get`. An auth ID is a secret that the node hands to one person: who has the ID may see and answer the request, and nobody can browse them (see [#2804]).

A request that timed out or was already answered is gone:

```console
$ headscale auth approve hskey-authreq-QrS...tuv
Error: no auth request has this ID. It may have timed out, or it was answered already.
```

`auth register` prints the new node with `-o json`. `approve` and `reject` print nothing.

#### `auth keys`

```console
$ headscale auth keys list
$ headscale auth keys list --all
$ headscale auth keys list --filter owner=tag:ci

$ headscale auth keys get ab12cd
```

The owner of a key is a user **or** a list of tags, never both. It is the one positional argument:

```console
$ headscale auth keys create alice
$ headscale auth keys create alice --reusable --expiry 24h
$ headscale auth keys create tag:ci,tag:build --ephemeral -d "CI runners"


$ headscale auth keys create alice,tag:ci
Error: a key is owned by one user or by tags, not both.

$ headscale auth keys create alice,bob
Error: a key is owned by one user. Got 2: alice, bob.
```

A tag is easy to recognise: it always starts with `tag:`.

A tag must be in the policy, as on Tailscale:

```console
$ headscale auth keys create tag:serverr --reusable
Error: these tags are not in the policy: tag:serverr
```

The default expiry is 1 hour. `never` is not allowed, and there is no upper limit.

```console
$ headscale auth keys delete 7
Delete Auth key 7 (ab12cd), owned by User 3 (alice)? [y/N] y
Auth key 7 (ab12cd) is revoked. Its record is removed in 7 days.
```

`delete` ends a key. How that works is the same for every credential, see [How a credential ends](#how-a-credential-ends).

**State and `--all`.** Every key has a state. The server computes it:

| State     | Meaning                                             |
| --------- | --------------------------------------------------- |
| `valid`   | works                                               |
| `used`    | a key that is not reusable and that a node has used |
| `expired` | past its expiry                                     |
| `revoked` | ended with `delete`                                 |

The API list has every key. By default the CLI hides every key that is not `valid`. `--all` removes that default filter and adds the `STATE` column to the default columns. A filter on `state` removes the default filter too. JSON follows the same rule. An explicit `--columns` decides the columns, with or without `--all`.

```console
$ headscale auth keys list --all
ID  PREFIX  OWNER   STATE    REUSABLE  EPHEMERAL  EXPIRY  CREATED
3   zz91aa  alice   revoked  no        no         in 5d   2d ago
5   kk20bb  bob     expired  yes       no         3d ago  33d ago
6   mm77cc  bob     used     no        no         in 2d   5d ago
7   ab12cd  alice   valid    yes       no         in 23h  1h ago
9   ef34gh  tag:ci  valid    no        yes        in 6d   2d ago

$ headscale auth keys list --filter state=expired
```

`get` shows the stored details of a key. It never shows the secret.

```console
$ headscale auth keys get ab12cd
ID:           7
Prefix:       ab12cd
Owner:        User 3 (alice)
State:        valid
Reusable:     yes
Ephemeral:    no
Expiry:       in 23h (2026-11-11 08:14 UTC)
Created:      1h ago (2026-11-10 08:14 UTC)
Description:  -
```

### `api`

`api` is authentication towards the headscale API.

`whoami` shows what the CLI is connected as. It helps when a remote CLI is refused and it is not clear which key is configured.

```console
$ headscale api whoami
Kind:    API key
ID:      2
Prefix:  tr81ys
Owner:   User 4 (bob)
Scopes:  all
Expiry:  in 60d (2027-02-08 09:14 UTC)

$ headscale api whoami          # over the socket
Kind:    local (unix socket)
```

#### `api keys`

```console
$ headscale api keys list
$ headscale api keys list --all
$ headscale api keys get 2

$ headscale api keys create                              # no owner, 90 days
$ headscale api keys create --expiry 30d
$ headscale api keys create --user alice --expiry 90d    # owned by User 3 (alice)

$ headscale api keys delete tr81ys
```

`--user` is new. It gives the key an owner. Every API key may do everything, with or without an owner. The owner decides two things: the key is deleted with its user, and the Tailscale API (`/api/v2`) creates user-owned auth keys for the owner of the API key that calls it.

The default expiry is 90 days. `never` is not allowed, and there is no upper limit.

An API key has three states: `valid`, `expired` and `revoked`. `--all` and the `state` column work as for [auth keys](#auth-keys).

```console
$ headscale api keys delete tr81ys
Delete API key 2 (tr81ys), owned by User 4 (bob)? [y/N] y
API key 2 (tr81ys) is revoked. Its record is removed in 7 days.
```

#### `api oauth-clients`

```console
$ headscale api oauth-clients list
$ headscale api oauth-clients get c9f2

$ headscale api oauth-clients create devices:core:read
$ headscale api oauth-clients create devices:core,auth_keys --tags tag:ci
$ headscale api oauth-clients create devices:core --tags tag:ci -d "CI"

$ headscale api oauth-clients delete c9f2
```

Scopes are required, so they are positional. Tags are optional, so they are a flag. Some scopes need a tag:

```console
$ headscale api oauth-clients create auth_keys
Error: scope auth_keys needs at least one tag (--tags).
```

An OAuth client has no expiry. It works until it is deleted. From then on its tokens are refused. Its states are `valid` and `revoked`, and `--all` shows the revoked ones.

#### How a credential ends

Auth keys, API keys and OAuth clients end the same way, with `delete`. Tailscale's API does the same; its console calls the action "Revoke".

- **The credential stops working at once.** Nodes that joined with an auth key are not touched.

- **The record stays for a while**, with the state `revoked`, so that an admin can see what was stopped. `list --all` shows it, and `get` shows it.

- **The server removes the record later.** A job removes every record that was revoked longer ago than the retention time, 7 days by default. A retention of 0 keeps revoked records for ever.

- **An auth key that a node still refers to is kept** until that node is deleted.

- **`delete` on a revoked credential succeeds** and changes nothing.

- **There is no way to remove a single record at once.** `users delete` is the one exception: it removes the keys of the user together with the user. To get a shorter list, use the default view, which hides everything that is not `valid`.

### `policy`

```console
$ headscale policy get > policy.hujson
$ headscale policy get -o json | jq -r .updated

$ headscale policy set policy.hujson
$ headscale policy set policy.hujson --dry-run

$ headscale policy reload
```

`policy get` prints the policy text exactly as stored, comments included, so `get > file` round-trips. It is the one `get` that does not print a sheet. With `-o json` it prints the policy object of the API: `policy`, `updated`, `mode` and `path`.

`policy set` replaces the whole policy. It does not prompt: you hold the file, and the server refuses an invalid policy and keeps the old one.

```console
$ headscale policy set policy.hujson
Error: the policy is not valid.
  line 14: unknown tag "tag:serverr"
  test 3 failed: alice@ -> 10.0.0.1:22 expected accept, got deny
```

`--dry-run` runs every check that `set` runs against the live users and nodes, then stops before it saves:

```console
$ headscale policy set policy.hujson --dry-run
Policy is valid for this server. Nothing was changed.
```

A file argument of `-` means stdin, for `policy set` and for `check policy`:

```console
$ generate-policy.sh | headscale check policy -
$ generate-policy.sh | headscale policy set -
```

With stdin as the file there is no terminal to answer a prompt. So `policy set -` together with the database bypass needs `--force`.

**When the policy is a file.** With `policy.mode: file`, the server reads the policy from a file and `policy set` is refused. `--dry-run` still works, so a tool can check a policy before it writes the file.

```console
$ headscale policy set policy.hujson
Error: the policy is read from /etc/headscale/policy.hujson. Edit that file.
```

**`policy reload`** asks the server to read the policy again from where it is stored, and prints the result. The server also reloads the file by itself when it is saved; `reload` is for the admin who wants to know at once whether the file was accepted.

```console
$ $EDITOR /etc/headscale/policy.hujson
$ headscale policy reload
Policy reloaded from /etc/headscale/policy.hujson.

$ headscale policy reload
Error: the policy is not valid. The old policy is still in use.
  line 14: unknown tag "tag:serverr"
```

#### The database bypass

`policy get` and `policy set` keep `--bypass-server-and-access-database-directly`. It is the rescue path when a bad policy in the database stops the server from starting.

With this flag the command does not talk to the server. It opens the database itself. So it needs the full server config, not only a socket path. It prompts, because the server must be stopped:

```console
$ headscale policy get --bypass-server-and-access-database-directly > p.hujson
This reads the database directly. Headscale must not be running.
Continue? [y/N]
```

`--dry-run` works with the bypass. It checks the file against the users and nodes in the database and writes nothing. This replaces the old `policy check` with the bypass flag.

```console
$ headscale policy get --bypass-server-and-access-database-directly > p.hujson

$ $EDITOR p.hujson

$ headscale check policy p.hujson

$ headscale policy set p.hujson --dry-run --bypass-server-and-access-database-directly

$ headscale policy set p.hujson --bypass-server-and-access-database-directly
```

### `check`

`check` commands are offline. They need no server and no database. They never prompt and never write a file. The exit code is the result.

This makes them usable in CI and at build time, for example in a Nix derivation ([#2898]).

A check of one file prints one line to stdout when it passes. When it fails, it prints the reason to stderr and exits 1.

```console
$ headscale check config
Configuration /etc/headscale/config.yaml is valid.

$ headscale check config other.yaml
Configuration other.yaml is valid.


$ headscale check policy policy.hujson
Policy is valid (12 tests passed).


$ headscale check policy bad.hujson
Error: test 3 failed: alice@ -> 10.0.0.1:22 expected accept, got deny
$ echo $?
1


$ headscale check derp-map derp.yaml
DERP map derp.yaml is valid.

$ headscale check extra-records records.json
Extra records records.json are valid.
```

`check policy` always runs the `tests` and `sshTests` blocks of the policy, against stand-in users and nodes built from the policy itself. There is no separate `policy test` command (see [#3005]).

`check policy` knows no real users or nodes. To test a policy against the live server without applying it, use `policy set --dry-run`.

`check config` rejects unknown and removed keys ([#1926]).

`check all` checks the config and every file it points at. It prints its whole report to stdout, one line per file, and exits 1 when a file fails:

```console
$ headscale check all
ok    /etc/headscale/config.yaml
ok    /etc/headscale/policy.hujson
FAIL  /etc/headscale/derp.yaml
        region 900: missing node hostname
skip  /var/lib/headscale/noise_private.key (created at startup)
$ echo $?
1
```

The `check` group comes from the open config pull requests, see [Relation to the open config pull requests](#relation-to-the-open-config-pull-requests). This redesign changes two things about it: the file is a positional argument, and `-` reads from stdin.

```console
$ headscale generate private-key

```

`generate private-key`, `generate config` and `generate nixos-options` exist today or come from the open config pull requests. This redesign adds `generate cli-reference`, see [Generated documentation](#generated-documentation).

`generate config --running` is the one local command that asks the server. It takes the place of the hidden `dumpConfig`, which wrote the CLI's own view of the config to a fixed file.

### `version`

`version` prints the version information, as today, and checks GitHub for a newer release. The hint goes to stderr.

```console
$ headscale version
...                                       <- stdout, as today
A newer version is available: v0.30.1     <- stderr
```

`version` is a local command, and the only command besides `serve` that contacts GitHub. `serve` checks once at startup, in the background, and logs one line.

Today every command checks. With blocked outbound traffic each command waits for the timeout ([#3119]).

- The check has a short timeout. When it fails, `version` prints no hint and still exits 0.

- The config key `disable_check_updates` turns the check off, for `serve` and for `version`. `version` reads the config for this when it finds one, and does not warn when it finds none.

- `version -o json` prints the same data as today, with Go field names: `Version`, `Commit`, `BuildTime`, `Go`, `Dirty`. It is an output of the CLI, not an API object.

This check is about new releases. It is not the [version check](#version-check) between the CLI and the server.

### `debug`

```console
$ headscale debug health
healthy
$ echo $?
0

$ headscale debug health -o json
{"healthy": true, "databaseConnectivity": true}
```

`debug health` asks the running server whether it is healthy. It prints `healthy`, or the reasons on stderr with exit 1. Container healthchecks rely on the exit code:

```yaml
healthcheck:
  test: ["CMD", "headscale", "debug", "health"]
```

`debug mockoidc` and `debug create-node` are test tools. They are unstable, keep their current flags, and do not follow the rules of this proposal. `mockoidc` runs a server of its own and reads no headscale config.

### Recipes

These live in the `Example` field of the commands they belong to, so they appear in the help and in the generated reference.

```console
# Names of all nodes
$ headscale nodes list -o json | jq -r '.[].name'

# All nodes of one user
$ headscale nodes list --filter owner=carol -o json | jq -r '.[].name'

# Delete every node not seen for 90 days
$ headscale nodes list --filter 'last-seen>90d' -o json \
    | jq -r '.[].id' \
    | xargs -n1 headscale nodes delete --force

# Nodes with a client older than 1.80
$ headscale nodes list --filter 'version<1.80' --columns name,owner,version

# Auth keys that expire within a week
$ headscale auth keys list --filter 'expiry<7d'
```

## The CLI and the server

### One client

The CLI calls only v0, through the generated client in `gen/client/headscale/v0`. It calls neither the legacy API (`/api/v1`) nor the Tailscale API (`/api/v2`).

A command finds its target with one walk of the list, which is one call for up to 1000 rows, and then makes one more call. Some commands make one call more: `users delete` asks for a dry run first, the `auth` commands read the auth request first, and a `delete` of a key or an OAuth client reads the record again for its time of removal. 002 lists the call behind every command ([Calls per command](002-api.md#calls-per-command)). This document does not repeat that table.

Some operations of v0 have no command of their own:

- `GET /auth-requests/{id}`: the CLI reads it for the prompts and messages of `auth`, and has no `auth get`.
- `GET /version`: the CLI calls it only before a command whose first call would be a write, see below.
- `GET /users/{id}`, `GET /nodes/{id}` and the other single reads: `get` resolves its target from the list, which already holds the whole object. The single reads of keys and OAuth clients are used only after a `delete`.

### Version check

v0 may change between releases, and the CLI can talk to a server on another machine. Without a check, a CLI and a server of different versions do not fail. The generated client drops fields it does not know and fills missing ones with zero, and every node looks offline.

Every v0 answer has the header `Headscale-Version`. The CLI compares it with its own version before it reads the body. A command whose first call would be a write, such as `users create`, `api keys create` or `policy set`, calls `GET /version` first. No write happens when the versions differ, and no new secret is lost, as long as the server is not replaced between the two calls.

- **The major and minor version must be equal.** A different patch version is fine, because a patch release has no breaking change to v0.

- **When they differ, the command stops** with exit 1 and names both versions. It prints no data.

- **A server with no v0** answers `404` without the header. The CLI says that the server is too old.

- **A development build skips the check**, on either side.

- **`debug health` is checked like every other server command.** A container runs the CLI and the server from one image, so they agree.

```console
$ headscale nodes list
Error: this headscale is 0.31.2, the server is 0.30.4.
The CLI and the server must have the same major and minor version.
If you just upgraded, restart the server.


$ headscale nodes list
Error: the server at hs.example.com is too old for this CLI.
It has no /api/headscale/v0.
```

Over the socket the two are usually the same binary. After an upgrade the server is the old version until it restarts, and the message says so.

### Configuration and environment

Environment variables stay for connection and config values:

| Variable                 | Purpose                         |
| ------------------------ | ------------------------------- |
| `HEADSCALE_CONFIG`       | path of the config file         |
| `HEADSCALE_UNIX_SOCKET`  | socket of a local server        |
| `HEADSCALE_CLI_ADDRESS`  | address of a remote server      |
| `HEADSCALE_CLI_API_KEY`  | API key for a remote server     |
| `HEADSCALE_CLI_TIMEOUT`  | how long to wait for the server |
| `HEADSCALE_CLI_INSECURE` | skip TLS verification           |
| `NO_COLOR`               | no colour in tables             |

`HEADSCALE_CONFIG` is the same as `--config`. No other flag has an environment variable. There is no `HEADSCALE_OUTPUT` and no `HEADSCALE_FORCE`. A `--force` that hides in the environment is dangerous.

A server command needs only a socket path or a remote address. A missing config file is normal for it, so it prints no warning and uses the defaults ([#3307]). Only `serve` warns about a missing config. The one exception is the [database bypass](#the-database-bypass), which needs the full server config.

## Generated documentation

**The rule: the command definitions in the code are the only source.**

Help text, the command tree, the reference page in the docs and shell completion are all derived from them. Nobody writes the same fact in two places. No list of commands, flags or columns is kept by hand.

This is the same approach as the config work in [#3680], where the example config, the config reference and the NixOS options are generated from the config schema, and CI fails on a stale copy.

### What every command must carry

Each command declares these once, in its cobra definition:

| Field     | Content                                                                            | Feeds                                        |
| --------- | ---------------------------------------------------------------------------------- | -------------------------------------------- |
| `Use`     | name and argument pattern, for example `set <node>`                                | help, tree, reference, argument-count errors |
| `Short`   | one line that starts with a verb                                                   | the tree, group help, reference headings     |
| `Long`    | the full text: what it does, its rules, whether it prompts, what `-o json` returns | command help, reference                      |
| `Example` | at least one runnable example; one per mode for commands with modes                | command help, reference                      |
| `Aliases` | only `ls`, `rm`, `approve`                                                         | help, reference                              |
| flags     | name, short letter, type, default, description                                     | help, reference, completion                  |
| columns   | for `list` commands: the declaration of [the table engine](#the-table-engine)      | everything the engine provides               |

### What is generated from them

| Output             | Shown by                              | Built from                      |
| ------------------ | ------------------------------------- | ------------------------------- |
| Full command tree  | `headscale` and `headscale --help`    | the tree, `Use`, `Short`        |
| Group help         | `headscale nodes --help`              | the sub-tree, `Short`, examples |
| Command help       | `headscale nodes set --help`          | `Long`, `Use`, `Example`, flags |
| Column list        | `headscale nodes list --list-columns` | column declarations             |
| Shell completion   | `headscale completion <shell>`        | commands, flags, column names   |
| CLI reference page | `headscale generate cli-reference`    | all of the above                |

### Tests that keep it honest

One test walks the whole command tree. It fails when:

- a command has an empty `Short`, `Long` or `Example`

- a short flag letter has two meanings

- a `list` command declares no columns

- a column names a field that the generated type does not have

- an entity group has `list` but no `get` (`routes` and `tags` are views and are exempt)

- a command has `--force` but can never prompt, or can prompt but has no `--force`

- a command accepts any number of arguments

`debug mockoidc` and `debug create-node` are exempt from all of these.

### The reference page

`headscale generate cli-reference` prints one markdown page to stdout. It is committed as `docs/ref/cli.md`.

- **One page.** It is easy to search and needs one entry in the docs navigation.

- **Built by walking the command tree.** The generator reads the same cobra definitions that the help reads, and the same column declarations that the table engine reads.

- **Never edited by hand.** The first line says so.

- **Checked in CI.** The workflow from [#3680] that checks generated files also runs `headscale generate cli-reference | diff -u docs/ref/cli.md -`. A stale page fails the build.

- **Committed on its own.** A generated file never shares a commit with the code that changes it.

The page has the full command tree, then the global flags with the short-flag and alias tables, then one section per command in tree order. A `list` command's section ends with its column table, the same as `--list-columns` prints.

### What stays hand-written

- **Prose pages** that mention commands in running text. The implementation updates them by hand. Today these are `docs/usage/getting-started.md`, `docs/about/faq.md`, `docs/about/clients.md`, `docs/ref/api.md`, `docs/ref/configuration.md`, `docs/ref/oidc.md`, `docs/ref/registration.md`, `docs/ref/routes.md`, `docs/ref/tags.md`, `docs/setup/install/container.md` and `docs/setup/install/main.md`.

- **The changelog.** See [Changelog](#changelog).

- **This proposal.** After the implementation, its command tree is replaced by a link to the generated reference.

### Shell completion

Completion is static: commands, flags, and the column names for `--columns`, `--filter` and `--sort`.

TAB never calls the server. Completing live node and user names can come later without changing any command.

## Changelog

The old commands are not kept in the code. There are no deprecated shims and no stubs that print a hint. Nothing of the old CLI is left to maintain.

The changelog is therefore the one place where a user learns what changed. It must be complete.

### Rules for the entry

- **Every changed command and every changed behaviour is listed.** If it is not in the changelog, the user finds out in production.

- **Every item has a before and an after example.** Real commands, not descriptions. A pure addition is listed without a "before".

- **The long lists are collapsed by default** (`<details>`). The entry is long; the visible part stays short.

- **Visible at the top:** what the change is, what to do before the upgrade, what to do after it.

- **The NixOS test kit gets its own BREAKING entry.** The test kit is a public contract (`nix/README.md`). It is new in 0.30, but other projects already use it from the main branch.

- **"Before" is the last release, 0.29.** Not the main branch. Three things differ: in 0.29 `preauthkeys create --user` took a user ID only, the bypass flag was `--bypass-grpc-and-access-database-directly`, and the JSON had snake_case keys with numbers for IDs.

- **Some things exist only on the main branch** and were never released: `oauth-clients`, `nodes update-client` and the NixOS test kit. Their rows are marked "(unreleased)". The 0.30 entries that already describe them are edited, see [What else the implementation touches](#what-else-the-implementation-touches).

- **The config pull requests and this redesign ship in the same release.** So no released version has the in-between form `check policy -f`.

- **The API has its own changelog section.** 002 defines the entry for v0 and for `/api/v1`, which is frozen and deprecated in 0.30 and removed in 0.31. This entry links to it and does not repeat it.

<details>
<summary>Tables</summary>

The default node columns are `ID`, `NAME`, `OWNER`, `IP`, `VERSION`, `ONLINE`, `LAST SEEN`, `EXPIRY`.

`Hostname`, `MachineKey`, `NodeKey` and `Ephemeral` are no longer shown by default. `User` and `Tags` are merged into `OWNER`. `Expired` is merged into `EXPIRY`. `Connected` is now `ONLINE`.

IP addresses are on one line. Times are relative. In a pipe the table has no colour and one line per row.

```
# before
ID | Hostname | Name | MachineKey | NodeKey | User | Tags | IP addresses | Ephemeral | Last seen | Expiration | Connected | Expired

# after
ID  NAME     OWNER   IP                    VERSION  ONLINE  LAST SEEN  EXPIRY
12  mynode   alice   100.64.0.1, fd7a::1   1.82.0   yes     now        in 89d

# to get a column back
$ headscale nodes list --columns +hostname,+node-key
```

Other tables change too:

| Table     | Before                                                                  | After                                                     |
| --------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| users     | `ID, Name, Username, Email, Created`                                    | `ID, NAME, DISPLAY NAME, EMAIL, PROVIDER, COUNT, NODES`   |
| auth keys | `ID, Key/Prefix, Reusable, Ephemeral, Used, Expiration, Created, Owner` | `ID, PREFIX, OWNER, REUSABLE, EPHEMERAL, EXPIRY, CREATED` |
| API keys  | `ID, Prefix, Expiration, Created`                                       | `ID, PREFIX, OWNER, EXPIRY, CREATED, LAST USED`           |
| routes    | `ID, Hostname, Approved, Available, Serving (Primary)`                  | `ID, NAME, APPROVED, AVAILABLE, SERVING`                  |

In the users table, `NAME` is now the username. Before, `Name` was the display name and `Username` the username.

</details>

<details>
<summary>Errors and exit codes</summary>

Errors are plain text on stderr in every output mode. They are no longer a JSON object.

A declined prompt exits 1. A prompt without a terminal is an error.

```console
# before
$ headscale nodes list -o json            # server down
{"error": "connecting to ..."}

$ echo n | headscale nodes delete -i 12; echo $?
0

# after
$ headscale nodes list -o json            # server down
Error: cannot connect to /var/run/headscale/headscale.sock      (stderr, exit 1)

$ echo n | headscale nodes delete 12; echo $?
Error: confirmation needed, but there is no terminal.
Run again with --force to delete Node 12 (mynode).
1
```

</details>

<details>
<summary>The CLI and the server must match</summary>

The CLI compares its version with the server's. When the major or minor version differs, the command stops.

```console
# after
$ headscale nodes list
Error: this headscale is 0.31.2, the server is 0.30.4.
The CLI and the server must have the same major and minor version.
If you just upgraded, restart the server.
```

</details>

<details>
<summary>More commands ask for confirmation</summary>

New prompts: `auth keys delete`, `api keys delete`, `auth reject`, and `nodes tags set` on a node that a user owns.

```console
# before
$ headscale preauthkeys expire -i 7            # no question

# after
$ headscale auth keys delete 7                 # asks
$ headscale auth keys delete 7 --force         # does not ask
```

</details>

<details>
<summary>Wrong arguments are errors</summary>

Extra arguments were silently ignored. Now every command checks its arguments. An empty list value is an error too.

```console
# before
$ headscale nodes approve-routes -i 2 "0.0.0.0/0"
Node updated                                  # nothing was approved

# after
$ headscale nodes routes set 2
Error: `nodes routes set` needs 2 arguments, got 1.

$ headscale nodes routes set 2 ""
Error: the route list is empty.
```

</details>

<details>
<summary>Keys</summary>

The owner of an auth key is one positional argument: a user, or a list of tags. A key cannot have both.

Lists show only keys that work. `--all` shows used, expired and revoked keys. This is new for API keys too: an expired API key is hidden by default.

**A key ends with `delete`, and `delete` no longer removes the record at once.** The key stops working at once and shows as `revoked`. The server removes the record after the retention time, 7 days by default. This is the same for auth keys, API keys and OAuth clients, and it is what the Tailscale API does. `expire` and `revoke` are gone as separate commands.

An auth key for tags needs tags that the policy names. A key for an unknown tag is refused.

On create, stdout carries only the key. The notes go to stderr.

```console
# before
$ headscale preauthkeys create --user 3 --tags tag:ci        # tagged key, "created by" user 3
$ headscale preauthkeys list                                 # all keys
$ headscale apikeys list                                     # all keys

# after
$ headscale auth keys create tag:ci
$ headscale auth keys list                                   # usable keys
$ headscale auth keys list --all                             # all keys, with STATE
$ headscale api keys list --all

$ headscale auth keys delete 7                               # revoked now, removed in 7 days

# new
$ headscale auth keys create tag:ci -d "CI runners"          # a description
$ headscale api keys create --user alice                     # an API key owned by a user
$ headscale auth keys get ab12cd
```

</details>

<details>
<summary>Nodes</summary>

`rename` and the expiry flags are now `nodes set`. A time in the past is rejected. An empty name resets the name to the one made from the hostname. Name and expiry change together, or not at all.

`nodes routes list` with an unknown node is an error. It used to list every node.

`exit` in a route list means both exit routes.

`nodes update-client` says why a node did not start the update.

```console
# before
$ headscale nodes rename -i 12 web-1
$ headscale nodes expire -i 12 -e 2020-01-01T00:00:00Z       # accepted: node expired

# after
$ headscale nodes set 12 --name web-1
$ headscale nodes set 12 --name ""                           # the name made from the hostname
$ headscale nodes set 12 --expiry 2020-01-01                 # Error: ... is in the past.
$ headscale nodes expire 12

# new
$ headscale nodes get mynode
$ headscale nodes set mynode --expiry 90d
$ headscale nodes routes set gateway 10.0.0.0/8,exit
$ headscale nodes tags list
$ headscale nodes list --columns +public-ip
```

</details>

<details>
<summary>Users</summary>

`users set` changes the username, display name, email and picture of a local user. `users rename` is gone.

`users delete` also removes the user's API keys. `users delete --with-nodes` removes the nodes too; it is refused when the user got a new node after the prompt.

`users create` checks its input: the picture URL must be an absolute `http` or `https` URL, and the email must be an address.

```console
# before
$ headscale users rename --name alice --new-name alice2
$ headscale users create dave --picture-url "javascript:alert(1)"    # accepted

# after
$ headscale users set alice --name alice2
$ headscale users create dave --picture-url "javascript:alert(1)"    # Error

# new
$ headscale users set alice --display-name "Alice A" --email a@b.c
$ headscale users set alice --picture-url ""                 # clear
$ headscale users get alice
$ headscale users delete alice --with-nodes
```

</details>

<details>
<summary>Auth requests</summary>

`auth approve` is for an SSH check. `auth register` is for a registration. The wrong one is now an error. Before, `auth approve` on a registration was accepted and the node had to start again.

The prompt of `auth reject` and the messages of all three say what is being answered.

```console
# after
$ headscale auth approve <registration-auth-id>
Error: this is a registration request. It needs a user:
  headscale auth register <registration-auth-id> <user>
```

</details>

<details>
<summary>OAuth clients (unreleased)</summary>

Scopes are one positional comma list. Tags are `--tags`. `delete` asks for confirmation, and the client stays visible as `revoked` until the retention time removes it.

```console
# before
$ headscale oauth-clients create --scope devices:core --scope auth_keys --tag tag:ci

# after
$ headscale api oauth-clients create devices:core,auth_keys --tags tag:ci
```

</details>

<details>
<summary>Policy and checks</summary>

`check config` and `check policy` need no server and no database, and they write nothing. `check policy` runs the tests in the policy.

To test a policy against the users and nodes of a running server, use `policy set --dry-run`.

`policy reload` asks the server to read the policy again and prints the result.

The bypass flag has a new name: `--bypass-grpc-and-access-database-directly` is now `--bypass-server-and-access-database-directly`. `policy check` with the bypass is now `policy set --dry-run` with the bypass.

```console
# before
$ headscale configtest                          # opened the database, ran migrations
$ headscale policy check -f p.hujson            # needed a running server
$ headscale policy check -f p.hujson --bypass-grpc-and-access-database-directly

# after
$ headscale check config
$ headscale check policy p.hujson
$ headscale check all
$ headscale policy set p.hujson --dry-run
$ headscale policy set p.hujson --dry-run --bypass-server-and-access-database-directly
$ headscale policy reload
```

</details>

<details>
<summary>Health, update check and config warning</summary>

`headscale health` is now `headscale debug health`. It prints `healthy`; before it printed an empty line.

Only `headscale version` and the start of `headscale serve` ask GitHub for a newer release. Other commands no longer do. This removes the long wait on hosts without outbound access.

Server commands no longer print `WRN no config file found, using defaults`.

```console
# before
$ time headscale users list               # no outbound access
real 0m30.1s

# after
$ time headscale users list
real 0m0.1s
```

</details>

**NixOS test kit: BREAKING** (the kit is unreleased; this is for projects that use it from the main branch)

`hs-authkey` takes an owner now, the same as `auth keys create`. The owner is a user name or a list of tags. For a user, the script still creates the user when it is missing. For tags, it creates no user. A tag must be in the policy now, and the kit starts with no policy, so a test sets one with `headscale policy set` before it asks for a key for tags.

## Not in this redesign

Each of these was asked for. Each has a decision.

| Ask                                                     | Decision                                                                                                                    |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `nodes ping` ([#2943])                                  | No. Not a job of the control server.                                                                                        |
| `policy test` with ad-hoc sources ([#3005])             | No. Tests live in the policy; `check policy` runs them.                                                                     |
| `nodes set-ip` ([#3133])                                | Later. Comes with IP pools ([#2912]).                                                                                       |
| `nodes move`, user merge, set OIDC identifier ([#2170]) | No. `nodes move` was removed in [#2922].                                                                                    |
| List auth requests ([#2804])                            | No. An auth ID is a secret for one person. One request can be read by its ID.                                               |
| Server-side list filters for the CLI                    | No. The filter grammar works on what the table shows, so it runs on the client.                                             |
| Hosting avatar images ([#2166])                         | No. The protocol carries a URL.                                                                                             |
| Several targets in one command ([#2687])                | Not now. One target per command; can be added without a break.                                                              |
| TAB completion of live names ([#2687])                  | Later. Does not change any command.                                                                                         |
| Mark stale tags in the node list ([#2981])              | Done in `nodes tags list` (`IN POLICY`), not in `nodes list`.                                                               |
| An "update available" column                            | No. The server does not know the newest Tailscale version ([002, "Not in this proposal"](002-api.md#not-in-this-proposal)). |
| A JSON format that is stable across releases            | No. The JSON is the API object, and v0 may change. A versioned output can come later.                                       |
| A way to remove the record of a key at once             | No. `delete` revokes; the server removes the record after the retention time.                                               |

### Reserved names

These are not built in this redesign. The names are reserved so that the tree does not block them later. They are not in the command tree above.

**Device approval ([#2176]).** The server has no such feature yet. Tailscale's API word is "authorized", and 002 reserves the field `authorized` on a node. The names do not collide with `auth approve` (an SSH check) or `nodes routes approve` (an alias of `routes set`).

```console
$ headscale nodes authorize   <node>
$ headscale nodes deauthorize <node>
$ headscale nodes list --columns +authorized
$ headscale auth keys create alice --preauthorized
```

**Update despite SSH sessions.** The Tailscale client refuses a remote update while it has active SSH sessions, unless the request says otherwise. When the server can send that, the flag is `--ignore-ssh-sessions`, and it becomes a field in the body of the v0 call. It is never `--force`, because it is not a prompt.

```console
$ headscale nodes update-client mynode --ignore-ssh-sessions
```

### Design decisions

The maintainer chose each of these on purpose, some against the first suggestion and some after a review found a gap. Do not change them back without a new decision. Where an earlier draft said something else, the middle column has it.

| Decision                                                                                                             | Rejected, or said before                                          | Why                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| The CLI calls only v0                                                                                                | prefer `/api/v2`, extend `/api/v1`                                | v0 is made for the CLI; one client, one vocabulary                                                         |
| `-o json` is the API object                                                                                          | a JSON that the CLI defines, with Go field names                  | v0 has everything the CLI shows, so the reason for a second format is gone                                 |
| The JSON carries no promise beyond v0's                                                                              | stable keys with a changelog rule                                 | v0 may change in any minor release; a versioned output can come later                                      |
| JSON that the CLI makes itself has Go field names (`version`, `--list-columns`)                                      | camelCase, as the API objects                                     | the case of the keys tells an API object from a CLI output                                                 |
| One table engine over the generated client types, with declared columns                                              | table code per command; columns derived from every field          | each column is deliberate and has a help text; a new field is one line                                     |
| Four columns keep short names (`ip`, `version`, `auth-key`, `count`)                                                 | columns named exactly as their fields                             | they are typed often; `--list-columns` shows the field                                                     |
| `--columns` with `-o json` is an error                                                                               | let `--columns` choose the JSON keys                              | JSON is always the whole object                                                                            |
| The CLI stops when the server has another major or minor version                                                     | warn and continue                                                 | wrong data that looks right is worse than no data                                                          |
| The CLI writes its own error text from the problem `code`                                                            | print the server's text                                           | a program never reads prose; the wording belongs to the CLI                                                |
| Files are positional (`policy set <file>`)                                                                           | `-f/--file`                                                       | required input is positional                                                                               |
| `check` and `generate` are top-level tool groups                                                                     | `policy check`, `config validate`                                 | they need no server; noun groups talk to the server                                                        |
| Plural groups: `auth keys`, `api keys`, `api oauth-clients`                                                          | `auth key`, `api key`, `api oauth2`                               | one rule: a group that holds many things is plural                                                         |
| `health` moves to `debug health`                                                                                     | keep it top-level for container healthchecks                      | it is a diagnostic; the changelog names the healthcheck change                                             |
| Aliases `ls`, `rm` and `routes approve` stay                                                                         | no aliases at all                                                 | habit                                                                                                      |
| `users set --name` replaces `users rename`                                                                           | a `rename` command                                                | a username is a field of the user                                                                          |
| `nodes set --name --expiry` replaces `rename` and the expiry flags                                                   | separate verbs for each                                           | the same pattern as `users set`                                                                            |
| `nodes set --expiry now` stays, as one call                                                                          | remove `now` from `set`; two calls                                | 002 accepts the word `now` in the update, so the server's clock decides                                    |
| `nodes set --name ""` resets the name to the one made from the hostname                                              | refuse an empty name                                              | captured: Tailscale does it; there was no other way to undo a rename                                       |
| One exit prefix approves both, and the API reports both                                                              | exactly what is sent, as Tailscale                                | captured: on Tailscale one prefix gives no exit node; the difference is documented in 002                  |
| An auth key for a tag that the policy does not name is refused                                                       | check only the spelling, as `/api/v1`                             | captured: Tailscale refuses it for every caller                                                            |
| No upper limit on the expiry of a key                                                                                | 90 days for auth keys, as Tailscale                               | a self-hosted admin may want a long-lived key; `/api/v2` keeps the cap                                     |
| A user has `name` as stored, and a read-only `loginName` for display                                                 | fill `name` with the email when it is empty                       | each field has one meaning; `OWNER` and messages show `loginName`                                          |
| `lastSeen` of an online node is the current time                                                                     | the stored time                                                   | captured: Tailscale does it; a filter on old nodes never matches a live one                                |
| `set` has one rule: a positional replaces, a flag changes one field                                                  | `set` meant different things per group                            | one sentence explains every `set`                                                                          |
| An empty list value is always an error                                                                               | `routes set ""` clears                                            | an unset shell variable must not wipe a list; `routes clear` exists                                        |
| `--force` only on commands that can prompt, always accepted there                                                    | a global `--force`                                                | the help says whether a command can prompt                                                                 |
| A declined prompt and a prompt with no terminal exit 1                                                               | exit 0, as today                                                  | "not done" is never success                                                                                |
| Short flags `-e`, `-d`, `-u` stay, one meaning each                                                                  | long flags only                                                   | less typing for the common flags                                                                           |
| No stubs or shims for old commands                                                                                   | hint stubs for one release                                        | nothing of the old CLI to maintain; the changelog has every change                                         |
| `nodes backfillips` is removed, with a changelog note                                                                | run the backfill at server start                                  | the cause no longer occurs                                                                                 |
| The resolver searches name fields together; only ID and IP win                                                       | the first field with a match wins                                 | the resolver never guesses                                                                                 |
| `--filter owner=` is resolved like a target; no match is an error                                                    | match the text of the cell                                        | a user is named the same way everywhere; a typo must not look like "no nodes"                              |
| A duration in a time filter is a distance from now                                                                   | timestamps only                                                   | "not seen for 30 days" stays short to write                                                                |
| `--filter` has `<` and `>` for times, numbers and versions                                                           | text only, with `jq` for the rest                                 | the common questions need no `jq`                                                                          |
| `state` is a normal column; `--all` removes the default `state=valid`                                                | `--all` as a second filter mechanism                              | one filter mechanism                                                                                       |
| A credential ends with `delete`, which is a soft revoke; the record is removed after the retention time              | separate `revoke` and `delete`; `api keys revoke` as "expire now" | captured: Tailscale's delete is a soft revoke; one rule for auth keys, API keys and OAuth clients          |
| The CLI walks every page of a list before it filters, sorts, matches a target or prints                              | print each page as it arrives; a server-side `match` parameter    | `--filter`, `--sort` and the matching of a name need every row, and the matching rules stay out of the API |
| The verb is `delete`, not `revoke`                                                                                   | `revoke`, the word of Tailscale's console                         | every entity has `delete`; `rm` works everywhere; the API method is `DELETE`                               |
| Revoked records are removed by headscale's existing rule: 7 days, never while a node refers to the key, 0 keeps them | a `--purge` to remove a record at once                            | one operation; the rule exists and is tested                                                               |
| `auth keys create <owner>`: a user or tags, positional                                                               | `--user` and `--tags` flags, combined                             | a key has one owner                                                                                        |
| `users delete --with-nodes`, one operation, with a prompt                                                            | refuse and make the admin delete nodes first                      | offboarding in one step, all or nothing                                                                    |

## Open points

**Expire on a tagged node.** Not decided.

- Headscale stores one field for a node: an expiry time, or none. `nodes expire` sets it to now, so a tagged node is logged out at once. It then needs an auth key to join again.

- Tailscale was captured doing something else. A node that joins as tagged has key expiry disabled. `POST /device/{id}/expire` answers 200 and sets the time, but the node keeps running. Only when key expiry is enabled with a second call does the node need a login. The same holds for a user-owned node with key expiry disabled.

- We think Tailscale's behaviour may be wrong, for four reasons: its own API text says the call "will require the device to re-authenticate"; it answers 200 for a call that had no effect; the device then shows `expires` in the past while it is connected; and the expire fires later, when somebody enables key expiry for another reason.

- It may also be intended: "key expiry disabled" could mean "ignore `expires`".

- Until this is decided, `nodes expire` and `nodes set --expiry` do what Headscale does today. 002 has the full capture.

**Open in this document:**

- **Where the table engine lives.** It needs a package that the CLI commands import, and the generated reference too. Pick the package.

- **A development build and the version check.** The check is skipped when either side is a development build. Confirm how a build knows that.

- **The reasons of `debug health`.** The API answers `unhealthy` with `reasons`. What the reasons are is server work.

## Implementation notes

This section is for whoever builds this. It records what the code looks like today, so that nothing has to be found out twice. The decisions are in the [decision log](#design-decisions).

### Relation to 002

The CLI moves to the generated v0 client command by command. That is step 4 of 002's order of work, so the read and write operations of v0 exist first. 002 lists the server work behind them.

The API objects, the error codes and the call behind every command are in 002. Read its sections "Conventions", "Errors", "Resources" and "The CLI and the API" before writing a command.

### Relation to the open config pull requests

A stack of open pull requests already adds `check` and `generate`: [#3668] (`check policy`), [#3669] (`check config`, `check all`, `check derp-map`, `check extra-records`), [#3674] (strict config loading), [#3680] (`generate config`, `generate nixos-options`, the CI check for generated files), [#3682] (NixOS module), [#3685] (config load errors).

They use `-f` for files. They land in their own shape first. **The redesign restructures on top of them.** Do not rework them first, and do not wait for this proposal to change them.

Reuse from that stack: the CI workflow that fails on stale generated files, and the pattern "print to stdout, commit the output, diff in CI".

### Shared building blocks

Every command uses these. No command has its own copy.

- **The table engine.** See [The table engine](#the-table-engine). It takes a slice of a generated client type and a column declaration, and provides the table, the sheet, `--columns`, `--list-columns`, `--filter`, `--sort` and the column part of the reference. It reads fields by their JSON tag through reflection.

- **JSON output.** For `-o json` the CLI keeps each element of the answer as raw JSON next to its decoded form. The filter and the sort work on the decoded form; the output prints the raw form. That is how a field that this build does not know survives.

- **Resolver.** One per entity type. It lists the collection, and returns one entity or a typed error (not found, ambiguous with candidates). Used for targets, for second arguments, for `--user`, for the owner of `auth keys create`, and for `--filter owner=`.

- **Problem mapping.** One function turns a problem into the CLI's sentence, from `code`, `object` and `details`. A code it does not know prints the `title`.

- **Version check.** One round tripper on the v0 client reads `Headscale-Version` before any body is decoded.

- **Output.** One function for results: table, sheet or JSON to stdout. One function for errors: plain text to stderr, exit 1. One function for notes to stderr.

- **Prompt.** One helper. It shows the entity, reads the answer, honours `--force`, and fails without a terminal. A declined prompt is an error, not a silent return.

- **Argument check.** One helper that builds the "needs N arguments, got M" message with the usage line.

- **Time parser.** One parser for every time value. `--expiry` rejects the past; `--filter` accepts past and future.

### What the code does today

These are the places in the CLI that the redesign has to change. Names, not line numbers, so that the list survives edits.

**`cmd/headscale/cli/root.go`**

- `--config`, `--output` and `--force` are persistent flags on the root. `--force` must become per-command.

- The flags and `initConfig` are skipped when `os.Args[1]` is `version`, `mockoidc` or `completion`. Moving `mockoidc` under `debug` breaks that test. Replace it with a per-command setting.

- `initConfig` calls the GitHub update check on every command. Move it to `version` and `serve`. The config key `disable_check_updates` still turns it off there.

**`cmd/headscale/cli/utils.go`**

- "Is the output machine-readable" is decided by scanning the arguments for a bare word `json`, `json-line` or `yaml`. `-o=json` is not detected, and a positional value `json` is. Read the flag instead.

- `confirmAction` returns without an error when the user declines. The command then exits 0.

- Errors are printed as `{"error": ...}` in the chosen format.

- An unknown `-o` value prints an empty line.

- The connection code probes the socket and retries until `cli.timeout` (5 seconds by default). Keep that; improve the final error text.

- There is no version check. A CLI and a server of different versions work together by luck.

**`cmd/headscale/cli/nodes.go`**

- `nodes list --user` is a server-side exact match on the username.

- `list-routes` filters on the client. An ID that does not exist falls through and lists every node.

- The route table's "Hostname" column holds the name of the node.

- `expire` already accepts an RFC 3339 time and `--disable`.

- `update-client` uses the Tailscale API client and its own 15 second timeout. A node that refuses is answered "not found"; the reason is only in the server log.

- `rename` takes its new name as a positional and accepts an empty one.

- Each command builds its own table.

**`cmd/headscale/cli/users.go`**

- The table header "Name" holds the display name and "Username" holds the name.

- `users list` filters on the server by exact match. Client and server disagree on which filter wins when several are given.

- `users create` checks the picture URL with `url.Parse` only. That accepts `javascript:` and relative paths.

- `resolveSingleUser` already builds an ambiguity error with ID, name, email and provider. Reuse the idea.

**`cmd/headscale/cli/preauthkeys.go`, `api_key.go`, `oauth_client.go`**

- `preauthkeys create` accepts `--user` together with `--tags`. The key is then owned by the tags, and the user is stored as "created by". In v0 the server sets `createdBy` itself; the CLI takes one owner.

- The lists show the key masked, as `hskey-auth-<prefix>-***`. v0 has a plain `prefix`.

- `apikeys delete` turns an ID into a prefix by listing all keys on the client. v0 deletes by ID.

- OAuth clients are listed through the Tailscale API and filtered on the client. In v0 they are their own resource.

- No key command prompts today.

**`cmd/headscale/cli/policy.go`**

- `get`, `set` and `check` ignore `-o`. `get` drops the update time.

- The bypass flag opens the database directly and needs a full server config. `check` has the flag today.

**`cmd/headscale/cli/configtest.go`, `health.go`, `version.go`**

- `configtest` builds the whole server. It creates the noise key and runs database migrations.

- `health` prints an empty line in human mode. Only the exit code carries the answer.

- `version` prints several lines. The redesign does not change them; it only adds the update hint on stderr.

**Facts about the server that shape the CLI**

- `User.Username()` returns the email first, then the name, then the provider identifier. `OWNER` follows that order, from the fields of `owner.user`.

- A revoked auth key is deleted by a background job after `preauth_keys.revoked_retention` (168 hours by default; v0 renames it to `credentials.revoked_retention`). The job runs every hour, skips a key that a node still refers to, and is off when the retention is 0. API keys and OAuth clients have no soft revoke today; 002 adds it.

- Tailscale's behaviour was captured for this design on 2026-11-12, with tscap's test tailnet. 002 has the results in "Checked against the Tailscale API".

- In 0.29 the JSON had snake_case keys and numbers for IDs, `preauthkeys create --user` took a user ID only, and the bypass flag was `--bypass-grpc-and-access-database-directly`. The main branch has a camelCase JSON that was never released.
