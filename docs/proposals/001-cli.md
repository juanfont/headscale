# Headscale CLI redesign

**Status:** draft, for discussion. This PR exists so we can shape the design together. It is not meant to be merged as-is.

The current CLI addresses targets inconsistently. Nodes take `--identifier` (ID only). Users take `--identifier` or `--name`. API keys take `--id` or `--prefix`. Short flags mean different things on different commands. Tables have a fixed set of columns. Extra arguments are silently ignored.

This proposal restructures the command tree and its conventions. Breaking changes are allowed.

It also answers every CLI request in the tracker. The [decision log](#decision-log) maps each issue and closed pull request to what we decided.

## Words used here

| Word             | Meaning                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------- |
| server command   | a command that talks to a running headscale, over the socket or a remote address        |
| local command    | a command that works on local files and needs no running headscale                      |
| entity           | a stored thing with an ID: a node, a user, an auth key, an API key, an OAuth client     |
| target           | the object a command acts on, given as a positional argument                            |
| resolver         | the code that turns a target into exactly one object                                    |
| sheet            | the output of `get`: one object, one `Field: value` line per field                      |
| given name       | the name a node has in headscale; MagicDNS uses it; `nodes set --name` changes it       |
| hostname         | the name the node reports about itself; headscale cannot change it                      |
| username         | the name of a user; what you write in the policy                                        |
| display name     | the free-text name of a user, shown in Tailscale clients                                |
| owner            | who a node or auth key belongs to: one user, or a set of tags, never both               |
| admin key        | an API key with no owner; it may do everything                                          |
| auth key         | a key a node uses to join (today: "pre-auth key")                                       |
| API key          | a key a program uses to call the headscale API                                          |
| OAuth client     | an ID and secret that mint short-lived API tokens                                       |
| auth request     | a short-lived request from a node, named by its auth ID; a registration or an SSH check |
| Tailscale client | the `tailscale` software on a node                                                      |

The examples use the same people and nodes everywhere:

| Who or what        | Details                                                                        |
| ------------------ | ------------------------------------------------------------------------------ |
| User 3, `alice`    | local user, no email; owns Node 12 `mynode`, Node 15 `laptop`, Node 16 `phone` |
| User 4, `bob`      | local user, no nodes; owns 2 auth keys and 1 API key                           |
| User 5, `carol`    | OIDC user, email `carol@example.com`; owns 12 nodes                            |
| Node 12, `mynode`  | hostname `ubuntu-vm`, owned by User 3 (alice)                                  |
| Node 13, `builder` | tagged `tag:ci`, `tag:build`                                                   |
| Node 14, `gateway` | tagged `tag:infra`, an exit node                                               |

The examples shorten IDs, key prefixes and IPv6 addresses. A real key prefix has 12 characters.

"Now" in the examples is 2026-11-10 09:14 UTC.

## Principles

1. **One way to name a thing.** The target of a command is a positional argument. A resolver turns it into exactly one object, or fails.

1. **Required is positional, optional is a flag.**

1. **Nothing is silently ignored.** A wrong argument count, an unknown column, an unknown filter key, a flag that does not apply: each is an error. Two harmless things are accepted on purpose: `--force` on a command that can prompt but does not this time, and `--columns +x` for a column that is already shown.

1. **A command asks first when something is gone afterwards.** `--force` skips the question, and exists only on commands that can ask.

1. **Two outputs.** A table for people, and `--output json` for scripts. One declaration per command feeds both.

1. **The CLI covers the API.** Every entity has `list` and `get`, and create, change and delete where that makes sense.

1. **Help is the documentation.** Every command carries a short text, a long text and examples. The reference in the docs is generated from them.

1. **Server commands talk to the headscale server and to nothing else.** The one exception is the [database bypass](#the-database-bypass) of `policy`.

## Command tree

Every leaf is a runnable command. `<x>` is required, `[x]` is optional. The comment lists the flags of the command.

```
headscale

  # ── Local commands: work on local files, need no running server ───

  serve                              # run the control server
  version                            # print version, check for updates

  check                              # offline: no server, no DB, no prompt
    config        [file]             # was `configtest`
    policy        <file>             # was `policy check`; runs the policy's tests
    derp-map      <file>
    extra-records <file>
    all           [config-file]      # every file the config points at

  generate
    private-key
    config                           # --running
    nixos-options
    cli-reference

  completion <shell>

  # ── Server commands: talk to a running headscale ──────────────────

  nodes
    list
    get           <node>
    set           <node>             # --name, --expiry
    expire        <node>
    delete        <node>             # --force
    update-client <node>
    routes
      list  [node]
      set   <node> <routes>          # alias: approve
      clear <node>
    tags
      list  [node]
      set   <node> <tags>            # --force

  users
    list
    get    <user>
    create <name>                    # --display-name, --email, --picture-url
    set    <user>                    # --name, --display-name, --email, --picture-url
    delete <user>                    # --with-nodes, --force

  # node authentication to headscale: registration and the SSH check
  auth
    register <auth-id> <user>
    approve  <auth-id>
    reject   <auth-id>               # --force
    keys                             # was `preauthkeys`
      list                           # --all
      get    <key>
      create <owner>                 # --reusable, --ephemeral, --expiry
      revoke <key>                   # --force
      delete <key>                   # --force

  # authentication towards the headscale API
  api
    keys                             # was `apikeys`
      list                           # --all
      get    <key>
      create                         # --user, --expiry
      revoke <key>                   # --force
      delete <key>                   # --force
    oauth-clients
      list
      get    <client>
      create <scopes>                # --tags, --description
      delete <client>                # --force

  policy
    get                              # --bypass-server-and-access-database-directly, --force
    set <file>                       # --dry-run, --bypass-server-and-access-database-directly, --force

  # ── Debug: a health check and test tools ──────────────────────────

  debug
    health                           # was top-level `health`
    mockoidc                         # was top-level `mockoidc`
    create-node
```

Every server command, `debug health` and `version` also take `--output`. Every `list` also takes `--columns`, `--list-columns`, `--filter` and `--sort`.

### How the tree is built

- **A group that holds many things is a plural noun:** `nodes`, `users`, `keys`, `oauth-clients`, `routes`, `tags`.

- **`policy` is singular.** There is exactly one policy.

- **`auth` and `api` are namespaces.** They say what a credential is for: `auth keys` let nodes in, `api keys` and `api oauth-clients` let programs call the API.

- **`routes` and `tags` sit under `nodes`.** `headscale nodes --help` shows everything you can do to a node. They are views of nodes, not entities.

- **`check`, `generate` and `debug` are tool groups.** They are named after what they do, because they have no entity.

### Aliases

The CLI has many aliases today. Three survive:

| Alias                  | Means              | Where                  |
| ---------------------- | ------------------ | ---------------------- |
| `ls`                   | `list`             | every `list` command   |
| `rm`                   | `delete`           | every `delete` command |
| `nodes routes approve` | `nodes routes set` | routes only            |

There are no group aliases. `node`, `user`, `preauthkey`, `apikey` and the rest are gone.

`nodes routes approve` is a pure alias of `set`. It replaces the whole list, it does not add to it. The help text of the command says so. It is kept because people know the word; it is not the same verb as `auth approve`.

### Commands that go away

- **`nodes backfillips`**, with its server logic (`State.BackfillNodeIPs`, `HSDatabase.BackfillNodeIPs`) and the `/api/v1/node/backfillips` endpoint. Removed in its own commit. The changelog tells operators to run it once before they upgrade.

- **`nodes register`**. Already deprecated. Use `auth register`.

- **`nodes rename`, `nodes expire --expiry`, `nodes expire --disable`**. Folded into `nodes set`.

- **`users rename`**. Folded into `users set --name`.

- **`configtest`, `policy check`**. Replaced by `check config` and `check policy`.

- **`dumpConfig`** (hidden). Replaced by `generate config --running`.

## Verbs

A verb means the same thing in every group. The alias `nodes routes approve` is the one exception; it is kept for habit and is not in this table.

| Verb            | Meaning                                            | Exists on                                         |
| --------------- | -------------------------------------------------- | ------------------------------------------------- |
| `list`          | show many, as a table                              | every entity; `routes` and `tags`                 |
| `get`           | show one, as a sheet                               | every entity; `policy get` prints the policy text |
| `create`        | make a new one                                     | users, auth keys, API keys, OAuth clients         |
| `set`           | change an existing one                             | nodes, users, routes, tags, policy                |
| `delete`        | remove the record                                  | every entity                                      |
| `revoke`        | stop a key from working now                        | auth keys, API keys                               |
| `expire`        | log a node out now                                 | nodes                                             |
| `clear`         | remove every entry of a list                       | routes                                            |
| `update-client` | ask a node to update its Tailscale client          | nodes                                             |
| `register`      | answer a registration: give the new node to a user | auth                                              |
| `approve`       | answer an SSH check with yes                       | auth                                              |
| `reject`        | answer a registration or an SSH check with no      | auth                                              |

**`set` has one rule.** A positional value replaces the whole thing. A flag changes only that field.

```
headscale nodes routes set mynode 10.0.0.0/8      # the route list is now exactly this
headscale nodes tags set builder tag:a,tag:b      # the tag list is now exactly this
headscale policy set policy.hujson                # the policy is now exactly this

headscale nodes set mynode --name web-1           # only the name changes
headscale users set alice --email a@b.c           # only the email changes
```

Where a verb is missing, there is a reason:

- **Nodes have no `create`.** A node is created when it registers.

- **Keys and OAuth clients have no `set`.** They cannot be changed. Make a new one.

- **OAuth clients have no `revoke`.** The server can only delete them.

- **Tags have no `clear`.** A tagged node needs at least one tag.

- **Policy has no `list` and no `delete`.** There is one policy. Set a new one.

- **`routes` and `tags` have no `get`.** They are views of nodes. `list [node]` narrows the view to one node.

- **Auth requests have no `list` and no `get`.** They are not entities. See [`auth`](#auth).

## Targets and resolvers

The target comes right after the operation.

```
headscale nodes set <node> --name new-name

headscale nodes set 12 --name new-name            # by ID
headscale nodes set mynode --name new-name        # by given name
headscale nodes set 100.64.0.1 --name new-name    # by tailnet IP
```

A resolver returns exactly one object, or an error. It never guesses.

| Type         | An exact match on this wins | Otherwise searched together               |
| ------------ | --------------------------- | ----------------------------------------- |
| Node         | ID, then tailnet IP         | given name, hostname                      |
| User         | ID                          | email, username, OIDC provider identifier |
| Auth key     | ID                          | key prefix                                |
| API key      | ID                          | key prefix                                |
| OAuth client | ID                          |                                           |
| Auth request | full auth ID                |                                           |

How it works:

1. **An exact ID ends the search.** For a node, an exact tailnet IP does too. Both are unique.

1. **All other fields are searched together.** The resolver collects every object that matches in any of them. An object that matches in two fields counts once.

1. **One object:** that is the target.

1. **More than one:** an error that lists the candidates, with the fields that were searched.

1. **None:** a "not found" error.

More rules:

- **A match is exact.** The whole value must be equal. There is no partial match.

- **A key can be typed three ways:** the ID, the bare prefix, or the masked key as the API prints it (`hskey-auth-ab12cd-***`).

- **Resolve once, then act by ID.** The object shown in a prompt is the object the command changes. The command never looks the name up a second time.

- **Second arguments and flags use resolvers too.** `<user>` in `auth register <auth-id> <user>`, `--user`, the `<owner>` of `auth keys create`, and the value of `--filter owner=`.

- **One target per command.** Bulk work is a shell loop, see [recipes](#recipes).

- **A node named like an ID.** A node whose given name is `12` cannot be selected by name when a node with ID 12 exists. Use its ID.

A name is searched in the given name and in the hostname, so two nodes can match:

```
$ headscale nodes delete web
Error: "web" matches 2 nodes. Use the ID to select one:

  ID  NAME   HOSTNAME  OWNER
  21  web    ubuntu    tag:infra
  27  web-1  web       carol@example.com
```

Usernames are not unique (issue [#3429] shows two users with the same name):

```
$ headscale users get debtquity
Error: "debtquity" matches 2 users. Use the ID to select one:

  ID  NAME       EMAIL          PROVIDER
  8   debtquity  -              local
  9   debtquity  d@example.com  oidc
```

Nothing matches:

```
$ headscale nodes get nope
Error: no node matches "nope".
```

## Flags

### Global flags

| Flag       | Short | On                                                 |
| ---------- | ----- | -------------------------------------------------- |
| `--output` | `-o`  | every server command, `debug health` and `version` |
| `--config` | `-c`  | every command that reads the config                |
| `--help`   | `-h`  | every command                                      |

`serve`, `completion`, `check`, `generate` and the two debug test tools have no `--output`. They print one fixed format.

`--config` names the config file that the CLI itself runs with. It is not the file that `check config [file]` checks; with no argument, `check config` checks the file that `--config` resolves to.

### `--force`

`--force` is **not** global any more. It exists on every command that can prompt, and only there.

- On a command that can prompt, `--force` is always accepted, also when this run would not ask. `nodes tags set` asks only for a user-owned node; a script can pass `--force` every time.

- On a command that never prompts, `--force` is an unknown flag. `headscale nodes list --force` is an error.

The help text of a command therefore tells you whether it can prompt.

### Short flags

A short flag has one meaning in the whole CLI. Today `-i` means five different IDs and `-e` means expiry or email.

| Short | Long            | On                                                 |
| ----- | --------------- | -------------------------------------------------- |
| `-o`  | `--output`      | global                                             |
| `-c`  | `--config`      | global                                             |
| `-h`  | `--help`        | global                                             |
| `-e`  | `--expiry`      | `nodes set`, `auth keys create`, `api keys create` |
| `-d`  | `--description` | `api oauth-clients create`                         |
| `-u`  | `--user`        | `api keys create`                                  |

Every other flag is long only. A test fails when a letter gets a second meaning. The `debug` test tools are exempt.

### Positional or flag

Required input is positional. Optional input is a flag. Two cases need a word:

- **A read command may take one optional positional** that says what to read: one node in place of all nodes, or one file in place of the default file. These are `nodes routes list [node]`, `nodes tags list [node]`, `check config [file]` and `check all [config-file]`.

- **`set` on nodes and users needs at least one flag.** Each flag is optional, but a `set` with no flag has nothing to do and is an error.

The owner of a key shows the rule at work. `auth keys create <owner>` needs an owner, so it is positional. `api keys create --user` works without one, so it is a flag.

### Lists as input

Every list value is comma separated: routes, tags, scopes, columns.

An empty list value is always an error. It never means "clear".

```
$ headscale nodes routes set 12 ""
Error: the route list is empty.
To remove all routes: headscale nodes routes clear 12
```

The same error, with its own word, applies to tags, scopes, `--tags` and `--columns`.

### Time values

One parser reads every time value, for `--expiry` and for `--filter`:

| Form      | Example                | Meaning                  |
| --------- | ---------------------- | ------------------------ |
| Timestamp | `2027-08-27T10:00:00Z` | that moment              |
| Date      | `2027-08-27`           | midnight UTC             |
| Duration  | `30m`, `24h`, `90d`    | that long from now       |
| `now`     |                        | this moment (nodes only) |
| `never`   |                        | no expiry (nodes only)   |

For `--expiry`, a time in the past is an error. It is almost always a typo. There is no upper limit.

How a filter compares a time is described under [`--filter`](#--filter).

A key must expire:

```
$ headscale api keys create --expiry never
Error: a key must have an expiry.
```

The spelling is `expiry` everywhere. Today nodes use `--expiry` and keys use `--expiration`.

### Argument count

Every command checks its argument count before it sends anything to the server.

```
$ headscale nodes routes set 12
Error: `nodes routes set` needs 2 arguments, got 1.

  headscale nodes routes set <node> <routes>

To remove all routes: headscale nodes routes clear 12


$ headscale nodes delete 12 13
Error: `nodes delete` needs 1 argument, got 2.


$ headscale nodes routes list 12 13
Error: `nodes routes list` takes at most 1 argument, got 2.
```

## Confirmation prompts

A command asks first when something is gone afterwards and no other command brings it back.

| Command                               | What is gone                                  |
| ------------------------------------- | --------------------------------------------- |
| every `delete`                        | the record                                    |
| `auth keys revoke`, `api keys revoke` | the key stops working for good                |
| `auth reject`                         | the auth request; it cannot be answered again |
| `nodes tags set` on a user-owned node | the user's ownership; it cannot be given back |

One more command asks, for a different reason:

| Command                                       | Why                              |
| --------------------------------------------- | -------------------------------- |
| `policy get` / `set` with the database bypass | the server must be stopped first |

These do **not** ask, on purpose:

- **`nodes expire`.** The node keeps its record and can log in again.

- **`nodes routes set` and `clear`.** The routes can be set again.

- **`policy set`.** You hold the file. The server refuses an invalid policy and keeps the old one.

- **`nodes set` and `users set`.** Every field can be set back.

`check` commands never prompt. Read commands never prompt, except `policy get` with the database bypass.

A prompt carries what the user needs to decide:

```
$ headscale nodes delete 12
Delete Node 12 (mynode), owned by User 3 (alice)? [y/N]


$ headscale nodes tags set mynode tag:server
Node 12 (mynode) is owned by User 3 (alice).
Tagging removes that ownership and cannot be undone.
Continue? [y/N]


$ headscale nodes delete builder
Delete Node 13 (builder), tagged tag:ci, tag:build? [y/N]


$ headscale auth reject hskey-authreq-AbC...xyz
Reject auth request hskey-authreq-AbC...xyz? The node must start again. [y/N]
```

`--force` skips the question:

```
$ headscale nodes delete 12 --force
Node 12 (mynode) deleted.
```

"Not done" is never exit 0:

```
$ headscale nodes delete 12
Delete Node 12 (mynode), owned by User 3 (alice)? [y/N] n
Aborted.
$ echo $?
1


$ echo | headscale nodes delete 12
Error: confirmation needed, but there is no terminal.
Run again with --force to delete Node 12 (mynode).
$ echo $?
1
```

## Output

There are two formats: a table for people (the default) and `--output json` for scripts. `yaml` and `json-line` are dropped. An unknown `--output` value is an error.

Neither format is a promise. Both can change between versions.

### The table

- **On a terminal:** colour, and cells cut to the terminal width.

- **In a pipe:** no colour, no truncation, one line per row. Stacked lists are joined with commas. `grep` and `awk` work.

- **`NO_COLOR`** turns colour off on a terminal.

A column that holds a list says how the list is shown. There are three ways:

| Way     | Looks like                                  | Used by                              |
| ------- | ------------------------------------------- | ------------------------------------ |
| inline  | joined with commas on one line; the default | `IP`, `OWNER` tags, `SCOPES`, `TAGS` |
| stacked | one entry per line on a terminal            | the three route columns              |
| cut     | as many as fit, then `… (+K)`               | `NODES`                              |

A node almost always has one IPv4 and one IPv6 address, so `IP` is `100.64.0.1, fd7a::1` on one line.

Times are relative in tables: `now`, `3d ago`, `in 89d`, `never`. A sheet shows both forms.

A list with no rows prints `No nodes.` on a terminal, and only the header in a pipe. With `-o json` it prints `[]`.

### JSON is defined by the CLI

`--output json` is **not** the API object. The CLI defines it.

The reason: no single API object has what the CLI shows. The v1 node has the owner and the routes but no client version. The v2 device has the client version but no user ID and no given name. The CLI joins them. Its JSON hides which calls it made, so the API can change without changing the output.

**JSON is every column of the command**, default and opt-in, with real values:

| Column type | JSON value                                                          |
| ----------- | ------------------------------------------------------------------- |
| id          | a string, as in the API                                             |
| text        | a string; `""` when unknown                                         |
| number      | a number                                                            |
| bool        | `true` or `false`                                                   |
| time        | RFC 3339, or `null` when there is none                              |
| version     | a string; `""` when unknown                                         |
| list        | an array; `[]` when empty, never `null`                             |
| owner       | `{"User": {"ID", "Name", "Email"}, "Tags": []}`, or `null` for none |

In an owner, exactly one side is filled: `User` is an object and `Tags` is `[]`, or `User` is `null` and `Tags` has entries. An admin key has no owner; its `Owner` is `null`.

**The keys are Go field names.** The CLI prints its Go types as they are, the way `tailscale status --json` does. The column `last-seen` has the key `LastSeen`. `--list-columns` prints the key of every column.

```
$ headscale nodes list -o json
[
  {
    "ID": "12",
    "Name": "mynode",
    "Owner": {"User": {"ID": "3", "Name": "alice", "Email": ""}, "Tags": []},
    "IP": ["100.64.0.1", "fd7a::1"],
    "Version": "1.82.0",
    "Online": true,
    "LastSeen": "2026-11-10T09:14:00Z",
    "Expiry": "2027-02-07T10:00:00Z",
    "Hostname": "ubuntu-vm",
    "OS": "linux",
    "ApprovedRoutes": ["10.0.0.0/8"],
    "AvailableRoutes": ["10.0.0.0/8", "192.168.0.0/24"],
    "ServingRoutes": ["10.0.0.0/8"],
    "UpdateAvailable": false,
    "Ephemeral": false,
    "RegisterMethod": "cli",
    "AuthKey": "",
    "MachineKey": "mkey:ab12...",
    "NodeKey": "nodekey:cd34...",
    "DiscoKey": "discokey:ef56...",
    "Created": "2026-07-13T08:02:00Z"
  }
]
```

The keys come in the order of the columns.

**The JSON matches the binary that printed it.**

- The format can change in any release. The help text of `--output` says so.

- The Go types behind it live in the headscale module. A Go program may decode the output with them, but only with the types of the same version as the binary. Headscale is not a Go library.

- JSON is still the output for scripts. It is complete, it has real values, and it is not cut or coloured.

The rules, the same for every command:

- **`list` prints an array of objects.** One object per row. Each entity has one row shape.

- **A view prints the rows of what it shows.** `nodes routes list` prints node objects, the same as `nodes list`; it has all node columns, with other defaults. `nodes tags list` has a row shape of its own.

- **`get` prints one object.** It has every key of a list row. It may add keys that are too expensive for a list. Today there is one: `Attributes` on a node, a map from attribute name to value.

- **`create` prints the new object.** For a key or an OAuth client it adds the key `Key`, the secret.

- **`Attributes` and `Key` are left out everywhere else.** A list row has no such key at all. These two are the only keys that are not columns.

- **A command that changes an entity prints the row after the change.** This covers `set` on nodes and users, `expire`, `revoke`, `nodes routes set`, `nodes routes clear`, `nodes tags set` and `auth register`. It is the list-row shape, with no `Attributes`.

- **A command with no object prints nothing.** The exit code says it worked. This covers every `delete`, `nodes update-client`, `auth approve`, `auth reject` and `policy set`.

- **`policy get -o json`** prints `{"Policy": "...", "UpdatedAt": "..."}`.

- **`version -o json` and `debug health -o json`** follow the same key rule. Their keys become Go field names too.

- **`--list-columns -o json`** prints the column list itself as JSON.

- **A route is its real prefix in JSON.** The table shows `exit`; the JSON has `0.0.0.0/0` and `::/0`.

```
$ headscale nodes list -o json | jq -r '.[].Name'

$ headscale nodes set 12 --name web-1 -o json | jq -r .Name
web-1

$ headscale nodes delete 12 --force -o json
$ echo $?
0
```

### Streams and exit codes

| Where  | Carries                                                                         |
| ------ | ------------------------------------------------------------------------------- |
| stdout | the result: a table, a sheet, JSON, a success sentence, the secret of a new key |
| stderr | errors, prompts, notes for the human, the update hint of `version`              |
| exit 0 | done                                                                            |
| exit 1 | not done: an error, a declined prompt, a failed check                           |

A script checks the exit code. It never has to parse text to know if a command worked.

Server commands print no log lines.

With `-o json`, the success sentence and the notes are not printed. The object takes their place.

`--output json` changes the output format and nothing else. Today it also silences logs and skips the update check.

### Errors

Errors are plain text on stderr, with exit code 1, in both output modes. This is what kubectl, gh, aws and docker do.

stdout is therefore either valid result JSON or empty. `jq` never reads an error.

```
if ! out=$(headscale nodes get nope -o json 2>err); then
  echo "failed: $(cat err)"       # Error: no node matches "nope".
  exit 1
fi

echo "$out" | jq -r .Name
```

### Secrets

A `create` command for an auth key, an API key or an OAuth client prints a secret that is shown only once.

stdout carries only the secret. The notes for the human go to stderr.

```
$ headscale auth keys create alice --reusable -e 24h
hskey-auth-ab12cd-XXXXXXXXXXXXXXXX                    <- stdout
Auth key 7 (ab12cd) for alice, reusable, expires in 24h.    <- stderr
This is the only time the key is shown.               <- stderr


$ headscale api keys create --user alice
hskey-api-vw56xy-XXXXXXXXXXXXXXXX                     <- stdout
API key 3 (vw56xy) for alice, expires in 90d.         <- stderr
This is the only time the key is shown.               <- stderr


$ headscale api oauth-clients create devices:core --tags tag:ci
hskey-client-k9f2-XXXXXXXXXXXXXXXX                    <- stdout
OAuth client k9f2: scopes devices:core, tags tag:ci.  <- stderr
This is the only time the secret is shown.            <- stderr
```

A script captures the secret directly. With `-o json` the object has a `Key` field, and the notes are not printed:

```
KEY=$(headscale auth keys create alice)

headscale api oauth-clients create devices:core --tags tag:ci -o json | jq -r '.ID, .Key'
```

### Extraction with `jq`

We do not build jsonpath into the CLI. `--output json` piped to `jq` covers extraction without a dependency or a second expression syntax.

The `jq` examples live in the help text of the commands they belong to, so they also appear in the generated reference.

## Tables: columns, filter, sort

Four generic flags work on every `list` command: `--columns`, `--list-columns`, `--filter` and `--sort`.

A command declares its columns once: the name, the JSON key, the type, the default, and a description. That one declaration feeds the table, the JSON, the filter, the sort, shell completion and the generated reference. They cannot disagree.

An unknown name is always an error:

```
$ headscale nodes list --columns id,nmae
Error: unknown column "nmae". Did you mean "name"?
Run `headscale nodes list --list-columns`.
```

### `--columns`

```
headscale nodes list --columns id,name,online    # only these
headscale nodes list --columns +os,+hostname     # the defaults, plus two
headscale nodes list --columns -ip               # the defaults, minus one
```

A value is either a plain list, or a list of `+` and `-` entries. Mixing the two forms is an error.

```
$ headscale nodes list --columns id,+os
Error: --columns takes a plain list, or only + and - entries. Not both.
```

Adding a column that is already shown, or removing one that is not, changes nothing and is not an error.

`--columns` works on tables only. Together with `-o json` it is an error, because JSON always has every column.

```
$ headscale nodes list --columns id,name -o json
Error: --columns works on tables only. JSON has all columns.
To pick fields: ... -o json | jq '.[] | {ID, Name}'
```

### `--list-columns`

`--list-columns` prints what exists and exits. The same list feeds shell completion and the generated reference.

### `--filter`

A filter keeps the rows that match. It applies to the table **and** to JSON.

A filter is a column name, one operator, and a value. The first `=`, `:`, `<` or `>` after the name is the operator. So `owner:tag:ci` is the column `owner`, the operator `:` and the value `tag:ci`.

| Operator | Meaning                                   | Example                    |
| -------- | ----------------------------------------- | -------------------------- |
| `=`      | exact match                               | `hostname=ubuntu-vm`       |
| `:`      | contains                                  | `name:web`                 |
| `<` `>`  | compare; time, number and version columns | `last-seen>30d`, `count>0` |

Several filters are joined with commas, and all must match. The flag may also be repeated. A value cannot contain a comma.

How each column type matches:

| Type      | `=`                               | `:`                               | `<` `>`                                        |
| --------- | --------------------------------- | --------------------------------- | ---------------------------------------------- |
| `id`      | the ID is equal                   | error                             | smaller, larger; only when the IDs are numbers |
| `text`    | the text is equal                 | the text contains the value       | error                                          |
| `number`  | the number is equal               | error                             | smaller, larger                                |
| `bool`    | `true`, `false`, `yes` or `no`    | error                             | error                                          |
| `time`    | only `never`                      | error                             | see below                                      |
| `version` | the version is equal              | error                             | older, newer                                   |
| `list`    | one entry is equal                | one entry contains the value      | error                                          |
| `owner`   | resolved like a target, see below | the shown text contains the value | error                                          |

An "error" cell looks like this:

```
$ headscale nodes list --filter 'online>true'
Error: column "online" is a bool. It works with = only.

$ headscale nodes list --filter colour=red
Error: unknown column "colour".
Run `headscale nodes list --list-columns`.
```

**Lists.** An entry of `IP`, `SCOPES` or a route column is a text. An entry of `NODES` is a node; it matches by the node's name. `exit` matches the two exit routes.

**Time.** A filter takes a duration or a timestamp.

With a **duration**, the filter compares how far the time is from now. The direction belongs to the column: `last-seen`, `last-used` and `created` look back (an age), `expiry` looks ahead (the time left). `<` means nearer to now, `>` means further away.

| Filter          | Meaning                              |
| --------------- | ------------------------------------ |
| `last-seen>30d` | not seen for more than 30 days       |
| `last-seen<1h`  | seen within the last hour            |
| `created<30d`   | created within the last 30 days      |
| `expiry<7d`     | expires within 7 days, or is expired |
| `expiry>90d`    | more than 90 days left               |

A time on the other side of now counts as a distance of zero. So `expiry<7d` also finds what is already expired.

With a **timestamp**, the filter compares points in time. `<` is earlier, `>` is later: `created<2026-01-01`.

A row with no time never matches `<` or `>`. `expiry=never` finds those rows.

**Owner.** `owner=` names a user the same way a target does: by ID, email, username or provider identifier. A value that starts with `tag:` matches every row that has that tag.

```
headscale nodes list --filter owner=alice
headscale nodes list --filter owner=3                   # the same rows

headscale nodes list --filter owner=carol@example.com
headscale nodes list --filter owner=5                   # the same rows

headscale nodes list --filter owner=tag:ci              # has this tag
headscale auth keys list --filter owner=tag:ci
```

A name that matches no user is an error, as for a target. A user who exists but owns nothing gives an empty list.

```
$ headscale nodes list --filter owner=alcie
Error: no user matches "alcie".

$ headscale nodes list --filter owner=bob
No nodes.
```

More examples:

```
headscale nodes list --filter name:web,online=true
headscale nodes list --filter 'last-seen>30d'
headscale nodes list --filter 'expiry<7d'
headscale nodes list --filter expiry=never
headscale nodes list --filter 'version<1.80'
headscale nodes list --filter ip=100.64.0.1

headscale users list --filter email=carol@example.com -o json
headscale users list --filter 'count>0'
```

`--filter` replaces the old filter flags: `nodes list --user`, and `users list --name`, `--email` and `--identifier`. To look up one user, `users get <user>` is shorter. There is no `--filter-mode` and no fuzzy matching.

Filtering happens on the client. The Tailscale v2 API has no list filters, and we do not add any.

### `--sort`

```
headscale nodes list --sort last-seen
headscale nodes list --sort -last-seen      # reverse
headscale nodes list --sort version
headscale users list --sort -count
headscale auth keys list --sort expiry
```

`--sort` takes one column. It applies to the table and to JSON.

- A `version` column sorts as a version, not as text.

- An `id` column sorts as a number when the IDs are numbers.

- A `bool` column sorts `no` before `yes`.

- A `list` or `owner` column sorts by the text that the table shows.

The default order is by ID. `nodes tags list` has no ID and sorts by tag.

## Messages and errors

Success and error messages are written for humans.

A message names an object the same way every time: the kind, the ID, and in brackets the name that tables show for it.

| Object       | Written as                                     |
| ------------ | ---------------------------------------------- |
| node         | `Node 12 (mynode)`                             |
| user         | `User 3 (alice)`, `User 5 (carol@example.com)` |
| auth key     | `Auth key 7 (ab12cd)`                          |
| API key      | `API key 2 (tr81ys)`                           |
| OAuth client | `OAuth client k9f2`                            |
| auth request | `auth request hskey-authreq-AbC...xyz`         |

An owner is written the same way: `owned by User 3 (alice)`, or `tagged tag:ci, tag:build`.

A success message says what changed. Every command that changes something prints one:

| Command                    | Message                                                    |
| -------------------------- | ---------------------------------------------------------- |
| `nodes set --name`         | `Node 12 (web-1) was mynode.`                              |
| `nodes set --expiry`       | `Node 12 (mynode) expires in 290d (2027-08-27 10:00 UTC).` |
| `nodes set --expiry never` | `Node 12 (mynode) does not expire.`                        |
| `nodes expire`             | `Node 12 (mynode) is now expired. It must log in again.`   |
| `nodes delete`             | `Node 12 (mynode) deleted.`                                |
| `nodes update-client`      | `Client update started on Node 12 (mynode).`               |
| `nodes routes set`         | `Node 12 (mynode) approved routes: 10.0.0.0/8, exit.`      |
| `nodes routes clear`       | `Node 12 (mynode) has no approved routes now.`             |
| `nodes tags set`           | `Node 13 (builder) tags: tag:ci, tag:build.`               |
| `users create`             | `User 6 (dave) created.`                                   |
| `users set`                | `User 3 (alice) updated: email, display name.`             |
| `users delete`             | `User 4 (bob) deleted with 2 auth keys and 1 API key.`     |
| `auth register`            | `Node 17 (newlaptop) registered to User 3 (alice).`        |
| `auth approve`             | `Auth request hskey-authreq-QrS...tuv approved.`           |
| `auth reject`              | `Auth request hskey-authreq-QrS...tuv rejected.`           |
| `auth keys revoke`         | `Auth key 7 (ab12cd) is revoked.`                          |
| `auth keys delete`         | `Auth key 7 (ab12cd) deleted.`                             |
| `api keys revoke`          | `API key 2 (tr81ys) is expired now.`                       |
| `api keys delete`          | `API key 2 (tr81ys) deleted.`                              |
| `api oauth-clients delete` | `OAuth client k9f2 deleted.`                               |
| `policy set`               | `Policy updated.`                                          |

The `create` commands for keys print their notes on stderr, see [Secrets](#secrets).

A count of zero is left out of a prompt and of a message.

An error says what is wrong and what to do next:

```
$ headscale nodes set 12 --expiry 2024-01-01
Error: 2024-01-01 00:00 UTC is in the past.
To expire the node now: headscale nodes expire 12
```

A database error never reaches the user as-is. For example, deleting a user that still owns nodes:

```
$ headscale users delete alice
Error: User 3 (alice) still owns 3 nodes: mynode, laptop, phone
Delete or tag them first, or delete them together:
  headscale users delete alice --with-nodes
```

When the server cannot be reached, the error names what the CLI tried:

```
$ headscale users list
Error: cannot connect to /var/run/headscale/headscale.sock
Is headscale running? To use another server:
  --config <file>, HEADSCALE_UNIX_SOCKET, or HEADSCALE_CLI_ADDRESS
```

## Commands by group

### `nodes`

```
headscale nodes list
headscale nodes list --columns +os,+hostname --sort -last-seen
headscale nodes list --filter owner=alice -o json

headscale nodes get mynode
headscale nodes get 12 -o json
headscale nodes get 100.64.0.1
```

`get` prints a sheet with every column, and the posture attributes of the node:

```
$ headscale nodes get mynode
ID:                12
Name:              mynode
Owner:             User 3 (alice)
IP:                100.64.0.1, fd7a::1
Version:           1.82.0
Online:            yes
Last seen:         now (2026-11-10 09:14 UTC)
Expiry:            in 89d (2027-02-07 10:00 UTC)
Hostname:          ubuntu-vm
OS:                linux
Approved routes:   10.0.0.0/8
Available routes:  10.0.0.0/8, 192.168.0.0/24
Serving routes:    10.0.0.0/8
Update available:  no
Ephemeral:         no
Register method:   cli
Auth key:          -
Machine key:       mkey:ab12...
Node key:          nodekey:cd34...
Disco key:         discokey:ef56...
Created:           120d ago (2026-07-13 08:02 UTC)

Attributes:
  ip:publicAddress   203.0.113.7
```

The sheet has the columns in their order. For a tagged node the owner line reads `Owner: tag:ci, tag:build`.

`Attributes` are the posture attributes that the server has for the node, under their Tailscale names. Tailscale's admin console shows them the same way, in the "Attributes" section of a machine. Today headscale sets one, `ip:publicAddress`.

Reading them costs one call per node. So they are in `get` only: on the sheet, and as the `Attributes` key of `nodes get -o json`. A list row does not have them.

```
$ headscale nodes get mynode -o json | jq .Attributes
{"ip:publicAddress": "203.0.113.7"}
```

`set` changes the plain fields of a node:

```
headscale nodes set mynode --name web-1

headscale nodes set mynode --expiry 2027-08-27T10:00:00Z
headscale nodes set mynode --expiry 2027-08-27     # midnight UTC
headscale nodes set mynode --expiry 90d            # 90 days from now
headscale nodes set mynode --expiry now            # same as `nodes expire`
headscale nodes set mynode --expiry never          # no expiry

headscale nodes set mynode --name web-1 --expiry never
```

- A flag you do not pass leaves the field alone.

- `set` with no flag is an error.

- `--name ""` is an error. A node needs a name.

- With both flags, the name is changed first, then the expiry. These are two calls. If the second fails, the error says that the name was already changed.

```
$ headscale nodes set mynode
Error: nothing to change. Give at least one of
  --name, --expiry

$ headscale nodes set mynode --name ""
Error: a node needs a name.
```

Nodes keep `expire` as its own command. It is the quick daily action: a reversible logout. It does the same as `nodes set --expiry now`.

```
headscale nodes expire mynode
headscale nodes delete mynode             # prompts
headscale nodes delete 12 --force
```

`expire` lives under `nodes`, not as a top-level verb. Expiry means different things in different places: a node expiry is a reversible logout, a key revoke is not reversible.

`update-client` asks a connected node to update its Tailscale client:

```
$ headscale nodes update-client mynode
Client update started on Node 12 (mynode).
```

A node can refuse. The server learns only that it refused, so the CLI lists the possible reasons:

```
$ headscale nodes update-client mynode
Error: Node 12 (mynode) did not start the update.
It may be offline, not allow remote updates, or have active SSH sessions.
The server log has the reason.
```

#### `nodes routes`

`routes` is a view of nodes. It has no `get`.

Approved routes are a **set**. `set` takes the full list and replaces what was there. It does not add.

```
headscale nodes routes list                 # every node that has routes
headscale nodes routes list mynode          # one node

headscale nodes routes set 12 10.0.0.0/8,192.168.0.0/24
headscale nodes routes approve 12 10.0.0.0/8,192.168.0.0/24    # alias of set

headscale nodes routes clear 12
```

`list` shows three route columns. `APPROVED` is what the admin allowed. `AVAILABLE` is what the node announces. `SERVING` is what is in use. Seeing "available but not approved" is the main reason to open this view.

`list` shows only nodes that have routes: at least one approved, available or serving route. A node argument narrows the table and the JSON to that node. An unknown node is an error; today it silently shows every node.

`clear` is the only way to remove all routes. An empty list on `set` is an error.

```
$ headscale nodes routes clear 12
Node 12 (mynode) has no approved routes now.
```

An exit node is the pair `0.0.0.0/0` and `::/0`. The keyword `exit` means both, and it mixes with subnet routes:

```
headscale nodes routes set 14 exit
headscale nodes routes set 14 10.0.0.0/8,exit
headscale nodes routes set 14 0.0.0.0/0     # same as exit
```

There is no `exit-node` spelling and no separate exit subcommand.

#### `nodes tags`

`tags` is a view of nodes as well. It has no `get`.

Tags are a set. `set` replaces the full list.

```
headscale nodes tags list                   # one row per tag, with its nodes
headscale nodes tags list builder           # only the tags that builder has

headscale nodes tags set 13 tag:ci,tag:build,tag:test
```

A tagged node needs at least one tag. Headscale has no way to hand a tagged node back to a user:

```
$ headscale nodes tags set 13 ""
Error: the tag list is empty. A tagged node needs at least one tag.
```

Tagging a user-owned node prompts, because it cannot be undone. Changing the tags of a tagged node does not prompt.

`tags list` joins two sources on the client: the node list and the `tagOwners` of the policy. It therefore shows tags that no node uses (`COUNT 0`) and tags that sit on a node but are gone from the policy (`IN POLICY no`).

With a node argument, `tags list` shows only the rows of the tags that the node has. The rows themselves do not change: `COUNT` and `NODES` still cover all nodes.

```
$ headscale nodes tags list builder -o json
[
  {"Tag": "tag:build", "Count": 1, "InPolicy": true, "Nodes": [{"ID": "13", "Name": "builder"}]},
  {"Tag": "tag:ci",    "Count": 1, "InPolicy": true, "Nodes": [{"ID": "13", "Name": "builder"}]}
]
```

### `users`

```
headscale users list
headscale users list --filter provider=oidc --sort -count

headscale users get alice
headscale users get carol@example.com -o json

headscale users create dave
headscale users create dave --display-name "Dave D" --email dave@example.com
```

`set` changes any field of a user, including the username:

```
headscale users set alice --display-name "Alice A" --email a@b.c
headscale users set alice --name alice2
headscale users set 3 --name alice2 --email a@b.c
headscale users set alice --picture-url ""            # clear the field
```

The rules come from the closed pull request [#3427]:

- A flag you do not pass leaves the field alone.

- An empty value clears the field. `--name ""` is an error; a user needs a name.

- No flag at all is an error.

- `--picture-url` must be an absolute `http` or `https` URL. `--email` must parse as an address. `users create` uses the same checks.

- OIDC users are refused. The next login would overwrite the fields anyway.

- All given fields change in one call. It is all or nothing.

```
$ headscale users set alice
Error: nothing to change. Give at least one of
  --name, --display-name, --email, --picture-url


$ headscale users set carol --display-name Carol
Error: User 5 (carol@example.com) is managed by OIDC and cannot be edited here.
```

`delete` removes a user together with what only that user can own: their auth keys and their API keys.

A user who still owns nodes is refused, before any prompt. `--with-nodes` also removes the nodes. Everything happens in one server call, so it is all or nothing.

```
$ headscale users delete bob
Delete User 4 (bob), 2 auth keys and 1 API key? [y/N]


$ headscale users delete alice
Error: User 3 (alice) still owns 3 nodes: mynode, laptop, phone
Delete or tag them first, or delete them together:
  headscale users delete alice --with-nodes


$ headscale users delete alice --with-nodes
Delete User 3 (alice), 3 nodes and 2 auth keys?
  mynode, laptop, phone
[y/N] y
User 3 (alice) deleted with 3 nodes and 2 auth keys.


$ headscale users delete alice --with-nodes --force
```

### `auth`

`auth` is how nodes authenticate to headscale.

A node that wants something shows an auth ID, in the browser or in the terminal. That is an auth request. There are two kinds, and each has its own answer:

| Kind         | The node wants                      | Answer yes                       | Answer no     |
| ------------ | ----------------------------------- | -------------------------------- | ------------- |
| registration | to join the tailnet                 | `auth register <auth-id> <user>` | `auth reject` |
| SSH check    | a fresh login for an SSH connection | `auth approve <auth-id>`         | `auth reject` |

```
$ headscale auth register hskey-authreq-AbC...xyz alice
Node 17 (newlaptop) registered to User 3 (alice).

$ headscale auth approve hskey-authreq-QrS...tuv
Auth request hskey-authreq-QrS...tuv approved.

$ headscale auth reject hskey-authreq-QrS...tuv
Reject auth request hskey-authreq-QrS...tuv? The node must start again. [y/N] y
Auth request hskey-authreq-QrS...tuv rejected.
```

The wrong verb for the kind is an error. The server checks it:

```
$ headscale auth approve hskey-authreq-AbC...xyz
Error: this is a registration request. It needs a user:
  headscale auth register hskey-authreq-AbC...xyz <user>


$ headscale auth register hskey-authreq-QrS...tuv alice
Error: this is an SSH check request. Use:
  headscale auth approve hskey-authreq-QrS...tuv
```

The target is the full auth ID. There is no prefix match, no `auth list` and no `auth get`. Auth requests live in the registration cache, which is internal state (see [#2804]).

`auth register` prints the new node with `-o json`. `approve` and `reject` print nothing.

#### `auth keys`

```
headscale auth keys list
headscale auth keys list --all
headscale auth keys list --filter owner=tag:ci

headscale auth keys get ab12cd
```

The owner of a key is a user **or** a list of tags, never both. It is the one positional argument:

```
headscale auth keys create alice
headscale auth keys create alice --reusable --expiry 24h
headscale auth keys create tag:ci,tag:build --ephemeral


$ headscale auth keys create alice,tag:ci
Error: a key is owned by one user or by tags, not both.

$ headscale auth keys create alice,bob
Error: a key is owned by one user. Got 2: alice, bob.
```

A tag is easy to recognise: it always starts with `tag:`.

The default expiry is 1 hour. `never` is not allowed.

`revoke` and `delete` are different:

```
headscale auth keys revoke 7       # stops working now; the record stays for a while
headscale auth keys delete 7       # the record is gone now
```

A revoked auth key stays visible, so that you can see what was stopped. The server removes it after a retention time (`preauth_keys.revoked_retention`, 7 days by default).

**State and `--all`.** Every key has a state:

| State     | Meaning                                             |
| --------- | --------------------------------------------------- |
| `valid`   | works                                               |
| `used`    | a key that is not reusable and that a node has used |
| `expired` | past its expiry                                     |
| `revoked` | stopped with `revoke`                               |

When more than one applies, the first of `revoked`, `used`, `expired` wins.

`state` is a normal column. By default the list hides every key that is not `valid`. `--all` removes that default filter and adds the `STATE` column to the default columns. A filter on `state` removes the default filter too. JSON follows the same rule. An explicit `--columns` decides the columns, with or without `--all`.

```
$ headscale auth keys list --all
ID  PREFIX  OWNER   STATE    REUSABLE  EPHEMERAL  EXPIRY  CREATED
3   zz91aa  alice   revoked  no        no         in 5d   2d ago
5   kk20bb  bob     expired  yes       no         3d ago  33d ago
6   mm77cc  bob     used     no        no         in 2d   5d ago
7   ab12cd  alice   valid    yes       no         in 23h  1h ago
9   ef34gh  tag:ci  valid    no        yes        in 6d   2d ago

$ headscale auth keys list --filter state=expired
```

`get` shows the stored details of a key. It never shows the secret.

```
$ headscale auth keys get ab12cd
ID:         7
Prefix:     ab12cd
Owner:      User 3 (alice)
Reusable:   yes
Ephemeral:  no
State:      valid
Expiry:     in 23h (2026-11-11 08:14 UTC)
Created:    1h ago (2026-11-10 08:14 UTC)
```

### `api`

`api` is authentication towards the headscale API.

#### `api keys`

```
headscale api keys list
headscale api keys list --all
headscale api keys get 2

headscale api keys create                              # admin key, 90 days
headscale api keys create --expiry 30d
headscale api keys create --user alice --expiry 90d    # owned by User 3 (alice)

headscale api keys revoke tr81ys
headscale api keys delete tr81ys
```

`--user` is new. Without it the key is an admin key, as today. With it the key is owned by that user. The v2 API needs a user-owned API key to create a user-owned auth key, so this makes that endpoint usable from Terraform and scripts.

The default expiry is 90 days. `never` is not allowed.

An API key has two states: `valid` and `expired`. `revoke` sets the expiry to now, so a revoked API key shows as `expired`. The server stores nothing more for it. `--all` and the `state` column work as for [auth keys](#auth-keys).

```
$ headscale api keys revoke tr81ys
Revoke API key 2 (tr81ys), owned by User 4 (bob)? [y/N] y
API key 2 (tr81ys) is expired now.
```

#### `api oauth-clients`

```
headscale api oauth-clients list
headscale api oauth-clients get k9f2

headscale api oauth-clients create devices:core:read
headscale api oauth-clients create devices:core,auth_keys --tags tag:ci
headscale api oauth-clients create devices:core --tags tag:ci -d "CI"

headscale api oauth-clients delete k9f2
```

Scopes are required, so they are positional. Tags are optional, so they are a flag. Some scopes need a tag:

```
$ headscale api oauth-clients create auth_keys
Error: scope auth_keys needs at least one tag (--tags).
```

An OAuth client has no expiry and no state. It works until it is deleted.

### `policy`

```
headscale policy get > policy.hujson
headscale policy get -o json | jq -r .UpdatedAt

headscale policy set policy.hujson
headscale policy set policy.hujson --dry-run
```

`policy get` prints the policy text exactly as stored, comments included, so `get > file` round-trips. It is the one `get` that does not print a sheet.

`policy set` replaces the whole policy. It does not prompt: you hold the file, and the server refuses an invalid policy and keeps the old one.

`--dry-run` runs every check that `set` runs against the live users and nodes, then stops before it saves:

```
$ headscale policy set policy.hujson --dry-run
Policy is valid for this server. Nothing was changed.
```

A file argument of `-` means stdin, for `policy set` and for `check policy`:

```
generate-policy.sh | headscale check policy -
generate-policy.sh | headscale policy set -
```

With stdin as the file there is no terminal to answer a prompt. So `policy set -` together with the database bypass needs `--force`.

#### The database bypass

`policy get` and `policy set` keep `--bypass-server-and-access-database-directly`. It is the rescue path when a bad policy in the database stops the server from starting.

With this flag the command does not talk to the server. It opens the database itself. So it needs the full server config, not only a socket path. It prompts, because the server must be stopped:

```
$ headscale policy get --bypass-server-and-access-database-directly > p.hujson
This reads the database directly. Headscale must not be running.
Continue? [y/N]
```

`--dry-run` works with the bypass. It checks the file against the users and nodes in the database and writes nothing. This replaces the old `policy check` with the bypass flag.

```
headscale policy get --bypass-server-and-access-database-directly > p.hujson

$EDITOR p.hujson

headscale check policy p.hujson

headscale policy set p.hujson --dry-run --bypass-server-and-access-database-directly

headscale policy set p.hujson --bypass-server-and-access-database-directly
```

### `check`

`check` commands are offline. They need no server and no database. They never prompt and never write a file. The exit code is the result.

This makes them usable in CI and at build time, for example in a Nix derivation ([#2898]).

A check of one file prints one line to stdout when it passes. When it fails, it prints the reason to stderr and exits 1.

```
$ headscale check config
Configuration /etc/headscale/config.yaml is valid.

$ headscale check config other.yaml
Configuration other.yaml is valid.


$ headscale check policy policy.hujson
Policy is valid (12 tests passed).


$ headscale check policy bad.hujson
Error: test 3 failed: alice@ -> 10.0.0.1:22 expected accept, got deny
$ echo $?
1


$ headscale check derp-map derp.yaml
DERP map derp.yaml is valid.

$ headscale check extra-records records.json
Extra records records.json are valid.
```

`check policy` always runs the `tests` and `sshTests` blocks of the policy, against stand-in users and nodes built from the policy itself. There is no separate `policy test` command (see [#3005]).

`check policy` knows no real users or nodes. To test a policy against the live server without applying it, use `policy set --dry-run`.

`check config` rejects unknown and removed keys ([#1926]).

`check all` checks the config and every file it points at. It prints its whole report to stdout, one line per file, and exits 1 when a file fails:

```
$ headscale check all
ok    /etc/headscale/config.yaml
ok    /etc/headscale/policy.hujson
FAIL  /etc/headscale/derp.yaml
        region 900: missing node hostname
skip  /var/lib/headscale/noise_private.key (created at startup)
$ echo $?
1
```

The `check` group comes from the open config pull requests, see [Relation to the open config pull requests](#relation-to-the-open-config-pull-requests). This redesign changes two things about it: the file is a positional argument, and `-` reads from stdin.

### `generate`

```
headscale generate private-key

headscale generate config                # example config
headscale generate config --running      # redacted config of the running server

headscale generate nixos-options         # options for the NixOS module

headscale generate cli-reference > docs/ref/cli.md
```

`generate private-key`, `generate config` and `generate nixos-options` exist today or come from the open config pull requests. This redesign adds `generate cli-reference`, see [Generated documentation](#generated-documentation).

`generate config --running` is the one local command that asks the server. It takes the place of the hidden `dumpConfig`, which wrote the CLI's own view of the config to a fixed file.

### `version`

`version` prints the version information, as today, and checks GitHub for a newer release. The hint goes to stderr.

```
$ headscale version
...                                       <- stdout, as today
A newer version is available: v0.30.1     <- stderr
```

`version` is a local command, and the only command besides `serve` that contacts GitHub. `serve` checks once at startup, in the background, and logs one line.

Today every command checks. With blocked outbound traffic each command waits for the timeout ([#3119]).

- The check has a short timeout. When it fails, `version` prints no hint and still exits 0.

- The config key `disable_check_updates` turns the check off, for `serve` and for `version`. `version` reads the config for this when it finds one, and does not warn when it finds none.

- `version -o json` prints the same data with Go field names: `Version`, `Commit`, `BuildTime`, `Go`, `Dirty`.

### `debug`

```
$ headscale debug health
healthy
$ echo $?
0

$ headscale debug health -o json
{"DatabaseConnectivity": true}
```

`debug health` asks the running server whether it is healthy. It prints `healthy`, or the reason on stderr with exit 1. It is stable in one way: exit 0 means healthy. Container healthchecks rely on that:

```
healthcheck:
  test: ["CMD", "headscale", "debug", "health"]
```

`debug mockoidc` and `debug create-node` are test tools. They are unstable, keep their current flags, and do not follow the rules of this proposal. `mockoidc` runs a server of its own and reads no headscale config.

### Recipes

These live in the `Example` field of the commands they belong to, so they appear in the help and in the generated reference.

```
# Names of all nodes
headscale nodes list -o json | jq -r '.[].Name'

# All nodes of one user
headscale nodes list --filter owner=carol -o json | jq -r '.[].Name'

# Delete every node not seen for 90 days
headscale nodes list --filter 'last-seen>90d' -o json \
  | jq -r '.[].ID' \
  | xargs -n1 headscale nodes delete --force

# Nodes with a client older than 1.80
headscale nodes list --filter 'version<1.80' --columns name,owner,version

# Auth keys that expire within a week
headscale auth keys list --filter 'expiry<7d'
```

## Generated documentation

**The rule: the command definitions in the code are the only source.**

Help text, the command tree, the reference page in the docs and shell completion are all derived from them. Nobody writes the same fact in two places. No list of commands, flags, columns or JSON keys is kept by hand.

This is the same approach as the config work in [#3680], where the example config, the config reference and the NixOS options are generated from the config schema, and CI fails on a stale copy.

### What every command must carry

Each command declares these once, in its cobra definition:

| Field     | Content                                                                              | Feeds                                                                              |
| --------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `Use`     | name and argument pattern, for example `set <node>`                                  | help, tree, reference, argument-count errors                                       |
| `Short`   | one line that starts with a verb                                                     | the tree, group help, reference headings                                           |
| `Long`    | the full text: what it does, its rules, whether it prompts, what `-o json` returns   | command help, reference                                                            |
| `Example` | at least one runnable example; one per mode for commands with modes                  | command help, reference                                                            |
| `Aliases` | only `ls`, `rm`, `approve`                                                           | help, reference                                                                    |
| flags     | name, short letter, type, default, description                                       | help, reference, completion                                                        |
| columns   | for `list` commands: name, header, JSON key, type, default, list layout, description | the table, the JSON, `--list-columns`, `--filter`, `--sort`, completion, reference |

### What is generated from them

| Output             | Shown by                              | Built from                      |
| ------------------ | ------------------------------------- | ------------------------------- |
| Full command tree  | `headscale` and `headscale --help`    | the tree, `Use`, `Short`        |
| Group help         | `headscale nodes --help`              | the sub-tree, `Short`, examples |
| Command help       | `headscale nodes set --help`          | `Long`, `Use`, `Example`, flags |
| Column list        | `headscale nodes list --list-columns` | column declarations             |
| Shell completion   | `headscale completion <shell>`        | commands, flags, column names   |
| CLI reference page | `headscale generate cli-reference`    | all of the above                |

### Tests that keep it honest

One test walks the whole command tree. It fails when:

- a command has an empty `Short`, `Long` or `Example`

- a short flag letter has two meanings

- a `list` command declares no columns

- a column has no field in the JSON type, or a field of the JSON type has no column (`Attributes` and `Key` are exempt)

- an entity group has `list` but no `get` (`routes` and `tags` are views and are exempt)

- a command has `--force` but can never prompt, or can prompt but has no `--force`

- a command accepts any number of arguments

`debug mockoidc` and `debug create-node` are exempt from all of these.

### The reference page

`headscale generate cli-reference` prints one markdown page to stdout. It is committed as `docs/ref/cli.md`.

- **One page.** It is easy to search and needs one entry in the docs navigation.

- **Built by walking the command tree.** The generator reads the same cobra definitions that the help reads.

- **Never edited by hand.** The first line says so.

- **Checked in CI.** The workflow from [#3680] that checks generated files also runs `headscale generate cli-reference | diff -u docs/ref/cli.md -`. A stale page fails the build.

- **Committed on its own.** A generated file never shares a commit with the code that changes it.

The page has this order:

1. the full command tree
1. global flags, the short-flag table, the alias table
1. one section per command, in tree order

## Configuration and environment

Environment variables stay for connection and config values:

| Variable                 | Purpose                         |
| ------------------------ | ------------------------------- |
| `HEADSCALE_CONFIG`       | path of the config file         |
| `HEADSCALE_UNIX_SOCKET`  | socket of a local server        |
| `HEADSCALE_CLI_ADDRESS`  | address of a remote server      |
| `HEADSCALE_CLI_API_KEY`  | API key for a remote server     |
| `HEADSCALE_CLI_TIMEOUT`  | how long to wait for the server |
| `HEADSCALE_CLI_INSECURE` | skip TLS verification           |
| `NO_COLOR`               | no colour in tables             |

`HEADSCALE_CONFIG` is the same as `--config`. No other flag has an environment variable. There is no `HEADSCALE_OUTPUT` and no `HEADSCALE_FORCE`. A `--force` that hides in the environment is dangerous.

A server command needs only a socket path or a remote address. A missing config file is normal for it, so it prints no warning and uses the defaults ([#3307]). Only `serve` warns about a missing config. The one exception is the [database bypass](#the-database-bypass), which needs the full server config.

## API backing

The rule for which API the CLI calls:

1. **Prefer the v2 API as it is.** v2 follows Tailscale's API. We never change it in a way that leaves that shape.

1. **Where v2 cannot do it, extend v1** with a proper REST design. Not in the style of the old gRPC shim.

The user does not see which API a command uses. The JSON is defined by the CLI, so the calls behind it can change.

These commands need server work:

| Command                                 | Needs                                                                                                                                  |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `users set`                             | new `PATCH /api/v1/user/{id}` (name, display name, email, picture)                                                                     |
| `users delete`                          | the v1 delete also removes the user's API keys                                                                                         |
| `users delete --with-nodes`             | new option on `DELETE /api/v1/user/{id}`, one transaction                                                                              |
| `api keys create --user`                | new owner field on the v1 create call                                                                                                  |
| `api keys list` with `OWNER`            | owner in the v1 list response                                                                                                          |
| `auth keys list --all`, state `revoked` | the v1 auth key list gets an option to include revoked keys, and the key carries its revoke time. No list returns a revoked key today. |
| `auth approve`, `auth register`         | the v1 calls refuse an auth request of the wrong kind                                                                                  |
| `generate config --running`             | `GET /api/v1/config`, added by [#3680]                                                                                                 |

Every other command uses calls that exist. The table follows the rule above: v2 where it does the whole job, v1 where it does not.

| Command                                  | Call                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| every resolver                           | the list call of that entity                                                                                          |
| `nodes list`, `nodes get`                | v1 node list (owner, given name, routes, keys) joined by ID with the v2 device list (client version, OS, update flag) |
| `nodes get`, `Attributes`                | v2 attributes call for that node                                                                                      |
| `nodes set --name`                       | v2 name call                                                                                                          |
| `nodes set --expiry never`               | v2 key call (disable key expiry)                                                                                      |
| `nodes set --expiry now`, `nodes expire` | v2 expire call                                                                                                        |
| `nodes set --expiry <time>`              | v1 expire call; v2 has no call that takes a time                                                                      |
| `nodes delete`                           | v2 delete call                                                                                                        |
| `nodes update-client`                    | v2 update-client call                                                                                                 |
| `nodes routes set`, `clear`              | v2 routes call; the CLI turns `exit` into both prefixes itself                                                        |
| `nodes tags set`                         | v2 tags call; the CLI refuses an empty list itself                                                                    |
| `nodes tags list`                        | the node list and `tagOwners` from the policy                                                                         |
| `users list`, `get`, `create`            | v1 user calls; v2 has no username and no writes                                                                       |
| `users list` columns `COUNT`, `NODES`    | the node list                                                                                                         |
| `auth register`, `approve`, `reject`     | v1 auth calls                                                                                                         |
| `auth keys create`, `delete`             | v1 auth key calls; v2 cannot create a key for a chosen owner                                                          |
| `auth keys revoke`                       | v2 key delete, which is a soft revoke                                                                                 |
| `auth keys`, `api keys`: prefix          | cut out of the masked key that the v1 lists return                                                                    |
| `api keys create`, `list`, `delete`      | v1 API key calls; v2 has no API keys                                                                                  |
| `api keys get`                           | v1 API key list; there is no call for one key                                                                         |
| `api keys revoke`                        | v1 expire call                                                                                                        |
| `api oauth-clients`                      | v2 key calls; OAuth clients exist only in v2                                                                          |
| `policy get`, `set`                      | v1 policy calls                                                                                                       |
| `policy set --dry-run`                   | v1 policy check call                                                                                                  |
| `debug health`                           | v1 health call                                                                                                        |

`nodes list` makes two calls today. That is hidden behind the CLI's JSON. If the server later gives all of it in one call, the output does not change.

These API operations get no CLI command, on purpose:

- tailnet settings, read and write (the write call is not implemented)
- the OAuth token endpoint (used by API programs, not by an admin)
- the v2 "authorize device" call (it does nothing until device approval exists)
- the v2 update-status call (not needed; `nodes update-client` reports the start)
- the v2 policy calls (the v1 calls do the same)

## Changelog

The old commands are not kept in the code. There are no deprecated shims and no stubs that print a hint. Nothing of the old CLI is left to maintain.

The changelog is therefore the one place where a user learns what changed. It must be complete.

### Rules for the entry

- **Every changed command and every changed behaviour is listed.** If it is not in the changelog, the user finds out in production.

- **Every item has a before and an after example.** Real commands, not descriptions. A pure addition is listed without a "before".

- **The long lists are collapsed by default** (`<details>`). The entry is long; the visible part stays short.

- **Visible at the top:** what the change is, what to do before the upgrade, what to do after it.

- **The NixOS test kit gets its own BREAKING entry.** The test kit is a public contract (`nix/README.md`).

- **Server and API changes are listed too**, also the ones that only add something.

- **"Before" is the last release, 0.29.** Not the main branch. Three things differ: in 0.29 `preauthkeys create --user` took a user ID only, the bypass flag was `--bypass-grpc-and-access-database-directly`, and the JSON had snake_case keys with numbers for IDs.

- **Some things exist only on the main branch** and were never released: `oauth-clients`, `nodes update-client`, the NixOS test kit, and the camelCase JSON. Their rows are marked "(unreleased)". The 0.30 entries that already describe them are edited, see [What else the implementation touches](#what-else-the-implementation-touches).

- **The NixOS test kit entry is edited and also marked BREAKING.** The kit is new in 0.30, but other projects already use it from the main branch.

- **The config pull requests and this redesign ship in the same release.** So no released version has the in-between form `check policy -f`.

<details>
<summary>Targets are positional, and names work</summary>

`--identifier`, `--id`, `--name`, `--prefix` and `--auth-id` are gone. The target comes after the command.

A node is named by ID, tailnet IP, given name or hostname. A user by ID, email, username or OIDC identifier. A key by ID or prefix.

```
# before
headscale nodes delete --identifier 12
headscale users destroy --name alice
headscale preauthkeys create --user 3            # a user ID only
headscale apikeys expire --prefix tr81ys

# after
headscale nodes delete 12
headscale nodes delete mynode
headscale nodes delete 100.64.0.1
headscale users delete alice
headscale auth keys create alice
headscale api keys revoke tr81ys
```

A name that matches more than one object is an error that lists the candidates.

</details>

<details>
<summary>Files are positional</summary>

`--file` / `-f` is gone. `-` reads from stdin.

```
# before
headscale policy set -f policy.hujson
headscale policy check -f policy.hujson

# after
headscale policy set policy.hujson
headscale check policy policy.hujson
generate-policy.sh | headscale policy set -
```

</details>

<details>
<summary>Flags: short letters, `--expiry`, `--force`</summary>

Short flags keep one meaning each. Only these exist: `-o`, `-c`, `-h`, `-e` (expiry), `-d` (description), `-u` (user). All others are long only. The `debug` test tools are exempt.

`--expiration` is now `--expiry` everywhere.

`--force` exists only on commands that can prompt. On any other command it is an unknown flag.

```
# before
headscale users create dave -d "Dave D" -e dave@example.com -p https://x/y.png
headscale preauthkeys create -u 3 --expiration 24h
headscale nodes list --force                      # accepted, no effect

# after
headscale users create dave --display-name "Dave D" --email dave@example.com --picture-url https://x/y.png
headscale auth keys create alice --expiry 24h
headscale nodes list --force                      # Error: unknown flag: --force
```

</details>

<details>
<summary>Aliases removed</summary>

Only `ls` (list), `rm` (delete) and `nodes routes approve` (routes set) remain.

```
# before
headscale node ls
headscale user new dave
headscale nodes show
headscale preauthkeys c -u 3
headscale nodes del -i 12

# after
headscale nodes ls
headscale users create dave
headscale nodes list
headscale auth keys create alice
headscale nodes rm 12
```

</details>

<details>
<summary>JSON output</summary>

`-o json` has a new format. The CLI defines it: one key per column, with Go field names. IDs are strings. Times are RFC 3339.

The format matches the binary that printed it. It can change between versions.

`yaml` and `json-line` are removed. An unknown format is an error.

```
# before (0.29)
$ headscale nodes list -o json | jq '.[0]'
{"id": 12, "name": "ubuntu-vm", "given_name": "mynode",
 "user": {"id": 3, "name": "alice"}, "ip_addresses": [...],
 "online": true, "last_seen": {"seconds": ...}, ...}

# after
$ headscale nodes list -o json | jq '.[0]'
{"ID": "12", "Name": "mynode",
 "Owner": {"User": {"ID": "3", "Name": "alice", "Email": ""}, "Tags": []},
 "IP": [...], "Online": true, "LastSeen": "2026-11-10T09:14:00Z",
 "Hostname": "ubuntu-vm", ...}
```

Node keys, before and after:

| Before (0.29)      | After                                           |
| ------------------ | ----------------------------------------------- |
| `id`               | `ID`                                            |
| `given_name`       | `Name`                                          |
| `name`             | `Hostname`                                      |
| `user`             | `Owner.User`                                    |
| `tags`             | `Owner.Tags`                                    |
| `ip_addresses`     | `IP`                                            |
| `online`           | `Online`                                        |
| `last_seen`        | `LastSeen`                                      |
| `expiry`           | `Expiry`                                        |
| `approved_routes`  | `ApprovedRoutes`                                |
| `available_routes` | `AvailableRoutes`                               |
| `subnet_routes`    | `ServingRoutes`                                 |
| `register_method`  | `RegisterMethod`                                |
| `pre_auth_key`     | `AuthKey` (the ID only)                         |
| `machine_key`      | `MachineKey`                                    |
| `node_key`         | `NodeKey`                                       |
| `disco_key`        | `DiscoKey`                                      |
| `created_at`       | `Created`                                       |
| not there          | `Version`, `OS`, `UpdateAvailable`, `Ephemeral` |

Users, auth keys, API keys and OAuth clients change in the same way. `headscale <group> list --list-columns` prints every key.

`version -o json` and `health -o json` change too: `buildTime` is now `BuildTime`, and so on.

The main branch had a camelCase JSON for a while (unreleased). It is replaced by this one.

With `-o json`, a command that changes something prints the object after the change. `delete` prints nothing.

`-o json` no longer silences log lines and no longer changes the update check. Server commands print no log lines in any mode.

```
# before
headscale nodes list -o yaml
headscale nodes list --columns id,name -o json     # no such flag

# after
headscale nodes list -o json
headscale nodes list -o yaml                       # Error: unknown output format "yaml". Use json.
headscale nodes list --columns id,name -o json     # Error: --columns works on tables only.
```

</details>

<details>
<summary>Filtering, sorting and choosing columns</summary>

The filter flags of single commands are replaced by `--filter` on every list. `=` is exact, `:` is contains, `<` and `>` compare times, numbers and versions. The filter also applies to `-o json`.

```
# before
headscale nodes list --user alice
headscale users list --email carol@example.com
headscale users list --identifier 3

# after
headscale nodes list --filter owner=alice
headscale users list --filter email=carol@example.com
headscale users get 3

# new
headscale nodes list --filter 'last-seen>30d'
headscale nodes list --columns +os,+hostname --sort -last-seen
headscale nodes list --list-columns
headscale auth keys list --filter owner=tag:ci
```

</details>

<details>
<summary>Tables</summary>

The default node columns are `ID`, `NAME`, `OWNER`, `IP`, `VERSION`, `ONLINE`, `LAST SEEN`, `EXPIRY`.

`Hostname`, `MachineKey`, `NodeKey` and `Ephemeral` are no longer shown by default. `User` and `Tags` are merged into `OWNER`. `Expired` is merged into `EXPIRY`. `Connected` is now `ONLINE`.

IP addresses are on one line. Times are relative. In a pipe the table has no colour and one line per row.

```
# before
ID | Hostname | Name | MachineKey | NodeKey | User | Tags | IP addresses | Ephemeral | Last seen | Expiration | Connected | Expired

# after
ID  NAME     OWNER   IP                    VERSION  ONLINE  LAST SEEN  EXPIRY
12  mynode   alice   100.64.0.1, fd7a::1   1.82.0   yes     now        in 89d

# to get a column back
headscale nodes list --columns +hostname,+node-key
```

Other tables change too:

| Table     | Before                                                                  | After                                                     |
| --------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| users     | `ID, Name, Username, Email, Created`                                    | `ID, NAME, DISPLAY NAME, EMAIL, PROVIDER, COUNT, NODES`   |
| auth keys | `ID, Key/Prefix, Reusable, Ephemeral, Used, Expiration, Created, Owner` | `ID, PREFIX, OWNER, REUSABLE, EPHEMERAL, EXPIRY, CREATED` |
| API keys  | `ID, Prefix, Expiration, Created`                                       | `ID, PREFIX, OWNER, EXPIRY, CREATED, LAST USED`           |
| routes    | `ID, Hostname, Approved, Available, Serving (Primary)`                  | `ID, NAME, APPROVED, AVAILABLE, SERVING`                  |

In the users table, `NAME` is now the username. Before, `Name` was the display name and `Username` the username.

</details>

<details>
<summary>Errors and exit codes</summary>

Errors are plain text on stderr in every output mode. They are no longer a JSON object.

A declined prompt exits 1. A prompt without a terminal is an error.

```
# before
$ headscale nodes list -o json            # server down
{"error": "connecting to ..."}

$ echo n | headscale nodes delete -i 12; echo $?
0

# after
$ headscale nodes list -o json            # server down
Error: cannot connect to /var/run/headscale/headscale.sock      (stderr, exit 1)

$ echo n | headscale nodes delete 12; echo $?
Error: confirmation needed, but there is no terminal.
Run again with --force to delete Node 12 (mynode).
1
```

</details>

<details>
<summary>More commands ask for confirmation</summary>

New prompts: `auth keys revoke`, `auth keys delete`, `api keys revoke`, `api keys delete`, `auth reject`, and `nodes tags set` on a node that a user owns.

```
# before
headscale preauthkeys expire -i 7            # no question

# after
headscale auth keys revoke 7                 # asks
headscale auth keys revoke 7 --force         # does not ask
```

</details>

<details>
<summary>Wrong arguments are errors</summary>

Extra arguments were silently ignored. Now every command checks its arguments. An empty list value is an error too.

```
# before
$ headscale nodes approve-routes -i 2 "0.0.0.0/0"
Node updated                                  # nothing was approved

# after
$ headscale nodes routes set 2
Error: `nodes routes set` needs 2 arguments, got 1.

$ headscale nodes routes set 2 ""
Error: the route list is empty.
```

</details>

<details>
<summary>Keys</summary>

The owner of an auth key is one positional argument: a user, or a list of tags. A key cannot have both.

Lists show only keys that work. `--all` shows used, expired and revoked keys. This is new for API keys too: an expired API key is hidden by default.

`auth keys revoke` stops a key and keeps the record until the server's retention time removes it. `api keys revoke` sets the expiry to now. `delete` removes the record at once.

On create, stdout carries only the key. The notes go to stderr.

```
# before
headscale preauthkeys create --user 3 --tags tag:ci        # tagged key, "created by" user 3
headscale preauthkeys list                                 # all keys
headscale apikeys list                                     # all keys

# after
headscale auth keys create tag:ci
headscale auth keys list                                   # usable keys
headscale auth keys list --all                             # all keys, with STATE
headscale api keys list --all

# new
headscale api keys create --user alice                     # an API key owned by a user
headscale auth keys get ab12cd
```

</details>

<details>
<summary>Nodes</summary>

`rename` and the expiry flags are now `nodes set`. A time in the past is rejected. An empty name is rejected.

`nodes routes list` with an unknown node is an error. It used to list every node.

`exit` in a route list means both exit routes.

```
# before
headscale nodes rename -i 12 web-1
headscale nodes rename -i 12 ""                            # accepted
headscale nodes expire -i 12 -e 2020-01-01T00:00:00Z       # accepted: node expired

# after
headscale nodes set 12 --name web-1
headscale nodes set 12 --name ""                           # Error: a node needs a name.
headscale nodes set 12 --expiry 2020-01-01                 # Error: ... is in the past.
headscale nodes expire 12

# new
headscale nodes get mynode
headscale nodes set mynode --expiry 90d
headscale nodes routes set gateway 10.0.0.0/8,exit
headscale nodes tags list
```

</details>

<details>
<summary>Users</summary>

`users set` changes the username, display name, email and picture of a local user. `users rename` is gone.

`users delete` also removes the user's API keys. `users delete --with-nodes` removes the nodes too.

`users create` checks its input: the picture URL must be an absolute `http` or `https` URL, and the email must be an address.

```
# before
headscale users rename --name alice --new-name alice2
headscale users create dave --picture-url "javascript:alert(1)"    # accepted

# after
headscale users set alice --name alice2
headscale users create dave --picture-url "javascript:alert(1)"    # Error

# new
headscale users set alice --display-name "Alice A" --email a@b.c
headscale users set alice --picture-url ""                 # clear
headscale users get alice
headscale users delete alice --with-nodes
```

</details>

<details>
<summary>Auth requests</summary>

`auth approve` is for an SSH check. `auth register` is for a registration. The wrong one is now an error. Before, `auth approve` on a registration was accepted and the node had to start again.

```
# after
$ headscale auth approve <registration-auth-id>
Error: this is a registration request. It needs a user:
  headscale auth register <registration-auth-id> <user>
```

</details>

<details>
<summary>OAuth clients (unreleased)</summary>

Scopes are one positional comma list. Tags are `--tags`. `delete` asks for confirmation.

```
# before
headscale oauth-clients create --scope devices:core --scope auth_keys --tag tag:ci

# after
headscale api oauth-clients create devices:core,auth_keys --tags tag:ci
```

</details>

<details>
<summary>Checks run offline</summary>

`check config` and `check policy` need no server and no database, and they write nothing. `check policy` runs the tests in the policy.

To test a policy against the users and nodes of a running server, use `policy set --dry-run`.

The bypass flag has a new name: `--bypass-grpc-and-access-database-directly` is now `--bypass-server-and-access-database-directly`. `policy check` with the bypass is now `policy set --dry-run` with the bypass.

```
# before
headscale configtest                          # opened the database, ran migrations
headscale policy check -f p.hujson            # needed a running server
headscale policy check -f p.hujson --bypass-grpc-and-access-database-directly

# after
headscale check config
headscale check policy p.hujson
headscale check all
headscale policy set p.hujson --dry-run
headscale policy set p.hujson --dry-run --bypass-server-and-access-database-directly
```

</details>

<details>
<summary>Health, update check and config warning</summary>

`headscale health` is now `headscale debug health`. It prints `healthy`; before it printed an empty line.

Only `headscale version` and the start of `headscale serve` ask GitHub for a newer release. Other commands no longer do. This removes the long wait on hosts without outbound access.

Server commands no longer print `WRN no config file found, using defaults`.

```
# before
$ time headscale users list               # no outbound access
real 0m30.1s

# after
$ time headscale users list
real 0m0.1s
```

</details>

<details>
<summary>API</summary>

- Added: `PATCH /api/v1/user/{id}` to change a user.

- Added: an option on `DELETE /api/v1/user/{id}` to delete the user's nodes in the same step.

- Added: an owner on API keys, in create and list.

- Changed: deleting a user also deletes the user's API keys.

- Added: an option on `GET /api/v1/preauthkey` to include revoked keys, and a revoke time on the key.

- Changed: `POST /api/v1/auth/approve` refuses a registration request. `POST /api/v1/auth/register` refuses an SSH check request.

- Removed: `POST /api/v1/node/backfillips`.

</details>

hs-authkey alice --tags tag:ci

## Not in this redesign

Each of these was asked for. Each has a decision.

| Ask                                                     | Decision                                                                 |
| ------------------------------------------------------- | ------------------------------------------------------------------------ |
| `nodes ping` ([#2943])                                  | No. Not a job of the control server.                                     |
| `policy test` with ad-hoc sources ([#3005])             | No. Tests live in the policy; `check policy` runs them.                  |
| `nodes set-ip` ([#3133])                                | Later. Comes with IP pools ([#2912]).                                    |
| `nodes move`, user merge, set OIDC identifier ([#2170]) | No. `nodes move` was removed in [#2922].                                 |
| List auth requests ([#2804])                            | No. It exposes internal state. Use auth keys.                            |
| Server-side list filters                                | No. Not in Tailscale's API. Filtering is client-side.                    |
| Hosting avatar images ([#2166])                         | No. The protocol carries a URL.                                          |
| Several targets in one command ([#2687])                | Not now. One target per command; can be added without a break.           |
| TAB completion of live names ([#2687])                  | Later. Does not change any command.                                      |
| Mark stale tags in the node list ([#2981])              | Done in `nodes tags list` (`IN POLICY`), not in `nodes list`.            |
| Public IP as a list column ([#2272])                    | No. It costs one call per node. It is in `nodes get`, under Attributes.  |
| Posture attributes `node:os`, `node:tsVersion`, ...     | Not needed here. If the server fills them later, `nodes get` shows them. |
| A stable JSON format                                    | No. The JSON matches the binary that printed it.                         |

### Reserved names

These are not built in this redesign. The names are reserved so that the tree does not block them later. They are not in the command tree above.

**Device approval ([#2176]).** The server has no such feature yet. Tailscale's API word is "authorized". The names do not collide with `auth approve` (an SSH check) or `nodes routes approve` (an alias of `routes set`).

```
headscale nodes authorize   <node>
headscale nodes deauthorize <node>
headscale nodes list --columns +authorized
headscale auth keys create alice --preauthorized
```

**Update despite SSH sessions.** The Tailscale client refuses a remote update while it has active SSH sessions, unless the request says otherwise. Headscale cannot send that today. When it can, the flag is `--ignore-ssh-sessions`. It is never `--force`, because it is not a prompt.

```
headscale nodes update-client mynode --ignore-ssh-sessions
```

### Decisions from the three reviews

| Finding                                                    | Decision                                                                                    |

| A name can match in two fields of the resolver             | ID and IP win. All other fields are searched together. More than one match is an error.     |

## To verify during implementation

Most open points were checked against the code and moved into the text. These remain:

- **The table of calls under [API backing](#api-backing).** It was made by the rule "v2 where it does the whole job". Confirm for each v2 call that it does what the v1 call does: the same ownership checks on tags, the same result for routes, the same errors.

- **Limits on key expiry.** The v2 key create call caps the expiry at 90 days. The CLI uses v1 for keys. Confirm what limit v1 has, and state it in the help text.

- **A third kind of auth request.** The code has a constructor for an auth request with no payload, and no caller outside tests. Confirm that only two kinds can reach `auth approve`.

- **Where the JSON types live.** The Go types that define the JSON must be in one package that other Go programs can import. Pick the package.

- **`debug health` reasons.** The server answers healthy or not. Find what reason it can give for "not".

- **Tagged nodes and expiry.** Confirm what `nodes set --expiry` and `nodes expire` do on a tagged node, and write the error text if the server refuses.

This section is for whoever builds this. It records what the discussion settled and what the code looks like today, so that nothing has to be found out twice.

### Decisions that look like mistakes but are not

The maintainer chose each of these on purpose. Do not "fix" them back.

| Decision                                                                   | The other option that was rejected                          |
| -------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Files are positional (`policy set <file>`)                                 | `-f/--file`, which the open config PRs and the test kit use |
| `health` moves to `debug health`                                           | keep it top-level for container healthchecks                |
| `--filter` has `<` and `>` for times, numbers and versions                 | text only, with `jq` for the rest                           |
| Aliases `ls`, `rm` and `routes approve` stay                               | no aliases at all                                           |
| `users set --name` replaces `users rename`                                 | keep `rename` as its own command                            |
| `nodes set --name --expiry` replaces `nodes rename` and the `expire` flags | separate verbs for each                                     |
| `users delete --with-nodes`, as one server call, with a prompt             | refuse and make the admin delete nodes first                |
| Short flags `-e`, `-d`, `-u` stay                                          | long flags only                                             |
| No stubs or shims for old commands                                         | hint stubs for one release                                  |
| `nodes backfillips` is removed, with a changelog note                      | run the backfill at server start                            |
| v2 is used as it is and never bent; gaps go to v1 as proper REST           | headscale-only extensions in v2                             |
| `check` and `generate` are top-level tool groups                           | `policy check`, `config validate`                           |
| JSON is defined by the CLI, one key per column                             | print the API object                                        |
| JSON keys are Go field names (`LastSeen`)                                  | camelCase, as the API uses                                  |
| The JSON carries no stability promise                                      | stable keys with a changelog rule                           |
| IDs are strings in the JSON                                                | numbers                                                     |
| `--columns` with `-o json` is an error                                     | let `--columns` choose the JSON keys                        |
| The CLI cuts the key prefix out of the masked key                          | a plain `prefix` field in the v1 API                        |
| `api keys revoke` sets the expiry to now                                   | a revoked state for API keys in the server                  |
| The public IP is only in `nodes get`, as a posture attribute               | an opt-in list column with one call per node                |
| `--ignore-ssh-sessions` is reserved, not built                             | a new v1 update call now                                    |
| The v1 auth key list can return revoked keys                               | a revoked key leaves every list, and `revoke` is dropped    |
| A duration in a time filter is a distance from now                         | timestamps only                                             |
| `disco-key`, `register-method` and `auth-key` stay, as opt-in node columns | drop them from the CLI                                      |
| `version` and `debug health` JSON use Go field names too                   | keep their camelCase keys                                   |
| `hs-authkey OWNER` in the NixOS test kit                                   | keep `USER` and handle `--tags` inside the script           |

### Relation to the open config pull requests

A stack of open pull requests already adds `check` and `generate`: [#3668] (`check policy`), [#3669] (`check config`, `check all`, `check derp-map`, `check extra-records`), [#3674] (strict config loading), [#3680] (`generate config`, `generate nixos-options`, the CI check for generated files), [#3682] (NixOS module), [#3685] (config load errors).

They use `-f` for files. They land in their own shape first. **The redesign restructures on top of them.** Do not rework them first, and do not wait for this proposal to change them.

Reuse from that stack: the CI workflow that fails on stale generated files, and the pattern "print to stdout, commit the output, diff in CI".

### Shared building blocks

The proposal asks for generic pieces. Every command uses them; no command has its own copy.

- **Resolver.** One per entity type. Returns one object or a typed error (not found, ambiguous with candidates). Used for targets, for second arguments, for `--user`, for the owner of `auth keys create`, and for `--filter owner=`.

- **Output types.** One Go type per entity: node, user, auth key, API key, OAuth client, tag row. Its field names are the JSON keys; no field is renamed by a tag. Two fields are not columns and are left out when empty: `Attributes` on a node and `Key` on a new key. The CLI fills the type from whatever API calls it needs.

- **Column table.** A list command declares its columns once: name, header, JSON field, type (id, text, number, bool, time, version, list, owner), default, list layout (inline, stacked, cut), description. `--columns`, `--list-columns`, `--filter`, `--sort`, completion and the reference page all read that one declaration. A test checks that columns and fields of the output type match one to one.

- **Output.** One function for results: table, sheet or JSON to stdout. One function for errors: plain text to stderr, exit 1. One function for notes to stderr.

- **Prompt.** One helper. It shows the object, reads the answer, honours `--force`, and fails without a terminal. A declined prompt is an error, not a silent return.

- **Argument check.** One helper that builds the "needs N arguments, got M" message with the usage line.

- **Time parser.** One parser for every time value. `--expiry` rejects the past; `--filter` accepts past and future.

### What the code does today

These are the places the redesign has to change. Names, not line numbers, so that the list survives edits.

**`cmd/headscale/cli/root.go`**

- `--config`, `--output` and `--force` are persistent flags on the root. `--force` must become per-command.

- The flags and `initConfig` are skipped when `os.Args[1]` is `version`, `mockoidc` or `completion`. Moving `mockoidc` under `debug` breaks that test. Replace it with a per-command setting.

- `initConfig` calls the GitHub update check on every command. Move it to `version` and `serve`. The config key `disable_check_updates` still turns it off there.

**`cmd/headscale/cli/utils.go`**

- "Is the output machine-readable" is decided by scanning the arguments for a bare word `json`, `json-line` or `yaml`. `-o=json` is not detected, and a positional value `json` is. Read the flag instead.

- `confirmAction` returns without an error when the user declines. The command then exits 0.

- Errors are printed as `{"error": ...}` in the chosen format.

- An unknown `-o` value prints an empty line.

- The connection code probes the socket and retries until `cli.timeout` (5 seconds by default). Keep that; improve the final error text.

**`cmd/headscale/cli/nodes.go`**

- `nodes list --user` is a server-side exact match on the username.

- `list-routes` filters on the client. An ID that does not exist falls through and lists every node.

- The route table's "Hostname" column holds the given name.

- `expire` already accepts an RFC 3339 time and `--disable`.

- `update-client` uses the v2 client and its own 15 second timeout. The server sends the node no override for SSH sessions. A node that refuses is answered "not found"; the reason is only in the server log.

- `rename` takes its new name as a positional and accepts an empty one.

**`cmd/headscale/cli/users.go`**

- The table header "Name" holds the display name and "Username" holds the name.

- `users list` filters on the server by exact match. Client and server disagree on which filter wins when several are given.

- `users create` checks the picture URL with `url.Parse` only. That accepts `javascript:` and relative paths.

- `resolveSingleUser` already builds an ambiguity error with ID, name, email and provider. Reuse the idea.

**`cmd/headscale/cli/preauthkeys.go`, `api_key.go`, `oauth_client.go`**

- `preauthkeys create` accepts `--user` together with `--tags`. The key is then owned by the tags, and the user is stored as "created by". The new CLI drops that combination.

- The v1 auth key has no plain prefix. It has `key`, masked as `hskey-auth-<prefix>-***`. The v1 API key has `prefix`, masked the same way. The CLI cuts the prefix out.

- `apikeys delete` turns an ID into a prefix by listing all keys on the client. There is no call for one API key.

- The API key list returns a last-seen time that the table does not show. The new table shows it as `LAST USED`.

- OAuth clients are v2 keys filtered on the client to the client key type. Their IDs are public hex strings with no prefix. The secret has the form `hskey-client-<id>-<secret>`.

- No key command prompts today.

**`cmd/headscale/cli/policy.go`**

- `get`, `set` and `check` ignore `-o`. `get` drops the update time.

- The bypass flag opens the database directly and needs a full server config. `check` has the flag today.

**`cmd/headscale/cli/configtest.go`, `health.go`, `version.go`**

- `configtest` builds the whole server. It creates the noise key and runs database migrations.

- `health` prints an empty line in human mode. Only the exit code carries the answer.

- `version` prints several lines. The redesign does not change them; it only adds the update hint on stderr.

**Server: users and nodes**

- `User.Username()` returns the email first, then the name. That is why `OWNER` shows an email for a user who has one.

- `db.GetUserByName` matches the name only. The resolver works on the client from the user list, so it is not affected.

- v1 users have create, rename, delete and list. There is no update. v2 users are read-only; they have no username, no separate email and no provider.

- The v1 node has `name` (what the node reports) and `givenName`. The v2 device has `name` (the full MagicDNS name) and `hostname` (what the node reports). The same word means two things.

- The v1 node carries no client version and no OS. Only the v2 device has them, with a flag for "update available" but no version number.

- The v2 device has `user` as a text only, with no ID. For a tagged device it is the login that made the auth key. Do not use it for `OWNER`; use the v1 node.

- Serving routes are only in the v1 node (`subnetRoutes`). The v2 device has advertised and enabled routes, and only when all fields are requested.

- The v2 device leaves `expires` out when there is no expiry and sets `keyExpiryDisabled`. The v1 node has `expiry: null`.

- The public IP is the posture attribute `ip:publicAddress`, from the v2 attributes call of one device. It is the only attribute headscale sets.

- The v1 tags call rejects an empty list ("cannot remove all tags"). The v2 call treats an empty list as "no change".

- The v1 route approval expands a single exit route to both address families.

**Server: keys and auth**

- v1 "expire" on an auth key sets the expiry to now. The v2 key delete is a soft revoke: it stores a revoke time and the key stops working. A background job deletes revoked keys after `preauth_keys.revoked_retention` (168 hours by default). Hard delete is a third call.

- No list returns a revoked auth key. The v1 list hides revoked keys. The v2 list hides every key that does not work: revoked, expired and used. Only the v2 call for one key by ID returns it.

- The v1 auth key has a `used` flag. It is also set on a reusable key that was used, so the state `used` is "`used` and not reusable".

- API keys have expire and delete only. There is no revoke time.

- `OAuthClient.Revoked` is never set. Deleting an OAuth client is always a hard delete, including its tokens.

- `State.SetAPIKeyUser` exists but no API reaches it.

- An auth request is one of two kinds: a registration (it carries registration data) or an SSH check (it is bound to a source and a destination node). `auth approve` finishes the request with an empty verdict. For an SSH check that means yes. For a registration it means "no node", and the node is told to register again. `auth reject` works for both kinds.

- There is no call that lists auth requests. Lookup is by full auth ID.

**Server: other**

- The policy read call works in database mode and in file mode.

- Every list prints a bare JSON array today, in the API's camelCase. That format is unreleased; 0.29 printed snake_case keys and numbers for IDs. `nix/testkit.nix` and `nix/tests/headscale.nix` read the JSON.

- In 0.29, `preauthkeys create --user` took a user ID only, and the bypass flag was `--bypass-grpc-and-access-database-directly`.
