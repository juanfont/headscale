# Headscale API redesign

**Status:** draft, for discussion. This PR exists so we can shape the design together; it is not meant to be merged as-is.

Headscale has two HTTP APIs today, and neither is a good base for the future.

- `/api/v1` is the admin API. Its shape comes from the old gRPC gateway, with verbs and arguments in paths, three ways to name a target, and a node that looks different from one call to the next. An error does not say which rule was broken, so web UIs match on its text.
- `/api/v2` follows the Tailscale API so that the Tailscale Terraform provider, `tscli` and the Kubernetes operator work. It can only offer what Tailscale has, in Tailscale's shape.

This proposal adds a third API, designed for Headscale: resource-based, built with Huma, and published with an OpenAPI document and a generated client. The new CLI ([001](001-cli.md), [#3375]) uses only this API. The old `/api/v1` is frozen in 0.30 and removed in 0.31. v0 does not have to stay compatible with it.

The design was checked against the calls that the web UIs in [the web UI list](../ref/integration/web-ui.md) make today; [Checked against the web UIs](#checked-against-the-web-uis) records what v0 covers and what it does not.

## Words used here

These are the words of [001](001-cli.md#words-used-here); the API and the CLI share one vocabulary.

| Word          | Meaning                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| v0            | the new API, at `/api/headscale/v0`                                                                                        |
| legacy API    | today's `/api/v1`                                                                                                          |
| Tailscale API | `/api/v2`, which follows Tailscale's public API                                                                            |
| resource      | a stored object with an ID: a node, a user, an auth key, an API key, an OAuth client. 001 says "entity" for the same thing |
| collection    | all resources of one kind, for example `/nodes`                                                                            |
| action        | an operation that is not create, read, update or delete, for example "expire"                                              |
| name          | of a node: its name in Headscale, used by MagicDNS (the legacy API: `givenName`)                                           |
| hostname      | the name a node reports about itself; Headscale cannot change it (the legacy API: `name`)                                  |
| owner         | who a node or key belongs to: one user, or a set of tags, never both                                                       |
| auth key      | a key a node uses to join (the legacy API: "pre-auth key")                                                                 |
| API key       | a key a program uses to call the API                                                                                       |
| OAuth client  | an ID and secret that mint short-lived, scoped access tokens                                                               |
| auth request  | a short-lived request from a node, named by its auth ID: a registration or an SSH check                                    |
| problem       | an error response in the RFC 9457 format                                                                                   |

The examples use the users and nodes of 001: User 3 `alice`, User 4 `bob`, User 5 `carol`, Node 12 `mynode` (owned by alice), Node 13 `builder` (tagged `tag:ci`, `tag:build`). "Now" is 2026-11-10 09:14 UTC.

## Principles

1. **One resource, one shape.** A node is the same object in a list, in a get and in the response to every write, and it carries everything a client shows: owner, routes, online state and client version.

1. **One way to name a target.** A resource is named by its ID in the path; names, emails and prefixes are filters on a list, never a second kind of ID.

1. **Standard methods first.** Collections and resources use `GET`, `POST`, `PATCH`, `PUT` and `DELETE`, and an action gets its own path only when it is not a field change.

1. **A program never has to read prose.** Every error has a stable code, and every state a client must branch on is a field or an enum, not something to compute from timestamps or a text to match.

1. **Nothing is silently ignored.** An unknown body field, an unknown query parameter and a field that cannot be changed are all errors.

1. **The CLI is the first client.** A 001 command finds its target and then makes one call. If the CLI has to join, count or guess, the API is wrong.

1. **Headscale words.** `/api/v2` speaks Tailscale ("device", "tailnet", `enabledRoutes`) and v0 speaks Headscale ("node", "approved routes"). No path has a tailnet segment.

1. **Change is announced.** v0 may change in any release, but every such change is in the changelog; nothing changes without a note.

## The three APIs

| API       | Path                 | Code                         | Rule                                                           |
| --------- | -------------------- | ---------------------------- | -------------------------------------------------------------- |
| legacy    | `/api/v1`            | `hscontrol/api/v1`           | frozen and deprecated in 0.30, when v0 ships; removed in 0.31  |
| Tailscale | `/api/v2`, `/api/v3` | `hscontrol/api/v2`           | only what Tailscale has, in Tailscale's shape                  |
| Headscale | `/api/headscale/v0`  | `hscontrol/api/headscale/v0` | this proposal; may change in any release until it becomes `v1` |

**`/api/v*` is reserved for the Tailscale API.** Every Headscale API lives under `/api/headscale/`, and v0 becomes `/api/headscale/v1` once it is stable.

**Why the paths are what they are:**

- The Tailscale API cannot move under a prefix such as `/tailscale/api/v2`. The Terraform provider, `tscli`, the Go client and the Tailscale client's OAuth flow all accept a base URL with a path. The Kubernetes operator is different: it has one setting, `OPERATOR_LOGIN_SERVER`, which it uses both as the API base and as the control server for the nodes it creates. A path in that URL would also move the control endpoints those nodes call (`/key`, `/machine/register`, `/machine/map`), so `/api/v2` stays at the root, next to them.
- The legacy API cannot move, because the web UIs have `/api/v1` in their code.
- A new API at `/api/v0` would have no next step: `/api/v1` is taken by the legacy API, reusing that path with a new shape would break the web UIs without an error, and `/api/v2` and up belong to Tailscale.
- `/api/headscale/v0` stays under `/api`, so reverse proxies that forward `/api` keep working.

**The Tailscale API gets no Headscale endpoints.** An endpoint that Tailscale does not have could collide with one Tailscale adds later. `hscontrol/api/v2/README.md` allows such endpoints today; that sentence is removed. The CLI does not call `/api/v2` at all.

**"Frozen" for the legacy API means:** no new operations and no change to the wire shape. v0 and the legacy API call the same server code, so a fix there reaches both. Two changes that 001 asks for reach the legacy API this way: deleting a user also deletes the user's API keys, and `approve` refuses a registration.

The frozen shape must be the shape of 0.29; see [Implementation notes](#implementation-notes).

**Tools that do not use the HTTP API.** [Headscale Panel] speaks gRPC, which 0.30 removes. [ouroboros] and the local mode of [unraid-headscale-admin] run the `headscale` command and read its JSON, which 001 changes. Neither change comes from this proposal, and v0 is what these tools can move to.

## Conventions

These conventions hold for every operation; a resource section only mentions where it differs.

### Paths

- The base is `/api/headscale/v0`, which the paths below leave out.
- Collections are plural and in kebab-case: `/nodes`, `/users`, `/auth-keys`, `/api-keys`, `/oauth-clients`, `/auth-requests`, `/tags`.
- A resource is `/{collection}/{id}`.
- Collections are flat: there is no `/users/3/nodes`, because a tagged node has no user and would have no path there. Use `GET /nodes?user=3`.
- The policy is one document: `/policy`.

### Methods and status codes

| Operation | Request                   | Success | Body                                  |
| --------- | ------------------------- | ------- | ------------------------------------- |
| list      | `GET /nodes`              | 200     | `{"nodes": [...]}`                    |
| get       | `GET /nodes/{id}`         | 200     | the resource                          |
| create    | `POST /users`             | 201     | the resource, and a `Location` header |
| update    | `PATCH /nodes/{id}`       | 200     | the resource after the change         |
| replace   | `PUT /policy`             | 200     | the document after the change         |
| delete    | `DELETE /nodes/{id}`      | 204     | none                                  |
| action    | `POST /nodes/{id}/expire` | 200     | the resource after the action         |

- **Every write returns the whole resource**, with its computed fields, so a client never needs a second call to show the result.
- Deleting something that is already gone is a `404`.
- `approve` and `reject` on an auth request answer `204`, because the request is gone once it is answered. `register` answers with the new node.
- Deleting an auth key, an API key or an OAuth client is a soft delete, and it answers `204` when it is repeated; see [How a credential ends](#how-a-credential-ends).
- The only delete with a body is the user delete, which reports what it removed; see [Users](#users).

### IDs

- **Every ID is a string**, in bodies, paths and query parameters: `"id": "12"`.
- A client compares an ID for equality. Node, user and key IDs are whole numbers in a string, and a client may order them as numbers. OAuth client IDs are hex and auth IDs are long random strings; these two are opaque, and a client does nothing else with them.
- A resource has exactly one ID, and a path takes only that ID, never a name.

### Update with PATCH

`PATCH` changes the fields that are sent and leaves the others alone, following the rules of JSON Merge Patch (RFC 7396):

- A field that is left out does not change.
- `null` clears a field and is allowed only where "no value" has a meaning: `"expiry": null` on a node means "never expires".
- An empty string clears an optional text field, so `"email": ""` on a user removes the email. `"name": ""` on a node resets the name to the one made from its hostname, as the Tailscale API does. The `name` of a user cannot be empty (`invalid_field`).
- A list is replaced as a whole.
- A field that cannot be changed (`id`, `created`, `hostname`) is an error, not ignored.
- A body with no fields is an error (`empty_patch`).
- All fields of one request change together, or none of them do.
- The body has the media type `application/merge-patch+json`; `application/json` is accepted too.

```
PATCH /nodes/12
{"name": "web-1", "expiry": null}
```

### Actions

An action is a `POST` to a path under the resource, such as `POST /nodes/12/expire`, and it returns the resource after the action. Approve and reject of an auth request return `204`, because they leave no resource to return.

An action exists only for something that is not a field change: it uses the server's clock, talks to the node, or cannot be undone. Changing a name is not an action. Expire is the one action that a `PATCH` can also do, with `"expiry": "now"`; it stays because it is the common call. The full list:

| Action                              | Why it is not a field                               |
| ----------------------------------- | --------------------------------------------------- |
| `POST /nodes/{id}/expire`           | "now" is the server's clock; the node is logged out |
| `POST /nodes/{id}/update-client`    | asks the node to update itself                      |
| `POST /auth-requests/{id}/register` | answers a waiting node and creates a node           |
| `POST /auth-requests/{id}/approve`  | answers a waiting node                              |
| `POST /auth-requests/{id}/reject`   | answers a waiting node                              |
| `POST /policy/reload`               | reads the policy again from where it is stored      |

### Lists

- A list is an object with one key, the name of the collection: `{"nodes": [...]}`, `{"users": [...]}`, `{"authKeys": [...]}`. It is never a bare array, so the response can gain fields later.
- **A list returns everything.** v0 has no paging: Headscale holds every node in memory, and a tailnet has thousands of nodes at most.
- If paging is added, it is opt-in: a client asks for it with `pageSize`, and a client that does not ask keeps getting everything. Paging that is on by default would make a small web UI lose every row after the first page, without an error.
- The order is fixed: nodes, users and keys by ID as a number, OAuth clients by `created`, tags by name.
- **Filters** are query parameters with exact values, and when several are given, all must match. A filter that matches nothing gives an empty list, not a `404`.
- There is no sort parameter, no field selection and no filter language; the CLI filters and sorts what it shows on the client ([001, "The table engine"](001-cli.md#the-table-engine)).

### Values

| Kind      | On the wire                                                                                                                                                                                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| key names | lowerCamelCase: `lastSeen`, `approvedRoutes`                                                                                                                                                                                                                               |
| time      | RFC 3339 in UTC: `"2027-02-07T10:00:00Z"`. `null` when there is none. Never the year 1.                                                                                                                                                                                    |
| duration  | not used. A request carries a time, not "90 days".                                                                                                                                                                                                                         |
| text      | a string. `""` when unknown.                                                                                                                                                                                                                                               |
| list      | an array. `[]` when empty, never `null`.                                                                                                                                                                                                                                   |
| enum      | a short string in lowerCamelCase: `"oidc"`, `"sshCheck"`. A client must accept values it does not know.                                                                                                                                                                    |
| IP prefix | the real prefix: `"0.0.0.0/0"`, never a word such as `exit`.                                                                                                                                                                                                               |
| owner     | `{"user": {"id", "name", "loginName", "displayName", "email"}, "tags": []}`. Exactly one side is filled. `null` when there is no owner.                                                                                                                                    |
| reference | a small object with the ID and the name: `{"id": "12", "name": "mynode"}`. `null` when there is none, as is an ID on its own. A reference to a user has `loginName` in place of `name`, because the stored name of a user can be empty: `{"id": "4", "loginName": "bob"}`. |

- **Every field is always present** in a response; a field is never left out because it is empty.
- **A time field is named after the event**: `created`, `expiry`, `lastSeen`, `lastUsed`, `updated`, `revoked`, `removal`, the same words the CLI uses.
- **The server computes a state.** An auth key has `"state": "used"` and a node has `"expired": true`; a client does not compare `expiry` with its own clock.

### Secrets

- The secret of an auth key, an API key or an OAuth client appears in the response to the create call, in the field `key`, and nowhere else. The server keeps only a hash of it, so it cannot be read again.
- Every other response has the `prefix`, the short public part of the key, as a plain string and never as masked text such as `hskey-auth-ab12cd-***`.

### How a credential ends

Auth keys, API keys and OAuth clients end the same way, with `DELETE`. It is a soft delete, which is what the Tailscale API does for auth keys and OAuth clients.

- The credential stops working at once, and the response is `204`. Repeating the `DELETE` answers `204` again and changes nothing.
- The record stays, with `"state": "revoked"` and the time in `revoked`, so that a client can show what was stopped. It is in the list and can be read by its ID.
- The server removes the record later. A job that runs every hour removes every record that was revoked longer ago than the retention time, which is 7 days by default. A retention of `0` keeps revoked records for ever.
- An auth key that a node still refers to is kept until that node is deleted, so that `authKeyId` on the node stays valid.
- A revoked record has `removal`, the time after which the server removes it. It is `null` while the record is kept: the record is not revoked, the retention is `0`, or a node still refers to the key.
- A node that joined with an auth key is not affected when the key ends.
- No operation removes a single record at once. The one exception is the delete of a user: it removes the auth keys and API keys of that user together with the user, as Headscale does today. A node that still refers to such a key loses its `authKeyId`.

Today only auth keys have this, through the Tailscale API, with the setting `preauth_keys.revoked_retention`. v0 extends it to API keys and OAuth clients, and the setting needs a name that covers all three.

### Dry run

Two writes take `?dryRun=true`: `PUT /policy` and `DELETE /users/{id}`. A dry run runs every check of the real call, changes nothing, and answers with the same status and body the real call would give. An invalid policy is a `422` problem in a dry run too, never a `200`. One case differs from the real call: in file mode the real `PUT /policy` is refused with `policy_read_only`, and the dry run still checks the policy.

### Strictness

- An unknown field in a body is a `422`.
- An unknown query parameter is a `422` too, because a typo such as `?usr=3` must not return every node.
- Every operation has a limit on the size of its body, and a larger body is `too_large`.
- A client must ignore response fields it does not know; that is what lets the server add fields.

### Where each rule comes from

v0 follows the published standards and the major API guidelines, and a reviewer can check each rule against its source.

| Rule                                                                      | Source                                                        |
| ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| methods and status codes; `201` with `Location`; `204` with no body       | [RFC 9110]                                                    |
| `PATCH`, and its merge rules and media type                               | [RFC 5789], [RFC 7396]; Azure and Zalando ask for merge patch |
| the error body                                                            | [RFC 9457]                                                    |
| `ETag`, `If-Match`, `412`                                                 | [RFC 9110], section 13                                        |
| `Authorization: Bearer`; access tokens from client credentials            | [RFC 6750]; [RFC 6749], section 4.4                           |
| times                                                                     | [RFC 3339]                                                    |
| `Deprecation` and `Sunset`                                                | [RFC 9745], [RFC 8594]                                        |
| plural, flat collections; one ID, in the path                             | AIP-122; Zalando rules 134 and 141                            |
| a write returns the resource; no `PUT` of a whole resource                | AIP-134; Azure                                                |
| a list is an object, never a bare array                                   | AIP-158; Azure                                                |
| dry run                                                                   | AIP-163                                                       |
| a stable code in every error                                              | AIP-193; Azure; Stripe                                        |
| the secret of a key only in the answer to create                          | what Tailscale, NetBird and Defined Networking do             |
| reject what is unknown in a request; ignore what is unknown in a response | Zalando rule 108                                              |
| what counts as a breaking change                                          | AIP-180                                                       |

**Where v0 departs from the common rule, and why:**

- **Lists are not paged.** AIP-158 says every list is paged from its first release, because paging cannot be added later without breaking clients. That holds when paging is on by default; here paging can only come as opt-in, so a client that does not ask keeps getting everything. See [Lists](#lists).
- **Actions are `/expire`, not `:expire`.** Google and Azure write `POST /nodes/12:expire`, while the Tailscale API, GitHub and Stripe write `POST /nodes/12/expire`. Both forms are in wide use, and v0 takes the one its users already know from the Tailscale API.
- **Time fields have no `At`.** Many guides write `createdAt`; v0 uses the words of the CLI, `created` and `expiry`.
- **One delete has a body.** [RFC 9110] allows a `200` with a body for a `DELETE`, and only the user delete uses it.

## Errors

Every error is a problem (`application/problem+json`, RFC 9457) with a `code`.

```
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://headscale.net/stable/ref/api/problems/#user_has_nodes",
  "title": "The user still owns nodes",
  "status": 409,
  "code": "user_has_nodes",
  "detail": "User 3 (alice) still owns 3 nodes.",
  "requestId": "hs1/Zx81kq-000042",
  "object": {"kind": "user", "id": "3", "name": "alice"},
  "details": {
    "nodes": [
      {"id": "12", "name": "mynode"},
      {"id": "15", "name": "laptop"},
      {"id": "16", "name": "phone"}
    ]
  }
}
```

| Member      | Meaning                                                                                                                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `code`      | a short, stable string. **This is what a program reads.** Changing a code is a breaking change.                                                                                                                                                                                                                |
| `type`      | a link to the documentation of this code                                                                                                                                                                                                                                                                       |
| `title`     | a short text, the same for every error with this code                                                                                                                                                                                                                                                          |
| `status`    | the HTTP status                                                                                                                                                                                                                                                                                                |
| `detail`    | a sentence for a person. It may change, and a program must not read it.                                                                                                                                                                                                                                        |
| `object`    | the resource the error is about: `{kind, id, name}`. `kind` is `node`, `user`, `authKey`, `apiKey`, `oauthClient` or `authRequest`. `name` is what a client shows for it: the `name` of a node, the `loginName` of a user, the `prefix` of a key. For `name_taken`, the one that has the name. `null` if none. |
| `requestId` | the ID of this request in the server log                                                                                                                                                                                                                                                                       |
| `errors`    | for `invalid_field`: one entry per field, `{location, message}`, for example `body.tags[2]`                                                                                                                                                                                                                    |
| `details`   | data for this code; the documentation of each code says what it holds.                                                                                                                                                                                                                                         |

**Rules:**

- An error never contains a database message or a Go error text, and it does not copy the request back. `details` holds only what the code documents.
- Every error a handler can return has a code; a `500` has the code `internal` and nothing more.
- Every operation names the problem schema and its codes in the OpenAPI document, so the generated client has `code` as a field.
- A path that does not exist and a method that is not allowed are problems too, not plain text.

| Status | Used for                                                              |
| ------ | --------------------------------------------------------------------- |
| 400    | a request that cannot be read: bad JSON                               |
| 401    | no credential, or one that is not valid                               |
| 403    | a valid credential that may not do this                               |
| 404    | the resource does not exist                                           |
| 405    | the path exists, the method does not                                  |
| 409    | the request is fine, but the state of the server forbids it           |
| 412    | `If-Match` did not match                                              |
| 413    | the body is too large                                                 |
| 415    | the body is not JSON                                                  |
| 422    | a field or a parameter is unknown, or has a value that is not allowed |
| 500    | a fault in the server                                                 |
| 503    | the server cannot answer now                                          |

**The codes of v0:**

| Code                     | Status | When                                                                                                  | `details`               |
| ------------------------ | ------ | ----------------------------------------------------------------------------------------------------- | ----------------------- |
| `unauthorized`           | 401    | no credential, or it is unknown, expired or revoked                                                   |                         |
| `forbidden`              | 403    | the credential may not do this: the token lacks the scope, or breaks a token rule                     | `scope`                 |
| `not_found`              | 404    | the resource does not exist, or no longer exists                                                      |                         |
| `invalid_request`        | 400    | bad JSON                                                                                              |                         |
| `method_not_allowed`     | 405    | the path exists, the method does not                                                                  |                         |
| `too_large`              | 413    | the body is over the limit of the operation                                                           |                         |
| `unsupported_media_type` | 415    | the body is not JSON                                                                                  |                         |
| `invalid_field`          | 422    | a field or parameter is unknown, or has a value that is not allowed; `errors` names each one          |                         |
| `empty_patch`            | 422    | a `PATCH` with no fields                                                                              |                         |
| `name_taken`             | 409    | the name belongs to another node or user; `object` is that one                                        |                         |
| `user_has_nodes`         | 409    | user delete without `withNodes`                                                                       | `nodes`                 |
| `nodes_changed`          | 409    | user delete with `expect`, when the user owns a node that is not in `expect`; `nodes` has those nodes | `nodes`                 |
| `user_managed_by_oidc`   | 409    | a change to a field the identity provider owns                                                        |                         |
| `owner_conflict`         | 422    | a key with both a user and tags, or with neither                                                      |                         |
| `tags_required`          | 422    | an empty tag list where one is needed                                                                 |                         |
| `tags_not_permitted`     | 422    | tags that are not in `tagOwners` of the policy                                                        | `tags`                  |
| `scope_requires_tags`    | 422    | an OAuth client with a scope that needs tags, and no tags                                             | `scopes`                |
| `invalid_scope`          | 422    | a scope that does not exist                                                                           | `scopes`                |
| `expiry_required`        | 422    | a key with no expiry                                                                                  |                         |
| `expiry_in_past`         | 422    | an expiry before now                                                                                  |                         |
| `auth_request_kind`      | 409    | `register` on an SSH check, or `approve` on a registration                                            | `kind`                  |
| `update_refused`         | 409    | the node did not start the update                                                                     | `reason`, `clientError` |
| `policy_invalid`         | 422    | the policy does not parse, does not validate, or fails its tests                                      | `errors`, `failedTests` |
| `policy_read_only`       | 409    | `PUT /policy` when the policy is a file                                                               | `path`                  |
| `precondition_failed`    | 412    | `If-Match` did not match the stored policy                                                            |                         |
| `unhealthy`              | 503    | `GET /health` when a check fails                                                                      | `reasons`               |
| `internal`               | 500    | a fault in the server; the server log has it                                                          |                         |

`update_refused` has a `reason` of `notConnected`, `updatesNotAllowed`, `clientRefused` or `timeout`; with `clientRefused`, `clientError` holds the text the Tailscale client sent.

`policy_invalid` has `errors`, one entry per problem in the policy, each `{message, line, column}`, where `line` and `column` are `null` when the problem has no place in the text. It also has `failedTests`, one entry per failed test, each `{index, src, dst, want, got}`: the position of the test in the policy, its source, the destination that failed, and the expected and the actual result (`accept` or `deny`).

## Authentication

**One header:** `Authorization: Bearer <credential>`. HTTP Basic stays in the Tailscale API only, where the Tailscale tools need it.

| Credential         | Looks like         | May do                                             |
| ------------------ | ------------------ | -------------------------------------------------- |
| API key            | `hskey-api-…`      | everything                                         |
| OAuth access token | `hskey-oauthtok-…` | what its scopes allow                              |
| the unix socket    | no credential      | everything; access to the socket is the credential |

- An access token comes from `POST /api/v2/oauth/token`, as it does today. The endpoint stays where the Tailscale tools expect it, and one OAuth client works on both APIs.
- **Scopes are the existing ones** (`hscontrol/scope`). v0 adds no scope names, and every operation states in the OpenAPI document which scope it needs.

| Operations                        | Scope to read        | Scope to write   |
| --------------------------------- | -------------------- | ---------------- |
| nodes, tags, auth requests        | `devices:core:read`  | `devices:core`   |
| `PUT /nodes/{id}/approved-routes` |                      | `devices:routes` |
| users                             | `users:read`         | `users`          |
| auth keys                         | `auth_keys:read`     | `auth_keys`      |
| OAuth clients                     | `oauth_keys:read`    | `oauth_keys`     |
| policy                            | `policy_file:read`   | `policy_file`    |
| API keys, config, debug           | `all:read`           | `all`            |
| `GET /whoami`, `GET /health`      | any valid credential |                  |
| `GET /version`                    | no credential        |                  |

- **A token is held to the rules of the Tailscale API**, and each of the following is answered with `forbidden`:
    - An auth key or an OAuth client made with a token gets only the tags the token has, or tags those tags own in the policy.
    - A new OAuth client gets no scope that the token lacks.
    - A token cannot make a key for a user (`userId`), and cannot register a node to a user.
    - A token cannot make an API key: an API key may do everything, so only an API key or the socket can make one.
    - `DELETE /users/{id}?withNodes=true` needs `devices:core` as well as `users`.
- The OpenAPI document and the docs page (`/api/headscale/v0/openapi.yaml`, `/api/headscale/v0/docs`) need no credential.

### Who am I

`GET /whoami` describes the credential of the request. A web UI uses it to check a key the user typed in and to know which key is its own; today some web UIs list every API key and search for their own prefix.

```
GET /whoami

{
  "kind": "apiKey",
  "id": "2",
  "prefix": "tr81ysk2m4xq",
  "owner": {"user": {"id": "4", "name": "bob", "loginName": "bob", "displayName": "", "email": ""}, "tags": []},
  "scopes": ["all"],
  "tags": [],
  "expiry": "2027-02-08T09:14:00Z"
}
```

`kind` is `apiKey`, `oauthToken` or `local` (the socket). For `local`, `id`, `prefix`, `owner` and `expiry` are `null`.

### CORS

Five of the web UIs run in the browser and call the API directly, which a browser allows only when the server sends CORS headers or when the web UI is served from the same address as Headscale. Headscale sends no such headers today, so these projects tell their users to do one or the other with a reverse proxy.

- A new configuration list names the origins that may call the API. It is empty by default, in which case nothing changes.
- There is no `*` default, because this is an admin API.
- For a listed origin the server answers preflight requests and allows `GET`, `POST`, `PUT`, `PATCH` and `DELETE` with the headers `Authorization`, `Content-Type` and `If-Match`. It exposes `ETag`, `Location`, `Headscale-Version`, `Deprecation`, `Sunset` and `Link`; without that, browser code cannot read the `ETag` of the policy.
- An error response carries the same headers. Without them the browser hides the problem and shows a network error.
- No cookies are used, so no credentials mode is needed.


```json
{
  "id": "12",
  "name": "mynode",
  "hostname": "ubuntu-vm",
  "fqdn": "mynode.example.com",
  "owner": {"user": {"id": "3", "name": "alice", "loginName": "alice", "displayName": "Alice", "email": ""}, "tags": []},
  "ipAddresses": ["100.64.0.1", "fd7a:115c:a1e0::1"],
  "online": true,
  "lastSeen": "2026-11-10T09:14:00Z",
  "expiry": "2027-02-07T10:00:00Z",
  "expired": false,
  "created": "2026-07-13T08:02:00Z",

  "os": "linux",
  "approvedRoutes": ["10.0.0.0/8"],

```

| Field             | Notes                                                                                                                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`            | The name in Headscale, which can be changed. The legacy API calls it `givenName`.                                                                                                  |
| `hostname`        | What the node reports; read-only. The legacy API calls it `name`.                                                                                                                  |
| `fqdn`            | `name` and the base domain, without a trailing dot, or `""` when no base domain is set. Headplane reads the configuration file today to build it.                                  |
| `owner`           | One user, or tags. For a tagged node `user` is `null`. There is no made-up `tagged-devices` user.                                                                                  |
| `ipAddresses`     | IPv4 first.                                                                                                                                                                        |
| `online`          | Connected, or gone for less than the grace period.                                                                                                                                 |
| `lastSeen`        | The current time while the node is online. `null` if it never connected.                                                                                                           |
| `expiry`          | `null` means the node never expires.                                                                                                                                               |
| `expired`         | `true` when `expiry` has passed, by the server's clock.                                                                                                                            |
| `clientVersion`   | The short version of the Tailscale client, `1.82.0`. `""` when unknown.                                                                                                            |
| `os`              | `linux`, `windows`, `macOS`, … as the node reports it. `""` when unknown.                                                                                                          |
| `approvedRoutes`  | Routes an admin or the policy approved.                                                                                                                                            |
| `availableRoutes` | Routes the node offers.                                                                                                                                                            |
| `servingRoutes`   | Routes the node currently serves to others: approved, offered, and with this node chosen to serve them. Exit routes are included, and the field has one meaning in every response. |
| `registerMethod`  | `authKey`, `cli` or `oidc`.                                                                                                                                                        |
| `authKeyId`       | The ID of the auth key the node joined with, or `null`. Only the ID, not the key.                                                                                                  |
| `attributes`      | Node attributes, a map from name to value.                                                                                                                                         |

**Filters:** `user` (a user ID; tagged nodes never match) and `tag` (nodes that have this tag).

**Update.** `name` and `expiry` can be changed.

- `expiry` takes a time in the future, `null` for "never", or the word `"now"`, which the server replaces with its own clock. A time in the past is `expiry_in_past`. Because of `"now"`, a client can rename a node and expire it in one request, and either both happen or neither does.
- A `name` that another node has is `name_taken`, with that node as `object`.
- A `name` that is not a valid DNS label is `invalid_field`, as today. The Tailscale API answered `200` to such a name (`probe-J`, J5); what it stored was not recorded.
- An empty `name` resets the name to the one made from the node's hostname. This is the way to undo a rename, and the Tailscale API does the same.

**Expire.** `POST /nodes/{id}/expire` sets the expiry to the server's "now", and the node must log in again. It does the same as `"expiry": "now"` in a `PATCH` and stays as the plain call for the common case.

**Update the client.** `POST /nodes/{id}/update-client` asks the node to update its Tailscale client and answers with the node. When the node does not start the update, the error is `update_refused`, which says why; the Tailscale API can only say "not found" here (not captured).

**Set tags.** `PUT /nodes/{id}/tags` replaces the tags of the node.

- A user-owned node becomes a tagged node: its owner changes from the user to the tags, and the API cannot undo this.
- An empty list is `tags_required`. The API cannot turn a tagged node back into a user-owned one; the node does that itself by logging in again as a user, as [the tags documentation](../ref/tags.md) describes.
- Every tag must be in the policy's `tagOwners`, or the answer is `tags_not_permitted`.

**Set approved routes.** `PUT /nodes/{id}/approved-routes` replaces the approved routes, and `[]` removes them all. The list replaces everything, including the routes the policy approved on its own. A route that the node does not offer is stored too, as today and as in the Tailscale API; it takes effect when the node offers it.

One exit prefix approves both `0.0.0.0/0` and `::/0`, and the response reports both. This differs from the Tailscale API on purpose: there, one of the two is stored alone, other nodes then receive neither route, and the node does not work as an exit node (see [Checked against the Tailscale API](#checked-against-the-tailscale-api)).

**Why tags and routes are not `PATCH` fields.** Setting tags changes the owner, and approving routes needs a different scope (`devices:routes`) from changing a name. Each is one clear operation with its own rules, and each matches one CLI command.

```
GET    /users                          ?name=<name> &email=<email>
GET    /users/{id}
POST   /users
PATCH  /users/{id}                     name, displayName, email, pictureUrl
DELETE /users/{id}                     ?withNodes=true &dryRun=true &expect=<id>,<id>
```

```json
{
  "id": "3",
  "name": "alice",
  "loginName": "alice",
  "displayName": "Alice",
  "email": "",
  "pictureUrl": "",
  "provider": "local",
  "providerId": "",
  "nodeCount": 3,
  "nodes": [
    {"id": "12", "name": "mynode"},
    {"id": "15", "name": "laptop"},
    {"id": "16", "name": "phone"}
  ],
  "created": "2026-07-01T10:00:00Z"
}
```

| Field        | Notes                                                                                                                                                            |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`       | The stored username. Unlike in the legacy API, it is not replaced by the email when it is empty.                                                                 |
| `loginName`  | What Headscale shows for the user: the email, else the username, else the provider identifier. Read-only. The Tailscale API has the same field. Clients show it. |
| `provider`   | `local` or `oidc`, never `""`.                                                                                                                                   |
| `pictureUrl` | One name in both directions; the legacy API uses `pictureUrl` in the request and `profilePicUrl` in the response.                                                |
| `nodeCount`  | Nodes this user owns, not counting tagged nodes. Several web UIs compute this today from the full node list.                                                     |
| `nodes`      | The same nodes, as references.                                                                                                                                   |

**Filters:** `name` and `email`, exact, alone or together. A username is unique only among local users; a user from OIDC can have the name of another user ([#3429]). So `?name=alice` can return more than one user.

**Create.** `name` is required. The server validates the username and checks that `email` is an email address and that `pictureUrl` is an absolute `http` or `https` URL. A name that another local user has is `name_taken`.

**Update.** Any of the four fields, with the same checks as in a create. A user from OIDC cannot be changed, because the identity provider owns those fields (`user_managed_by_oidc`).

**Delete.**

```
DELETE /users/3?withNodes=true

200 OK
{"nodes": [{"id": "12", "name": "mynode"}, {"id": "15", "name": "laptop"}, {"id": "16", "name": "phone"}],
 "authKeyCount": 2,
 "apiKeyCount": 0}
```

- The delete removes the user and the auth keys and API keys the user owns, but not the tagged keys the user created. Today the API keys stay behind, without an owner.
- A user that owns nodes is not deleted (`user_has_nodes`, with the nodes) unless `withNodes=true` is given, in which case the nodes are deleted too.
- It is one operation: all of it happens, or none of it.
- The response reports what was removed; this is the only delete that has a body.
- `dryRun=true` gives the same response and removes nothing, and a client shows it to the admin before it asks "are you sure?".
- `expect` takes the node IDs the client showed. When the user owns a node that is not in the list, because one registered in between, the delete is refused with `nodes_changed`, which names the new nodes, and removes nothing. A node from the list that is gone by then does not stop the delete. Without `expect` the delete removes what the user owns at that moment.

| Field       | Notes                                                                                                                                                                |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `owner`     | The user, or the tags, that nodes joining with this key get. For a tagged key `user` is `null`.                                                                      |
| `createdBy` | The user that owns the credential that made the key, or `null`. The server sets it, and it is not the owner.                                                         |
| `used`      | `true` when a node has joined with the key.                                                                                                                          |
| `state`     | `valid`, `used`, `expired` or `revoked`. `revoked` wins over `used`, which wins over `expired`. `used` means used and not reusable.                                  |
| `revoked`   | When the key was revoked, or `null`.                                                                                                                                 |

- **The list has every key**, including revoked ones, until the server removes them. No list in the legacy API or the Tailscale API returns a revoked key.
- **Create** takes exactly one of `userId` and `tags` (`owner_conflict`), plus `reusable`, `ephemeral`, `expiry` and `description`. `expiry` is required (`expiry_required`) and has no upper limit; the Tailscale API caps it at 90 days. Every tag must be in the policy's `tagOwners`, or the answer is `tags_not_permitted`, as it is on Tailscale (captured with an admin API key). The response is the key, with the secret in `key`.
- **Delete** revokes the key: it can no longer register a node, and it stays in the list as `revoked` until the server removes it. Nodes that joined with it stay. See [How a credential ends](#how-a-credential-ends).
- **Filters:** `user` and `tag` match the owner, not `createdBy`.

The legacy API has "expire" (which sets the expiry to now) and "delete" (which sometimes deletes and sometimes revokes). v0 has one operation, and it always does the same thing.

### Auth requests

A node that wants to join without an auth key, or a user who must confirm an SSH session, waits for an answer. The auth ID is part of the URL the node shows.

```
GET    /auth-requests/{id}
POST   /auth-requests/{id}/register    {"userId": "3"}
POST   /auth-requests/{id}/approve
POST   /auth-requests/{id}/reject
```

```json
{"id": "hskey-authreq-…", "kind": "registration", "hostname": "newlaptop", "source": null, "destination": null}
```

- `kind` is `registration` or `sshCheck`.
- A registration has the `hostname` the node reports; an SSH check has `source` and `destination`, the two nodes, as references.
- **There is no list.** An auth ID is a secret that the node hands to one person: whoever has the ID may see and answer the request, and nobody can browse for one.
- **Register** answers a registration, creates the node for the user and returns the new node. It takes a user ID, where the legacy API takes a username, which can match two users.
- **Approve** answers an SSH check and **Reject** answers either kind; both answer `204`.
- A request that timed out is gone, as is one that was answered, and both are `not_found`.
- The wrong action for the kind is `auth_request_kind`. Today "approve" on a registration reports success, and the node has to start again.

### Policy

```
GET    /policy
PUT    /policy                         ?dryRun=true      If-Match: "<etag>"
POST   /policy/reload
```

```json
{
  "policy": "{\n  // comments are kept\n  \"acls\": [ … ]\n}",
  "updated": "2026-11-09T16:40:00Z",
  "mode": "database",
  "path": ""
}
```

- `policy` is the text exactly as it is stored: HuJSON, with its comments.
- `mode` is `database` or `file`; in file mode `path` is the file and `updated` is `null`.
- **No policy is not an error.** When nothing is stored, `policy` is `""`; the legacy API answers `500` here.

**Set.** `PUT /policy` with `{"policy": "…"}`.

- The server parses the policy, checks it against the users and nodes it has, and runs the tests in it. A failure is `policy_invalid`, with every error and every failed test in `details`.
- In file mode the answer is `policy_read_only`, with the path.
- `dryRun=true` runs all of that and stores nothing. It works in file mode too, so a tool can check a policy before writing the file.

**No lost updates.** `GET /policy` sends an `ETag` header, and a client that sends it back as `If-Match` on `PUT` gets a `412` (`precondition_failed`) when someone else changed the policy in between. The header is optional: a script that only writes a file works without it. Every web UI that edits the policy today reads all of it, changes it and writes all of it back, with nothing to stop two admins from overwriting each other.

**The policy file is watched.** In file mode the server reloads the policy when the file is saved, as it does for the extra-records file, so nobody has to send a signal. An invalid file leaves the old policy in place, and the log says why.

**Reload.** `POST /policy/reload` reads the policy again from where it is stored, the file or the database, and applies it. It is the policy part of what `SIGHUP` does today, with one difference: the caller gets the result, either the policy or `policy_invalid`. A tool that writes the policy file can call it to learn at once whether the file was accepted. `SIGHUP` stays; it also reloads the TLS certificate.

## The CLI and the API

[001](001-cli.md) and this proposal are designed together, and this section holds the parts of that agreement that shape the API. How the CLI presents what it receives (tables, columns, filters, prompts and messages) belongs to 001.

### One client

The CLI calls only v0, through the generated client in `gen/client/headscale/v0`, and calls neither the legacy API nor the Tailscale API. An earlier draft of 001 preferred v2 and extended v1; that rule is gone.

### `--output json` is the API object

An earlier draft of 001 defined its own JSON for `--output json`, because no single API object held everything the CLI shows and the CLI had to join two calls. v0 removes that reason: the CLI prints the v0 object as the server sent it, and for a list it prints the array without the object around it.

This makes the shape of a v0 object part of the CLI's user experience, which is why v0 keeps its fields flat, uses the words of the CLI (`name`, `hostname`, `owner`, `expiry`, `created`) and computes on the server what the CLI shows. In return, the same keys appear in `headscale nodes list -o json` and in `curl`, the CLI is a working example for web UI authors, and the OpenAPI document is the single field reference.

The cost is that a change to v0 is also a change to the CLI's JSON, which 001 already says matches the binary that printed it and can change in any release.

### Finding a target

The CLI turns a target such as `mynode`, `12` or `100.64.0.1` into one resource by listing the collection and matching on the client. Over the socket that is one cheap call.

The API does not take over the CLI's matching rules, because they would become part of the API contract and every change to them an API change. A `match` parameter can be added later without breaking anything.

### Version check

v0 may change between releases, and the CLI can talk to a server on another machine. Without a check, a CLI and a server of different versions would not fail: the generated client drops fields it does not know and fills missing ones with zero, so every node would look offline.

- Every v0 answer has the header `Headscale-Version`. Its value is the version of the server, the same text as `version` in `GET /version`, such as `0.30.1`. A development build sends `dev`.
- A server that has no v0 answers `404` without the header.

With these two facts the CLI can detect a server that is too old or too new before it reads a body; what it does then is described in 001. A command whose first call would be a write calls `GET /version` first, so that no write happens, and no new secret is lost, when the versions differ.

### What changes for every project that moves

- **Status codes.** Creates answer `201` and deletes `204`, but HeadControl and Headscale Manager count only `200` as success.
- **Error bodies.** `code` is a string and the text is `detail`. Most REST projects read `message`, and headscale-admin reads `code` as a number.
- **Enums.** `REGISTER_METHOD_CLI` becomes `cli`, and headscale-piying filters on the old names.
- **Keys need an expiry.** Today Headplane can send a create request without one.
- **A tagged auth key has no user in the request.** `userId` and `tags` together are `owner_conflict`, and the server sets `createdBy` from the credential.
- **The proxy recipes.** The CORS examples of headscale-ui and Headscale UI do not allow `PATCH`, and the headscale-ui one does not allow `PUT` either; v0 uses both.
- **The `Deprecation` and `Sunset` headers** of the legacy API cannot be read by a browser project that goes through a proxy recipe, because the recipes the projects document do not expose them.

### What v0 does not solve for them

- **Server configuration and restart**, for Headplane, Headscale Panel and unraid-headscale-admin. `GET /config` gives a read-only copy as YAML with secrets removed; whether it holds what these projects read was not checked.
- **Host information.** Headplane runs an agent for the OS version, the client version and the SSH host keys. v0 has `os` and `clientVersion`; the OS version and the SSH host keys stay with the agent.
- **Permissions.** Headplane, ouroboros and Headscale Panel check ownership themselves, and `GET /whoami` is the first part of what they would need.
- **Moving a node between users.** headscale-ui and Headscale Manager still offer it.
- **The name of a user in the policy.** headscale-admin, Headscale UI and Headplane add `@` to a username by hand, and v0 gives no such text. `loginName` is close, but it has no `@` for a plain username; this is an [open question](#open-questions).
- **CLI output.** ouroboros and the local mode of unraid-headscale-admin parse `headscale -o json`. Since `--output json` becomes the v0 object, both break. The local mode of unraid-headscale-admin never used gRPC.
- **Browser node login.** headscale-console, and Headplane for browser SSH, ask for CORS headers on Headscale for the node login traffic. The CORS list here covers the API paths, and whether it should reach those paths too is an [open question](#open-questions).

### Expire, and key expiry that is disabled

One capture is not settled, and it is behind the open question on tagged nodes.

On Tailscale a node that joins as tagged has key expiry disabled. `POST /device/{id}/expire` then answers `200` and sets `expires` to now, but the node keeps running; it was watched for 60 seconds. A user-owned node with key expiry disabled behaves the same. Only when a second call enables key expiry does the node need a login, and it then needs it at once.

| Device                           | Call              | Answer | Node afterwards           |
| -------------------------------- | ----------------- | ------ | ------------------------- |
| user-owned, key expiry enabled   | expire            | 200    | needs a login within 15 s |
| tagged, key expiry disabled      | expire            | 200    | still running after 60 s  |
| user-owned, key expiry disabled  | expire            | 200    | still running after 30 s  |
| the tagged one, after the expire | enable key expiry | 200    | needs a login within 12 s |

We think this may be wrong in Tailscale, for four reasons:

1. Tailscale's own description of the call says it "will require the device to re-authenticate in order to connect to the tailnet". With key expiry disabled it does not.
1. The call answers `200` although it had no effect, so an admin who expires a compromised server believes it is cut off.
1. The device afterwards shows `expires` in the past while it is connected, with key expiry disabled.
1. The expire takes effect later, when somebody enables key expiry for another reason.

It may also be intended: "key expiry disabled" could mean that `expires` is ignored, and the call only writes `expires`.

Headscale stores one field, an expiry time or none, so its expire logs out every node, tagged or not, in the Tailscale API as well. Whether Headscale should copy Tailscale here is [open](#open-questions).

No recording exists for these two; they were found by reading the code of 0.29 and of the web UIs.

## Versioning and deprecation

### What v0 promises

- v0 may change in any release, including in ways that break clients.
- Every breaking change is listed in `CHANGELOG.md` under the heading "API v0"; nothing changes without a note.
- Where practical, an operation or a field is marked as deprecated for one release before it is removed.
- The OpenAPI document has the version of the server that made it.

**A breaking change is:** removing or renaming an operation, a field, an enum value in a request or an error code; changing the type of a field; a new required field in a request; a new default; a narrower set of accepted values.

**Not a breaking change:** a new operation; a new optional field or query parameter in a request; a new field in a response; a new enum value in a response; a new error code on a new condition. Clients must be written to accept these.

### From v0 to v1

Once the shape has not changed for a while and the CLI and the web UIs have used it, v0 becomes `/api/headscale/v1`. From then on a breaking change needs `/api/headscale/v2`, and `/api/headscale/v0` keeps answering for one more release.

### The end of the legacy API

| Release | Legacy API `/api/v1`                                                                         |
| ------- | -------------------------------------------------------------------------------------------- |
| 0.30    | works as before; every operation is marked deprecated and every response carries the headers |
| 0.31    | removed                                                                                      |

v0 ships in 0.30, and the legacy API is removed one release later. A web UI therefore has one release in which both APIs answer. v0 may still change after that, and every such change is announced; see [What v0 promises](#what-v0-promises).

- In the OpenAPI document of the legacy API every operation has `deprecated: true`, so the docs page shows it.
- Every legacy API response carries the headers `Deprecation` (RFC 9745) and `Sunset` (RFC 8594), and a `Link` to the migration guide. A web UI with its own server can show a warning from these, while a web UI in the browser can read them only when its proxy exposes them.
- The server logs a warning the first time the legacy API is used after each start.
- `docs/ref/api.md` gets a migration guide: the table in [Coverage of v1](#coverage-of-v1), with examples.

## Not in this proposal

**Changing the server configuration through the API.** Headplane and Headscale Panel edit `config.yaml` and then restart Headscale through Docker, Kubernetes or a signal; they also edit the extra-records file. The need is real, but it is a design of its own: which keys can change while the server runs, how a change is validated, and where it is stored when the configuration file is read-only. v0 has `GET /config` and `POST /policy/reload`, and no path under `/config` is used for anything else, so writes can be added there.

**Permissions for a user.** An API key may do everything. Headplane keeps its own database with roles on top of that, and ouroboros and Headscale Panel check ownership themselves. A permission model in Headscale (a key that can only see its owner's nodes, roles) would remove that work and that risk, but it is a large design. v0 has OAuth scopes, the `owner` of an API key and `GET /whoami`, which are the parts such a model would build on.

**Events.** Several web UIs fetch the full node list every 5 to 30 seconds, where a stream of changes would be better. It is left out for now for two reasons: a browser's `EventSource` cannot send an `Authorization` header, so the usual way to do it does not work with a bearer token; and the server has a 30-second write timeout that a stream must get around. A later `GET /events` can send the same node and user objects that the lists return.

**More about a node.** Headplane runs its own agent on the tailnet to learn the OS version and the SSH host keys of a node. v0 has `os` and `clientVersion`; the rest of what a node reports about itself can be added field by field when a client asks for it.

**Paging, sorting and a filter language.** See [Lists](#lists).

**Update available.** The server does not know the newest Tailscale version, so the Tailscale API field `updateAvailable` is always `false` in Headscale. A node in v0 has `clientVersion` and no `updateAvailable`; adding it would mean the server fetching a version list from the internet.

**Statistics.** Traffic counters and uptime history, which Headscale does not record.

**Device approval ([#2176]).** The field `authorized` on a node and the actions for it are reserved, as in 001.

**Changing the owner of a node to a user.** The API cannot turn a tagged node back into a user-owned one, and a node cannot move between users. If that is added, it is a new operation next to `PUT /nodes/{id}/tags`.

**The token endpoint.** `POST /api/v2/oauth/token` stays in the Tailscale API, and v0 accepts the tokens it issues.

## Open questions

1. **Expiry of a tagged node.** Headscale logs out every node that is expired. Tailscale was captured ignoring an expire while key expiry is disabled, which is the normal state of a node that joined as tagged; see [Expire, and key expiry that is disabled](#expire-and-key-expiry-that-is-disabled). We are not sure that Tailscale's behaviour is right, and we are not sure that Headscale should differ. Until this is decided, v0 does what Headscale does today. If v0 refuses instead, the code is `expiry_not_allowed`.

1. **The policy as a raw body.** `PUT /policy` takes JSON with the policy as a string, which with `curl` needs `jq -Rs '{policy: .}'`. Accepting `Content-Type: application/hujson` with the file as the body would be simpler by hand, at the cost of a second method in the generated client. The Tailscale API takes the file as the body (from its documentation; not captured).

1. **The name of the CORS config key**, and whether it lists origins for all three APIs or only for v0. Two projects also ask for CORS on the node login paths, for a Tailscale client running in the browser.

1. **Who made a tagged node?** A tagged node has no user, but the server still knows which user registered it, and Headscale Manager guesses that person from the name of the tag. A `createdBy` on the node, as on an auth key, would answer this. The Tailscale API shows a user in the `user` field of a tagged device. The recording cannot tell whether that is the user who registered the node or the user who made the auth key.

1. **The name of the retention setting.** `preauth_keys.revoked_retention` now covers API keys and OAuth clients too.

1. **The name of a user in a policy.** Three web UIs add `@` to a username by hand to write a policy. `loginName` is the email, or the plain username without `@`. A read-only field with the exact text for a policy would end the guessing.

## Implementation notes

**Where it goes.**

- The package is `hscontrol/api/headscale/v0`, so the folders match the paths (`api/v1`, `api/v2`, `api/headscale/v0`) and nothing is renamed.
- The generated client is `gen/client/headscale/v0`, from `make client`.
- The API is added in four places in `hscontrol/app.go`: where the Huma APIs are built in `Serve`, in `HTTPHandler()`, in `createRouter`, and in the mux of the unix socket, before the catch-all that sends everything to the legacy API.
- The unix socket serves v0 with local trust, as it serves the other two.
- v0 is written clean, directly on the state layer. Shared code is welcome: where it is cheap, a legacy handler becomes a thin layer that calls the same code as v0 and maps the result to the old shape. That is a bonus, not a goal, because the legacy API goes away.

**Before the legacy API is frozen.** Two places in `/api/v1` differ from 0.29 in the tree today and should be fixed before the release; see [Found outside this proposal](#found-outside-this-proposal).

**Order of work.**

1. The empty API: package, wiring, OpenAPI and docs paths, client generation, the problem type, the auth middleware.
1. Read operations, with the full objects.
1. Writes.
1. The CLI moves to the new client, command by command; this is the work of 001.
1. The legacy API gets its deprecation marks and headers.

**Rules for the Huma code.** Each was checked against Huma v2.40.0.

- **Register every operation with `huma.Register` and an explicit `OperationID`** (`listNodes`, `getNode`, `updateNode`). The short helpers build the ID from the full path, and the client method becomes `ListApiHeadscaleV0Nodes`.
- **Do not use `autopatch`.** Under a path prefix it documents the `PATCH` route but answers `405` on it, so write `PATCH` by hand.
- **`PATCH` fields use a small `Optional[T]` type**, not a Go pointer. With a pointer, a field that was left out and a field that is `null` look the same, and "clear the expiry" becomes "leave the expiry".
- **Do not change a package-level setting of Huma** (`huma.NewError`, `huma.DefaultArrayNullable`, `huma.ValidateStrictCasing`). All three APIs run in one process, and the setting would change the other two as well. Use field tags and v0's own types instead.
- **The problem type is v0's own**, with `code`, `object` and `details`. Validation errors that Huma produces itself are converted to it by a transformer on the v0 API. The `value` member of Huma's errors is dropped, because for an unknown field it holds the whole request body. Each operation declares this type as its error schema, and the router's own responses for an unknown path and a wrong method are replaced, because they are plain text.
- **Every handler error goes through one mapping function.** An error that is not mapped becomes `internal`, without its text.
- **Set `RejectUnknownQueryParameters`.** It is off by default; once set, Huma answers `422` for such a parameter.
- **Mark every list field `nullable:"false"`, and return an empty slice, never `nil`.** The tag only changes the schema, so a test checks that no response has `null` for a list.
- **The `ETag` of the policy is compared by hand**: a strong hash of the stored bytes, in quotes. Huma's helper for `If-Match` answers `412` to `If-Match: *`.
- **Generate the client from the OpenAPI 3.1 document**, with `nullable-type: true`. oapi-codegen reads 3.1 since v2.8.0, so the step down to 3.0 that the other two clients use is not needed. Without `nullable-type` the client cannot send `null`.
- **Read through the view types** (`NodeView`, `UserView`), never `AsStruct()`, as `AGENTS.md` says.

**Server work behind the API.** Most operations call existing code; these need new code in `hscontrol/state` or `hscontrol/db`:

- a user delete that removes the nodes and the API keys in one database transaction, and a dry run of it; the in-memory node store and the messages to the other nodes follow the commit
- a user update for display name, email and picture, with the OIDC check that only the rename has today
- an owner for an API key at create (`State.SetAPIKeyUser` exists and only tests call it)
- the list of auth keys with revoked keys and their state
- a soft delete for API keys and OAuth clients, and the hourly job extended from auth keys to all three; an OAuth client's tokens are refused from the moment it is revoked
- the delete of an auth key always revokes; the special case for an ephemeral key that a node still uses goes away
- the check of tags against the policy when an auth key is made
- `loginName` on a user
- a node name that resets to the one made from the hostname
- the `expect` check in the user delete
- the list of tags from the policy
- a watch on the policy file
- the reason a node refused an update, which is only in the log today
- reading one auth request
- recording when an API key is used; nothing writes `lastUsed` today
- errors with a type from the policy reload, which only logs today
- a node update that changes name and expiry together, or neither
- the checks on a new user: username, email, picture URL
- the token rules in [Authentication](#authentication) that the Tailscale API does not need

**Tests.**

- Each operation has a test in the package with `humatest`: the request, the status, the body.
- `hscontrol/servertest` runs the generated client against a real server.
- One test fails when an operation has no scope, no error codes or no explicit operation ID, in the way `hscontrol/api/v2/guard_test.go` does for the Tailscale API.
- One test fails when `hscontrol/api` calls `AsStruct()`.
- The OpenAPI document is checked in, so a change to it shows in review, and CI fails when it is stale.
