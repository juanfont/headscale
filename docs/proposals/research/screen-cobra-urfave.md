## Screen card: spf13/cobra + spf13/pflag

### Takeaway

Cobra is maintained but slowly: 12 commits and 1 release (v1.10.2, 2025-12-04) in the last 12 months, and nothing tagged for 11 months. Pflag came back to life (v1.0.6-v1.0.10 in 2025, v1.1.0 on 2026-11-06). No v2 is planned that I could find. Completion is the strongest of the pair; it is the benchmark.

### Using cobra only for parsing and completion

- The default `help` command and `-h` flag, `Usage`/`Short`/`Long` fields and templates are optional layers. `SetHelpFunc` plus `SetUsageFunc` replace output entirely; `DisableAutoGenTag`, `CompletionOptions{DisableDefaultCmd}` let us ship our own `completion` command. So "cobra as parser + completer" works and is what headscale does. Cost: cobra still owns error printing/usage-on-error behaviour unless `SilenceUsage`/`SilenceErrors` are set. Source: [command.go](https://github.com/spf13/cobra/blob/main/command.go). Completion descriptions come from `Short`, so specs must feed that field even if help is ours. (Inference from API; not built here.)

### Inferences

- Cobra is the safe default: three-level trees, runtime-built, full help override and dynamic completion all work today. Its weakness is velocity, not capability: release gap of 11 months, big open backlog, no v2 and no structural progress on the long-standing issues.
- Pflag revival lowers the "frozen dependency" worry, but cobra has not yet adopted v1.1.0; pflag 1.1.0 is fresh (11 days old), expect follow-up fixes.
- Flags after args work out of the box in cobra/pflag (interspersed), matching what a CLI users expect.

### Gaps

- Binary size cost not measured. Indirect module count not computed from `go mod graph`.
- Exact 12-month release count for pflag is from the releases list only (6 releases, one since 2025-11).

### Inferences

- urfave/cli v3 matches the card on every must-have except dynamic *value* completion, which looks thinner than cobra's (hook per command, not per flag, no directives). Needs a deep check if it advances.
- Much stronger maintenance and smaller dependency list than cobra; the cost is a higher Go floor and a framework that wants to own flag types, `Sources`, and help templates, where Headscale wants only parsing.
- Migration cost from cobra is a full rewrite of the adapter (the one file that imports the framework), small if 001's spec layer holds.

### Gaps

- Per-flag completion hook, completion descriptions, notable users, maintainer count, issue list of pain points, binary size: not checked.

## Open questions for the maintainer

1. Does dynamic completion of values from the server (node names, users) have to match cobra's quality (per-flag functions, descriptions, no-file directives)?
    - Yes, required: only cobra clearly qualifies today; urfave needs deep verification. Cost: a short list.
    - Static + hand-written completion scripts are acceptable: opens the whole field. Cost: worse UX for `nodes ... <id>`.
1. How much does a framework with fast-moving minors (urfave v3.x behavior fixes monthly) vs a slow one (cobra) matter to you?
    - Prefer slow and stable (cobra): fewer surprises, but bugs wait. Cost: backlog stays.
    - Prefer active (urfave): fixes land, but pinning and re-checking each bump. Cost: churn in the adapter.
