What this means: the CLI uses a small, plain core of cobra: command literals, `RunE`, local
string/uint/bool flags, aliases, a few persistent flags, `MarkFlagRequired`, `NoArgs`, and the
auto-generated `help`/`completion`. No completion functions, no templates, no custom flag types.
Everything 001 wants beyond that is own code on top.

### What a replacement framework must match (user-visible)

From the table plus `integration/` (section 5): `--flag value`, `--flag=value`, `-o json`,
`-o=json` (today `hasMachineOutputFlag` at `utils.go:396` only sees bare `json`, 001 fixes),
short letters (`-u -i -o -c -f -e`), `[]string` flags both as comma list (`StringSlice`, tags/routes) and
repeated (`StringArray`, `oauth_client.go:58`), uint64 flags, bool `--force`/`--reusable`, required flags,
flags after positional args (`users create NAME --display-name x`), nested commands up to 3 levels
(`nodes routes ...` in 001; today 2). Plus the completion scripts (section 5).

**Viper is gone from upstream/main.**

- PR juanfont/headscale#3674 "types: replace viper with koanf": **MERGED 2026-11-11T14:02:17Z**,
  author kradalby, +5233/-2708, 77 files, review APPROVED (https://github.com/juanfont/headscale/pull/3674).
  Commit `3e12fa9d3 types: remove viper`, then `890adee7f types: decode configuration strictly` (2026-11-11).
  The BRIEF says "being removed" and 001 l.3313 lists #3674 as `open`: both are stale. #3670 (base) is merged too.

  `knadh/koanf/v2 v2.4.1` (+ `parsers/json`, `parsers/yaml`, `providers/confmap`), no `spf13/viper`.
  `go-viper/mapstructure/v2` remains (different module, used by `hscontrol/config/load.go:22`, `hscontrol/dns/provider.go:17`).
  The worktree's `go.mod` still has `spf13/viper v1.21.0` (50) because it is on the old base.
- Modules that left with viper (diff of worktree vs upstream go.mod): `spf13/viper`, `spf13/afero`,
  `spf13/cast`, `sagikazarmark/locafero`, `subosito/gotenv`, `pelletier/go-toml/v2`. Added: koanf (5 modules), `mitchellh/copystructure`, `mitchellh/reflectwalk`.
- Viper in the CLI, old base: `viper.GetString("log.format")` and `viper.GetBool("disable_check_updates")`
  (`root.go:67,72`), `viper.WriteConfigAs` (`dump_config.go:19`). **No `viper.BindPFlag`, `BindEnv`, `BindPFlags` anywhere**
  (grep over cmd/, hscontrol/ in worktree and `git grep` on upstream/main). Viper never saw a flag; the only
  link was `viper.SetEnvPrefix("HEADSCALE")` + `viper.AutomaticEnv()` in `hscontrol/types/config.go:585-587` (gone upstream).
- Upstream/main CLI today: `root.go:36` `cobra.OnInitialize(initConfig)`; `initConfig` calls `loadConfig("")` →
  `config.Load(path, path != "", os.Environ())` (`root.go:72-75`), path = `cmp.Or(path, cfgFile, os.Getenv("HEADSCALE_CONFIG"))`.
  So `-c` is a cobra flag bound to a Go variable (`StringVarP(&cfgFile,...)`), `HEADSCALE_CONFIG` is read by hand,
  and the environment is handed to koanf as a `[]string`. The framework takes no part.

What a new framework must do for config and env (001 "### Configuration and environment", l.1987):

- Nothing automatic. No env-to-flag binding is wanted: 001 says "No other flag has an environment variable"
  and no `HEADSCALE_OUTPUT`/`HEADSCALE_FORCE`.
- Provide the `-c/--config` flag (string) and run the config loader once before `Run` (cobra: `OnInitialize`; in 001 the builder does it).
- `HEADSCALE_CONFIG`, `HEADSCALE_UNIX_SOCKET`, `HEADSCALE_CLI_ADDRESS`, `HEADSCALE_CLI_API_KEY`, `HEADSCALE_CLI_TIMEOUT`,
  `HEADSCALE_CLI_INSECURE` are read by Headscale (`os.Getenv` / koanf), not by cobra. `NO_COLOR` in `cmd/headscale/headscale.go`.
- A framework with its own env-var layer (ff, kong, urfave) is not needed and must not read `HEADSCALE_*` by itself:
  koanf rejects unknown keys from the file, and unknown `HEADSCALE_*` variables only warn (3674 body), so a second env reader
  would double-handle them.

How it reads against cobra: flags are struct tags on a plain config struct, e.g.
`TestPattern string \`flag:"test,Test pattern to run"\``, `Timeout time.Duration \`flag:"timeout,default=120m,Test timeout"\`` (`cmd/hi/run.go:21-36`). Commands are a nested literal tree of `\*command.C`, built at program start; handlers get `\*command.Env`(args via`env.Args`, context via `env.Context()`). Defaults live in the tag, so there is no `StringP("x","y","","...")`+`Get`pair and no stringly-typed`cmd.Flags().GetString("user")`lookup (54 of those in the Headscale CLI). No short flags are used in these three tools (UNVERIFIED that flax supports them; it is struct-tag only, so the tag must carry them). Tools are small (max 2 levels, no aliases, no completion, no flags after positional args relied on); none has been stress-tested for the Headscale surface.`hi`has no`--output\`, no required flags, no aliases.

`ff/v3` is pulled by Tailscale, not by Headscale code:
`go mod why -m github.com/peterbourgon/ff/v3` → `tailscale.com/cmd/tailscale` → `tailscale.com/cmd/tailscale/cli` →
`github.com/peterbourgon/ff/v3/ffcli`. `go mod graph`: `tailscale.com@v1.105.0-pre... github.com/peterbourgon/ff/v3@v3.4.0`.
Headscale never imports it. Tailscale's CLI is the model for the Tailscale-style `ffcli` that 001's authors know.

Who else requires cobra/pflag/viper in the module graph (so removal is not free of other users): cobra ← `tailscale.com`,
`danielgtaylor/huma/v2 v2.40.0`, `bradfitz/monogok`; pflag ← the same plus `k8s.io/client-go`, viper, cobra; viper ← `tailscale.com` (module graph only; not in the built binary on upstream/main).
Cobra and pflag therefore stay in `go.sum`/module graph whatever Headscale picks, as long as huma and tailscale.com require them;
the binary only links what `cmd/headscale` imports (check: `go version -m` lists `spf13/cobra`, `spf13/pflag` as deps of the binary; huma's CLI sub-package is not imported - UNVERIFIED which import pulls cobra into the link on upstream/main other than `cmd/headscale/cli`).

## Facts the framework decision should use

1. Viper is already gone on main; "cobra's link to viper is worth nothing" is true today, not in the future. Update 001 l.3313 (#3674 is merged).
1. The surface is shallow: no completion functions, templates, custom flag types, hooks. The costly parts of a migration are (a) 28 aliases (3 survive in 001), (b) required flags, mutually exclusive flag, ArbitraryArgs behaviour, and (c) completion scripts.
1. Completion is the one thing outside the repo that calls the CLI contract: nixpkgs runs `headscale completion bash|fish|zsh`. Static completion (001) matches what exists today (nothing dynamic).
1. `creachadair/command` is already used by three small tools but none exercise short flags, aliases, flags after positionals, required flags or completion; #2647 had to build aliases by hand and has no completion.
1. #2647 was closed with one line ("abandon for now"), no review. There is no recorded technical objection to `command`.
1. Binary size is not a factor: cobra+pflag ≈ 0.2 MB of 79 MB.

## Open questions for the maintainer

1. **Does `headscale completion <shell>` have to keep working, with the same name and shells?** nixpkgs calls it at build time.
   (a) Keep it: the adapter must generate bash/zsh/fish (and powershell today via cobra); stays on cobra, or a new framework needs its own generator (cost: new code, per-shell testing).
   (b) Drop or rename it: nixpkgs and users break; needs a CHANGELOG BREAKING entry and a nixpkgs patch (cost: coordination, small).
1. **Do unknown-command suggestions ("Did you mean ...") and `help <cmd>` have to stay?** 001 does not say.
   (a) Own it in the spec layer (the "Did you mean" in 001 l.779 is for columns only; commands would need new code, ~Levenshtein over the spec tree);
   (b) accept whatever the framework gives; cobra gives suggestions by default.
1. **Mutually exclusive and required-flag rules: field-level in the spec or per-command `Validate`?** Today cobra does it (16 required, 1 exclusive).
   (a) A small rule vocabulary in the spec (`required`, `exclusive`), tested like the rest; (b) a free `Validate(in)` per command, simpler, less generated help ("required" marker in help would need a tag).
1. **Is a migration in the same release as the CLI redesign acceptable?** #2647 mixed both and was dropped.
   (a) Redesign on cobra behind the spec, framework swap later in one file (001's current plan; cost: cobra's global state and `OnInitialize`-style hooks live in the adapter, tests rely on cobra's `SetOut`);
   (b) swap first, redesign second (cost: two rounds of breaking test edits to 128 integration invocations).
